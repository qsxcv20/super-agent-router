# Super Agent Router

把「会话」当系统来用的编排插件：任务来了自动路由到合适的专项成员、组队派工、
独立验收、把成败沉淀成错题本与实战记录。

安装后你得到的是一套**程序层拦得住**的授权模型 —— 不是提示词里的君子协定：

- 派工没写 SCOPE 白名单 → 直接拒绝派发。
- Worker 想改白名单外的文件 → 越界拦截，工具调用当场被 deny。
- Worker 声称做完却拿不出证据 → 交付被拦一次，要求补证据。
- Worker 的边界算不出来 → **拒绝**，不是放行。

当前版本：**v0.5.9**。

## 装在哪

插件包本体（只读，随插件安装）：

```text
<插件目录>/
  .minimax-plugin/plugin.json    清单：版本、能力声明
  hooks/hooks.json               Hook 接线
  scripts/*.mjs                  Hook 脚本
  skills/super-agent-router/     编排协议（SKILL.md + references/）
  icon.png / icon-dark.png
```

运行时数据（可写，跨会话持久，与插件包分离）：

```text
${PLUGIN_DATA}/dispatches.json  派工台账
```

> `PLUGIN_DATA` 由 Hook 运行时注入，指向插件的数据目录；普通 PowerShell 窗口里
> 没有这个环境变量，要手动找台账文件请用下面的排查第 4 步给的命令。

按项目组织的部分留在项目里，随 git 管理：

```text
.superagent/roster.json          专项名录（归属的唯一依据）
.superagent/methods/<成员名>.md  成员方法论 + 实战记录
.superagent/lessons/<成员名>.md  成员错题本
.superagent/lessons/_router.md   Router 自己的错题本（编排层的锅记这里）
```

## 怎么装

1. 把插件包目录放进 MiniMax Code 的本地插件目录：

   ```text
   C:/Users/yang2/.minimax/plugins/super-agent-router/
   ```

   目录名必须与 `.minimax-plugin/plugin.json` 里的 `name` 一致（`super-agent-router`），
   不要再套一层同名目录。

2. 装完后**新开一个会话**；**从旧版本升级的，还要重启 MiniMax Code 客户端**。

   > **Hook 是按会话激活的。** `SessionStart` 只在新会话或真正恢复的 Hook 会话触发。
   > 安装/升级后不新开会话，Hook 不会跑 —— 这是「装完没反应」最常见的原因，
   > 不是安装失败。
   >
   > **升级场景还要重启客户端**（不只是新开会话）：宿主把 Hook 绑在**注册时按内容哈希物化出的
   > 缓存树**上，覆盖插件文件只会多出一棵新树，运行中的客户端仍绑旧树 ⇒ **不会自动生效**。
   > 机制与自证办法见下面「升级已有安装」一节。
   >
   > **v0.5.0 尤其要注意这条**：本版给 `PreToolUse` 的 matcher 加了 `run_code` 与 `mavis`，
   > 新增的匹配项**只在新会话里生效**。老会话里，`mavis`（含 `agent delete` / `agent update`）
   > 和 `run_code` 这两类调用仍然不会进越界拦截。
   > 原因：匹配项取自**会话绑定的 hook 缓存树**，老会话绑的是老树，老树的 matcher 里没有这两项。
   > 所以「装完/升完版不新开会话」不只是不加载新脚本，而是**新加的匹配项整条不生效**。

3. 确认 Node.js 可用（Hook 脚本用 `node` 执行）：

   ```powershell
   node --version
   ```

4. 项目侧按需建一个 `.superagent/roster.json`。没有它，插件依然能装上并注入协议，
   但路由会缺少专项名录依据，只能退到通用 worker 直做。

### 升级已有安装：必须**重新安装**，然后**重启客户端**并**新开会话**

本版（0.5.9）在 0.5.8 的基础上修掉了「重复调用闸门在 PTC 形态下恒不触发」的**一半**（D-91，只覆盖会话库形态），
并给派工粒度补上「项目」这一维（D-92）；0.5.8 引入的 `scripts/loop-gate.mjs` 与那条新的 `PreToolUse` 匹配项仍在。
**只换一部分文件、或者不重启客户端，新规则都不会生效。**

**并且要当心一处已知缺口（D-97）**：宿主真正喂给 hook 的 transcript 是一份 **Claude 兼容投影**，
与 D-91 假设的会话库形态不同 ⇒ **v0.5.9 装上后，这道闸门在真实运行时仍然一次都不会触发**
（静默失效：不报错、也不留痕）。修法已在仓库主线并**通过活体验证**（全新子会话里 6 连发，第 6 次真被拦下），**待下一个 patch 版本发布**；
在此之前，请把下面「第 6 次会被拦下」理解成**设计意图**，不是**已生效的行为**。

**办法一：从仓库克隆的（推荐，旧版会自动备份）**

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

`install.ps1` 的口径是固定的：目标目录不存在 → 直接装；
**版本号相同 → 报「已是最新 —— 不重装」**；
**版本号不同 → 先把旧版整份备份到 `.backup\super-agent-router-<时间戳>\`，再装新版**。
本次从 0.5.8 升到 0.5.9，版本号变了 ⇒ 会正常备份 + 重新安装。

**办法二：手动覆盖**

把新版本包目录里的内容覆盖到《怎么装》第 1 步说的那个插件目录，
确认 `scripts/loop-gate.mjs` 与 `hooks/hooks.json` 都是新版。

**然后：先重启 MiniMax Code 客户端，再新开会话。** 两步都不能省。

#### 为什么「重新安装」还不够：宿主把 Hook 绑在内容哈希缓存树上

宿主在**插件注册时**按插件包的**内容哈希**物化出一棵缓存树，并把 Hook 绑在那棵树上：

```text
%USERPROFILE%/.minimax/v2/plugin-hook-cache/sha256-tree-v1-<64 位内容哈希>/
```

目录名就是**插件包的内容哈希** —— 包变了，哈希就变，就多出一棵新树。由此有两个确定后果：

- **覆盖磁盘上的插件文件（重新安装）只会多物化出一棵新树**，运行中的客户端**仍绑定旧树**
  ⇒ 新版本不上场；
- 宿主还把**解析后的 Hook 配置缓存在内存**里 ⇒ 即使把新文件直接写进旧树，也**不生效**。

⇒ **升级插件后必须重启 MiniMax Code 客户端，新代码才会生效。**

> **口径与复核条件**：这是 2026-11-12 在本机实测确证的行为（换到 v0.5.8 后，新会话仍跑 v0.5.7 的树）。
> 它是**宿主当前实现**的性质，不是宿主永久承诺 —— **若宿主将来改为热重载，本节需复核**。

#### 怎么自证「当前生效的是哪一版」

不想重启客户端、想先确认现在跑的是哪一份，按下面两步看：

**第 1 步：让当前跑着的 Hook 报出自己的缓存树路径。**

让一个子代理做一次必然越界的操作（例如让它去改 `SCOPE` 之外的文件），
拦截文案里**「批准命令」那一段**会带出**运行中那份副本**的路径，形如：

```text
...\.minimax\v2\plugin-hook-cache\sha256-tree-v1-<64 位哈希>\scripts\scope-amend.mjs
```

那串 `sha256-tree-v1-<hash>` 就是**当前真正在跑**的那棵树
（路径由运行中的 Hook 从**自己所在位置**反推得出，所以它指向的就是实际在跑的那一份）。

**第 2 步：看那棵树里有没有本版才有的文件。**

```powershell
Get-ChildItem "$env:USERPROFILE\.minimax\v2\plugin-hook-cache\sha256-tree-v1-<上一步拿到的哈希>\scripts" -Filter loop-gate.mjs
```

- **查得到 `loop-gate.mjs`** ⇒ 跑的是 **v0.5.8 及以后**的那棵树（这道闸门是 0.5.8 引入的）；
- **查不到**（或 `hooks/hooks.json` 里没有第 5 组 `PreToolUse`）⇒ 跑的是更旧的树 ⇒ **重启客户端**。

再精确一点：**直接读那棵树自己的清单，版本号一目了然**。

```powershell
Get-Content "$env:USERPROFILE\.minimax\v2\plugin-hook-cache\sha256-tree-v1-<上一步拿到的哈希>\.minimax-plugin\plugin.json"
```

里面的 `version` 字段就是**当前真正在跑的那一版**。本插件当前版本是 **v0.5.9** ——
读到 `0.5.9` 说明新代码已上场；读到更小的号 ⇒ 还在跑旧树，**重启客户端**再重测。

## 怎么确认 Hook 真的生效

按这个顺序看，**三条都命中才算完全生效**：

### 第 1 步：新会话里应该自动出现协议注入

新开一个会话，第一轮就能看到类似这样的注入：

```text
[super-agent-router] 本会话已启用 Super-agent 编排机制。
```

看不到 → 跳到下面的排查清单第 1、2 条。

### 第 2 步：问一句带编排意图的话，应该看到路由指令

输入「帮我把这个需求拆给合适的成员」，或任何明确要求拆分 / 并行 / 派谁 / 验收的提问
（书面说法如「派工 / 组队 / 拆成 / 分工 / 验收 / 复盘」，口语说法如「拆一下」「分头做」「谁负责」同样算数）：

```text
[super-agent-router] 本轮按编排流程处理。
```

看不到 → Hook 装上了但意图粗筛没命中（换一句明确要求拆分 / 并行 / 派谁的话再试）；
仍然看不到则看排查清单第 3 条。

### 第 3 步：派一个工，越界应该被当场拦下

派一个带 SCOPE 的工，让 worker 去改一个 SCOPE 外的文件，应该看到拦截：

```text
[super-agent-router] 越界拦截：本次派工声明的 SCOPE 为 [...]，目标 ... 不在白名单内
```

拦不住 → 派工时没写 `SCOPE:` 具体路径清单，或写成了否定式禁令。
注意：**只有被派工的子代理受约束**；Router 主会话本来就不该被拦，
如果连 worker 都拦不住，看排查清单第 4 条。

### 第 4 步（可选）：查台账确认链路通了

```powershell
Get-ChildItem -Path "$env:USERPROFILE/.minimax" -Filter dispatches.json -Recurse -ErrorAction SilentlyContinue
```

应能看到两个数组：

- `dispatches` —— 每条有 `parent_session_id`、`scope`、`state`（`active` → `done`）。
- `bindings` —— worker 跑过之后出现，记录该子会话绑定的 scope。

## 不生效时按什么顺序排查

严格按顺序来，从上往下过一遍。**不要跳步** —— 后面的检查依赖前面的结论。

### 1. 是不是没新开会话？

最高频原因。Hook 按会话激活，安装/升级后必须新开一个会话。
先新开会话再重测，这一步能解决大部分「没反应」。
v0.5.0 换了 `hooks.json` 的 matcher，**不新开会话就等于没升级**。

**若是「升级之后新规则整条不生效」，先确认客户端重启过。**
宿主把 Hook 绑在注册时按内容哈希物化出的缓存树上，覆盖插件文件只会多出一棵新树，
运行中的客户端仍绑旧树 ⇒ 光新开会话不够，**必须重启客户端**。
自证当前跑的是哪一版：见「升级已有安装」一节里的「怎么自证当前生效的是哪一版」。

### 2. 插件目录放对了吗？

- 路径：`C:/Users/yang2/.minimax/plugins/super-agent-router/`
- 该目录下的 `.minimax-plugin/plugin.json` 要存在
- 目录名必须等于清单里的 `name`（`super-agent-router`），多套一层就会认不出
- 清单里 `hooks` 与 `skills` 两个数组的每个路径都要真实存在

```powershell
Get-ChildItem -Recurse -File 'C:/Users/yang2/.minimax/plugins/super-agent-router' | Select-Object FullName
```

### 3. Node.js 能不能跑？

所有 Hook 脚本都是 `node` 执行的。`node` 不在 PATH 里，Hook 会静默失败
（Hook 失败是 fail-open 的 —— 不生效，但不会报错给你看）。

```powershell
node --version
```

### 4. 派工的时候到底带没带 SCOPE？

Hook 拦不住越界，最常见的原因是派工时没给可判定的白名单：

- ✅ `SCOPE: src/app.ts, src/util/` —— 具体路径，目录以 `/` 结尾
- ❌ `SCOPE: 不要动生产配置` —— 否定式禁令，程序无法判定，直接不算 scope
- ❌ 只写目录不带 `/` —— 会被当成单个文件，其下的文件全部拦掉

记不住格式就看插件包里的 `references/brief.md`。

### 5. 是不是 Router 自己被拦了？（v0.4.0 已修）

v0.3.x 有个链路漏洞：台账记的是「发起方」会话，于是 worker 在子会话查不到自己的 scope，
Router 在父会话反而命中了 —— 表现为「派完第一个工，Router 连自己的收尾文件都写不了」。

v0.4.0 已修：约束只落在被派工的子代理身上，Router 父会话不受 worker scope 约束，
worker 的 scope 改从它自己 transcript 的派工原文解析。

如果你在旧会话里遇到这个现象，**新开一个会话**即可确认是否已修复。

### 6. 派工被「组队冲突」或「派工超限」拒绝？

这是组队闸门在正常工作，不是故障：

- **组队冲突** —— 本次 SCOPE 与仍在飞的派工重叠。要么等它结束再派，要么把范围拆开。
- **派工超限** —— 并发在飞上限 6 个、累计上限 30 个。说明任务没拆干净，或者在用派工代替思考。

两个闸门都只算**写冲突**，读范围天然重叠不会被拦 —— 只读条目（`ro:`）也永远不构成写冲突。

### 7. 插件在设置里被禁用了吗？

已安装的本地插件默认启用，但如果你之前手动关过同一个目录，它会保持关闭状态。
到设置里的插件列表确认它处于启用状态。

### 8. 报「越界拦截」但你确认路径没问题？

- 绝对路径与相对路径都会折算后比对 —— 通常不是路径写法的问题。
- 目录 scope 必须以 `/` 结尾才涵盖其下所有文件；写成 `src/app` 时，
  `src/app/sub/x.ts` 会被拦。
- 读操作比写宽松：允许读 scope 所在目录树（读邻近文件理解上下文是正当的）。
- 派工用 `ro:` 条目时，读放行、写照拦 —— 这是设计，不是误判。

### 9. Worker 报「解析不到边界」被拒绝？

v0.5.0 起，worker 的 scope 来自它自己 transcript 里的派工原文；解析不出来时**一律拒绝**，
不再放行。看到这条说明派工原文有问题：

- brief 里必须有一行可解析的 `SCOPE:` 清单
- 路径要写成规范路径，别用否定式表述
- 派工的内容要确实进了 worker 的 transcript

### 10. 派工被取消后，名额没还回来？

派工被取消（或子会话异常退出）时**不会触发** `SubagentStop`，
台账里的 `state` 会停在 `active`，一直占着并发名额（上限 6 个）到 TTL（2 小时）。
表现是「机制突然不让我派工了」，但报的是「在飞派工已达上限」，不指向真正原因。

注意：**TTL 到期只回收台账名额，不会停掉还在跑的子代理** —— 名额回来了，
子代理还在跑、还在消耗资源。止损要显式停：停后台任务用 `task_stop`，
停子会话当前轮次用 `mavis_session_interrupt`。

取消后请显式释放：

```powershell
$env:PLUGIN_DATA = "$env:USERPROFILE\.minimax\v2\plugin-data\hooks\super-agent-router"
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\release-slot.mjs" --dispatch dsp_xxx
```

释放某个父会话下的全部在飞派工：

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\release-slot.mjs" --parent mvs_xxx
```

> **用开关而不是 JSON**：PowerShell 的原生参数解析会吃掉 JSON 里的双引号 ——
> `node x.mjs '{"id":"a"}'` 实际收到 `{"id:a}`（非法 JSON）。
> 开关形式不含引号，跨 shell 一致。JSON 形式仍然支持，但在 PowerShell 里要自己转义。

只把仍在飞的（`active`）记录翻成 `aborted`，已完成的记录不动。
id 写错或台账读不出来时会直接报错退出，不会「假装释放成功」。

### 11. 粗筛像是从不命中？先看留痕文件

载荷坏掉时（平台改了字段名、JSON 不合法），粗筛会**留痕而不是静默退出**。
痕迹文件在插件的数据目录下：

```powershell
Get-Content "$env:USERPROFILE\.minimax\v2\plugin-data\hooks\super-agent-router\gate-trace.jsonl" -Tail 20
```

- 看到 `payload-parse-failed` 或 `prompt-field-missing` → 是**载荷问题**，不是粗筛词表的问题；
- 文件不存在 → 载荷没问题，是「没命中」，回第 2 步看意图词。

### 12. 派工被拒，报「目标成员在账号里不存在」？

v0.5.6 起，派工会核验目标成员是否真的存在于**账号成员目录**
（`~/.minimax/agents/<name>/`，内置成员在 `.builtin/` 下）。
不存在就**拒绝派工** —— 因为派给一个不存在的成员不会启动子会话，
却会占掉名额、还会让同 SCOPE 的后续派工被「组队冲突」误拦，**外观完全正常**。

处理顺序：

1. 确认成员名写对了（显示名与 routing id 是两套命名空间，别混用）；
2. 确认账号里真有这个成员 —— 建号是**账号级危险动作**，只能由你本人发起，
   插件会拦子代理的建号调用（与删除、改写对称）；
3. 若该成员只是项目自己声明的专项成员、账号里还没有，
   在**账号名单不可得**的环境里会走降级路径：这条派工**不占名额、不参与 SCOPE 冲突判定**，
   并会向你披露一段降级提示（说明这次**没有核验**目标成员是否存在）。

查这次派工被判成什么：

```powershell
Get-Content "$env:USERPROFILE\.minimax\v2\plugin-data\hooks\super-agent-router\gate-trace.jsonl" -Tail 20
```

台账记录上带 `member_existence` 字段，三态可分辨：

| 值 | 含义 |
|---|---|
| `account_verified` | 账号名单可得且核验通过（正常路径） |
| `roster_declared` | 账号名单不可得，但该成员在项目名录里登记过 |
| `unverified` | 账号侧核验不了，项目名录里也没有登记 |

### 13. 派工回执里没有「复用提示」？

复用提示**只在该成员已有可复用会话时出现** —— 判据只有一条：
那个会话的绑定范围是否覆盖本单要动的路径。

看不到提示通常是这几种情况（**不是故障**）：

- 换了专项成员（不同成员的会话不能互相复用）；
- 换了要动的文件（范围没覆盖上）；
- 那个会话已经**归档** —— 归档过的会话不能再被追加（追加会返回 `TASK_CHILD_ARCHIVED`）；
- 那个会话太久没动，上下文太旧，该新开。

复用是**纪律不是自动机制**：机制只负责把「有得复用」这件事说出来，
**追加动作要你自己发起**（在已有子会话上追加，而不是新派一单）。
详见下面「会话复用：省上下文的纪律」一节。

## 只读条目 `ro:`：想让它读，但不想让它改

同一个 SCOPE 清单里，两种条目可以混着用：

```text
SCOPE: ro: plugin/scripts/, docs/audit/report.md
```

含义是：

| 条目 | 能读 | 能写 |
|---|---|---|
| `ro: plugin/scripts/` | ✅ 该目录树下所有文件 | ❌ 一律拦 |
| `docs/audit/report.md` | ✅ | ✅（仅这一个文件） |

写法上 `ro: path` 与 `ro:path` 都认；目录条目仍要带结尾的 `/` 才涵盖其下所有文件。

两条配套规则：

- `ro:` 条目**永不**授予写权限 —— 写同一个文件也会被拦。
- `ro:` 条目**不参与**派工的写冲突检测 —— 两个人都只读同一个目录不算冲突。


## 权限等级：给成员更多权限，但不靠自觉

逐路径白名单对「派一个大活」太琐碎。这个插件给每个成员一条**权限等级**（tier）：

| 等级 | 含义 |
|---|---|
| `scoped`（默认） | 逐路径白名单；白名单外一律拦，越界自动记账进待审清单 |
| `full` | 项目工作区内自由读写，不必逐路径枚举 |

**每个成员都是平等的** —— `full` 不是某些成员的特权，任何成员都可以被管理员提权。
提权这个动作在管理员手里：

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --tiers
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --tier full --agent sa-gate-integrity --approver <父会话 id>
```

**`<父会话 id>` 填什么**：填**你这一侧的父会话 id**（你自己的 session id，形如 `mvs_xxx`），
**不能写「router」「管理员」这种自称** —— 机制只认台账里真实存在过的父会话 id，
写个自称会被直接拒掉（报错里会列出已知的父会话 id）。
`--tiers` 看当前所有成员的等级。

提权写进 `.superagent/roster.json`，留痕 `.superagent/changes.log`。
收回就是把 `full` 换回 `scoped`（同一条命令，改一个词）。

**`full` 不等于无限权限**，这四条照旧生效：

1. `.superagent/` 编排层私有状态目录除外 —— 那是成员互相篡位、自己给自己提权的战场；
2. 工作区之外的路径仍然拦，并自动记账待审；
3. 账号级 / 对外不可逆动作（删成员、改成员、部署、发布）照旧硬拦；
4. **写冲突检测仍按声明的 SCOPE 比对** —— `full` 放开的是「白名单外的项目内路径」，
   不是「冲突检测」；所以 `full` 成员的 SCOPE 仍要写清楚它实际要动的范围。

**诚实边界**：提权并不是「worker 绝对改不了自己的等级」—— 机制做的是
把**权威面脚本**（提权 / 批准扩权 / 写履历 / 写错题本 / 登记成员）列为父会话专属，
子代理执行它们会被护栏直接拒绝（这是主防线）；admin CLI 还要求**批准人是真实的父会话 id**
（纵深防御）；提权与批准全部留痕。
但 hook 是护栏不是沙箱 —— 完整的诚实边界见下面的「诚实边界：护栏是护栏，不是沙箱」一节。

**等级按派工时快照**：派工那一刻把成员的 tier 写进派工记录，子会话绑定继承这份快照 ——
会话中途的等级变更对**已在飞**的会话不生效（下一个派工才按新等级生效）。

## 子代理撞墙了怎么办：自动审核，一键批准

子代理撞到 scope 墙时，护栏**自动**把「它想访问什么、被拒了什么」记进台账 ——
不用等 worker 汇报。整个流程是**三步**，自动的是前两步，批准永远是人工的：

| 步 | 谁做 | 发生什么 |
|---|---|---|
| 1. 发现 + 记账 | **自动** | 撞墙当场写进台账 `scope_requests[]`，同目标重复撞墙只记一条（`hits` 累加） |
| 2. 审核 | **父会话** | 一条命令看待审清单，逐条决定批 / 拒 |
| 3. 批准 | **父会话** | 批准后目标并入该派工的 scope，同步派工记录与子会话绑定，worker 下一次访问即生效 |

### 第 1 步：看待审清单

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --list
```

清单里每条都直接给出 `parent_session_id` —— 那是批准时要填的值，照抄即可。

### 第 2 步：批准一条（读请求只授读，写仍然拦）

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --grant req_xxx --approver <父会话 id>
```

`<父会话 id>` = 该派工记录里的 `parent_session_id`（父会话自己的 session id），
**不是「router」这种自称** —— 机制只认台账里真实存在过的父会话 id，自称会被直接拒掉。

拒绝一条：

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --deny req_xxx --approver <父会话 id> --reason "不该读"
```

直接给某个仍在飞的派工加条目（不走待审清单的那条路）：

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --dispatch dsp_xxx --add src/app/ --approver <父会话 id>
```

### 三条批准口径

1. **批准必须落在仍在飞的派工上** —— 派工结束了就拒绝扩权（事后再补权限没有意义，重新派工即可）。
   两条扩权路径（`--grant` 与 `--dispatch --add`）**同口径**，都会查派工状态。
2. **批准读 ≠ 批准写** —— 读请求只加 `ro:` 条目，写同一路径仍然被拦。
3. **私有记忆目录的扩权会被当场拒绝** —— `.superagent/lessons/`、`.superagent/methods/`
   下的路径即使被批准也**不会生效**（范围层一律不授予），所以机制直接拒掉并提示正确路径：
   需要那段内容，请让 Router 转写进 brief。

自动的是**发现与记账**，批准权始终在管理员手里：让被约束者自己决定边界等于拆掉授权模型。

批准人校验是**纵深防御**，不是主防线：worker 的派工原文里就带着 `PARENT SESSION:`，
所以它挡不住蓄意自提权；主防线是「权威面脚本父会话专属」。

## 会话复用：省上下文的纪律，不是自动机制

给同一个专项成员派**连续**的活时，优先**复用它已有的子会话**，不要每次新开。

**为什么值得在意**：每新开一个子会话，那位成员都要**重新读一遍**它需要读的东西
（方法论文件、契约、台账、相关脚本、既有报告）。这些重复读取会挤掉它真正要干的活，
也会逼你重新写一遍「这个人知道什么、不知道什么」的铺垫。

**机制帮你做到哪一步**：派工时如果发现该成员已有会话、且那个会话的范围覆盖本单要动的路径，
派工回执里会给你一条**复用提示**，告诉你有几个会话可复用。

**机制不帮你做的**：

- **追加动作要你自己发起** —— 机制不会自己去追加，也不会因为没复用而拦截派工；
- 提示**不阻断派工** —— 换了专项、换了边界、上下文太旧的情况，本来就该新开。

所以这一条是**纪律**：判断「该不该复用」是你的活，机制只负责提醒你别忘了。

**归档与复用互斥**：

| 会话状态 | 还能不能追加复用 |
|---|---|
| 刚做完、产物已落盘、短期内可能还要续 | 能（上下文完整保留） |
| 做完很久、产物已落盘、不会再续 | 不能（已归档的会话追加会返回 `TASK_CHILD_ARCHIVED`） |

归档**不会丢产物**（代码与报告都在工作树里），只影响「能不能继续追加这一轮对话」。
别为了「窗口列表好看」把还能复用的会话归档掉 —— 复用省的是上下文，归档省的是列表长度。

**追加时的一个坑**：追加的内容会**并入该子会话的下一轮**，
所以追加内容里写的 `SCOPE:` 行会**参与边界解析**。
要么根本不写 `SCOPE`（原有边界会继承），要么写成协议格式（`SCOPE: path/a.ts, path/b.ts`，
逗号分隔、无反引号、行首 `SCOPE:`）。
写成「本单 SCOPE：`a`、`b`」这种顿号 + 反引号的形式，解析器会得到 0 条条目，
后果是该子会话**整轮所有工具调用都被拒**（读、写、bash 全被拦）。

完整口径见 `references/contract.md` 的 **S4.5**。

## 诚实边界：护栏是护栏，不是沙箱

这一节请认真读 —— 它决定了你该怎么看待这个插件拦下来的每一次拒绝。

**机制做到的**：

- 派工没写可判定的 SCOPE → **拒绝派工**，不猜、不放行；
- worker 的工具调用越过 SCOPE → **当场拒绝**，并自动记账进待审清单；
- 越界被拒的路径若在私有状态目录里 → 诊断文案**不误导**，也不会给一条永远不会生效的批准提示；
- 权威面脚本（提权 / 批准扩权 / 写履历 / 写错题本 / 登记成员）→ **子代理执行即拒**；
- 扩权与提权的批准人 → 必须是**真实的父会话 id**，且必须落在**仍在飞**的派工上；
- 提权与批准 → 全部进 `.superagent/changes.log` 留痕，可审计。

**机制做不到的**（这一段是重点）：

- **hook 是护栏，不是沙箱。** worker 若能执行一段**落盘的脚本**，
  那段脚本**内部**的写入不受判定约束 —— 护栏拦的是「这次工具调用要碰哪个路径」，
  看不见脚本内部又写了什么。
- **权威面脚本父会话专属只降低误用，不是绝对禁止。** 把脚本复制一份、改个名字再执行，
  或用内联代码直接写文件，都不在判定范围内。
- **批准人校验挡不住蓄意自提权。** worker 的派工原文里就带着 `PARENT SESSION:`，
  知道父会话 id 就能填对 —— 这一层拦的是「随手写个名字就过」。
- **`full` 等级不是无限权限**：工作区外、私有状态目录、账号级不可逆动作照旧拦，
  且 `full` 放开的是「白名单外的项目内路径」，**不放开写冲突检测**。
- **复合层载荷把命令放进变量时判不了**（v0.5.6 记为设计边界，不是缺陷）：
  `run_code` 里的复合载荷若把危险命令先塞进变量再执行，护栏取不到命令文本，判不了。
  这是复合层判定的**固有限制**，已写进契约与注入，留成明示边界而不是隐性缺口。
- **家目录展开已下沉到 lib 层**（v0.5.7 的 D-80）：
  `~` / `$HOME` / `%USERPROFILE%` 的展开现在做在底层路径折算那一步（早于「拼工作区根」），
  调用方不必各自记得展开 —— 口径只有一处，不会再出现「某个脚本忘了展开」。
  取不到家目录时退回「不展开」，**不会凭空造一个家目录出来**。

**所以真正的防线是这三条**，而不是「脚本层绝对拦得住」：

1. **运行时权限** —— 操作系统与账号层面的权限，是最后一道；
2. **审计留痕** —— `.superagent/changes.log` 与派工台账记下每一次提权与批准；
   验收时**逐条复核**，而不是相信「机制拦住了」；
3. **独立验收** —— `references/review.md` 的扩权复核清单，对扩权结果做人工确认。

一句话：**别把这套机制当成沙箱来用，要当成「可审计的护栏」来用。**
它的价值在于让越界**看得见、留得痕、可复核**，而不是声称越界不可能发生。

## 空设备：`> /dev/null` 不再被当成写目标（v0.5.7）

**这一条是使用者能直接感觉到的变化。**

以前 bash 重定向到**空设备**会被当成写目标，于是：

- 台账里多一条**用不上的越界请求**（噪声，且会把真正的越界请求淹掉）；
- 拦截文案给出**批准了也没意义**的批准命令（批准它也不会让任何东西生效）；
- `node build.js 2>/dev/null` 这种极常见的写法被整条拦下。

现在空设备从写目标与判定对象里剔掉了。收进来的形态：

| 平台 | 形态 |
|---|---|
| POSIX | `/dev/null` `/dev/zero` `/dev/stdout` `/dev/stderr` `/dev/stdin` |
| Windows | `NUL`（大小写不敏感）/ `NUL:` / `\\.\NUL` |
| PowerShell | `$null` |

**两条可直接对照的行为变化**：

| 命令 | 之前 | 现在 |
|---|---|---|
| `tee /dev/null` | **DENY** | **ALLOW** |
| `dd of=/dev/null` | DENY | **仍然 DENY** |

第二条是**刻意留的保守项**，不是漏判：`of=` 是参数形态，护栏对它的识别保守，
所以宁可多判不可漏判。**别把这两条读成「空设备一律放行」。**

**边界没变的部分**：

- 真实路径越界**照常**记账并拦；
- 真实写动词（`rm` / `cp` / `mv` …）**仍然**算写操作；
- 重定向目标**解析不出**时（`cmd >`）**仍然**兜底拒绝 —— 解析不出即拒绝，不放行。

**刻意不收进去的形态**：`/dev/urandom`、`/dev/random` 是**真实设备**（不是丢弃口）；
`> null` 在 bash 里会真的建一个叫 `null` 的文件，那是**真实写目标**。

**要处理已有的历史待审项**：这次**只堵产生侧** —— 台账里**已经记着**的历史 `/dev/null` 待审项，
`--grant` 仍会把它写进 scope（批准它没有意义）。
需要人工在待审清单里**拒绝**它们：

```powershell
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --list
node "$env:USERPROFILE\.minimax\plugins\super-agent-router\scripts\scope-amend.mjs" --deny req_xxx --approver <父会话 id> --reason "空设备不是写目标"
```


## 重复调用闸门：子代理卡在同一个调用上（v0.5.8）

**这一条是使用者能直接感觉到的变化。**

子代理有时会陷进「查证 → 再查证 → 再查证」的循环：同一条命令连着跑十几遍，
每遍都以为能多出一点信息，其实什么也没多。**以前没有任何一层看得见** ——
看门狗只在子代理**停下**时才看它最后一句话，循环跑到一半是黑的；
父会话在它停之前完全不知情，只看到 token 在烧。

现在加了一道闸门（规则编号 `R-LOOP-SAME-CALL`）：
**同一个子代理连续发起 5 次完全相同的工具调用**（中间没有任何别的工具调用）时，
**第 6 次当场被拦下** —— **前提是装的是含 D-97 修复的版本**（0.5.9 不含，见上面的升级节）。

### 什么时候会拦你

拦的是**「严格连续」的重复** —— 连续 5 次发起**参数完全一样**的同一种调用：

- `run_code` / `bash`：同一条命令连着跑；
- `task_output`：用**完全相同的参数**轮询同一个后台任务；
- `read`：**同一个文件、同样的 `offset` / `limit`** 连着读
  （换一段区间读不算重复 —— 那是新信息）。

中间插进任何别的工具调用，连续计数就**断开**（这是故意的：正常的迭代不该被拦）。

### 被拦了怎么办

被拦时子代理会收到一条明确指令：

> 你已经连续第 N 次发起**完全相同**的工具调用 ⇒ 这一轮不会再产生新信息。
> **请现在就交付当前结论，或说明卡在哪一步、还缺什么**；
> 确实必须再跑同一条命令，请说明为什么前几次没有产出新证据。

**被拦不等于干活失败** —— 它是在催**先给结论，别再空转**。你看到这条 deny 时：

1. 让子代理**先交当前结论**（哪怕结论是「结论是 X，卡在 Y」）；
2. 判断它是不是真缺信息 —— 它**换了参数**再跑（换 `wait_ms`、换 `offset`）就**不会被拦**；
3. 确实必须反复跑同一条命令时，让它**说明理由**，而不是硬顶。

### 阈值能调

默认 **5**（也就是拦第 6 次）。嫌紧就调大：

```powershell
$env:SAR_LOOP_GATE_MAX_SAME = "8"
```

**调大只会少拦、不会多拦** —— 方向永远是安全的那一侧；调小 = 更严（也更容易误伤）。

**唯一常见的误伤**：合法地等一个跑很久的后台任务时，连续用**完全相同的参数**轮询 5 次会被拦一次。
换个 `wait_ms` 再轮询就换了指纹，不会被拦。

### 它不拦什么（诚实边界）

- **只覆盖「严格连续」这一族。** 「查证 → 验证 → 再查证」这种**被别的调用打断**的打散形态，
  覆盖有限 —— 每次调用之间夹了别的工具，连续计数就断了。
  要覆盖那种形态需要「同一指纹累计次数」口径，**那是另一条规则，本版没有**。
- **读不到历史就放行。** 这是**效率闸门**，不是安全闸门：万一读不到子代理的历史，
  它会**放行**而不是乱拦 —— 拦错的代价是「子代理干不了活」，比「少拦一次循环」严重得多。
  **这与越界拦截（安全闸门）方向相反，是刻意的。**
- **不影响越界判定。** 「文件越不越界」是另一回事，仍由护栏独立判定；本闸门失效也不放宽它。
- **父会话不会被拦** —— 这道闸门只管子代理。

### v0.5.9 修好了什么：这道闸门以前在真实运行时整条没跑

**这一条是使用者能直接感觉到的变化。**

v0.5.8 引入这道闸门时，它在本机默认的 PTC 形态下**一次都不会触发**。
原因是：宿主把 `PreToolUse` 派发在**子调用**上 ⇒ 闸门收到的载荷是**内层**工具
（`tool_name='bash'`），而 transcript 的 `message.content[]` 记的是**外层** `run_code`
⇒ 两个命名空间的指纹**永不相等** ⇒ 末尾连续数**恒为 0** ⇒ 闸门恒不触发。

现在改成**按载荷形态择一计数**：载荷是内层工具就数 `message.details.ptc.child_calls[]`，
是外层工具就数 `content[]` 里的 toolCall，**两套序列绝不混数**
（两套在 transcript 里是交替出现的，混数会把连续段切碎 ⇒ 更拦不到）。
另外加了**可比性**判定：宿主落盘的内层参数是**子集**
（`grep` / `glob` 参数全空、`read` 只记 `path`）⇒ 与载荷不可比时
**打断连续段但不计入**（宁可少拦一次，不误伤正常分段读取）。


**修好之后的效果（判定逻辑层）**：子代理真的连着跑同一条命令时，第 6 次会被拦下来催它交结论。
**活体拦截证据仍未取到** —— 见下面三条边界。

**但有三条边界必须一起读**（不要只读上一句）：

1. **活体拦截证据仍未取到。** 判定逻辑已由**真实 transcript + 真实载荷本地回放**坐实
   （内层 `bash` 连跑第 6 次 deny、外层 `run_code` 第 6 次 deny），
   但「**真实客户端里真被拦下过**」这条证据**还没有** ——
   需要先安装 + **重启 MiniMax Code 客户端** + 重跑活体探针才取得到。
   **在拿到之前，不要把它当成「已经生效」。**
2. **参数只落子集的那类调用不可判。** `grep` / `glob` 这类内层参数全空的调用
   ⇒ 实测**连跑 29 次逐字相同的 `grep` 仍然放行**。
   这是 fail-open 方向（少拦一次，不误伤），不藏。
3. **仍然是效率闸门。** 读不到子代理的历史就**放行**、不乱拦 —— 与越界拦截（安全闸门）方向相反，是刻意的。

## brief 是 worker 唯一的协议载体

这条是运行时事实，不是什么设计偏好：

> `plugin/hooks/hooks.json` 声明的 Hook 全部挂在**父会话（Router）**的事件流上。
> **子会话不会触发 `SessionStart`，也不会触发 `UserPromptSubmit`。**
> 没有对应事件可挂，代码层面关不掉。

所以「会话开始自动注入编排协议」这件事**只对 Router 生效**。对 worker 来说：

| worker 需要的东西 | 怎么到达 |
|---|---|
| 编排协议要点 | **随 brief 走** —— Router 在 brief 里写清，别指望 hook 自动注入 |
| 派工白名单（SCOPE） | brief 正文 + 子会话 transcript |
| 该成员的历史教训 | 机制直接注入 worker 上下文（v0.5.0 起，不再只挂父会话） |
| 该成员的实战记录 | 派工时随注入文本给出（匹配阶段给 Router 参考） |

结论：**brief 少写一条，worker 就少一条依据。**
目标、边界、验收标准、交付要求，一条都不能省。

## v0.5.0 的破坏性变更

以下四项会改变现有用法。升级前请逐条检查，避免「以前能跑、升级后被拦」。

1. **解析不到边界 = 拒绝（不再放行）。**
   旧 brief 写法若解析不出 SCOPE，worker 会被拒绝操作。
   - 检查：所有在用的派工 brief 是否都含一行可解析的 `SCOPE:` 路径清单。

2. **通道判定变严。**
   bash 现在按**命令意图**分流（只读命令按读判定，其余按写判定）；
   glob / grep 改按**有效检索根**判定；未登记的文件类工具名一律按**写**判定。
   - 检查：worker 脚本里是否有依赖「bash 里带点的东西不算路径」的写法；
     是否有对目录树外做 glob/grep 的步骤需要补进 scope。

3. **履历的验收方必须真实存在。**
   写实战记录时，`verified_by` 必须在派工台账里有一条 `state = done` 的记录。
   填一个陌生名字写履历会被拒绝。
   - 检查：现有履历写入流程是否走真实派工验收。
   - 历史履历不受影响：闸门只在**写入时**校验，读取时不管历史记录。

4. **编排层的归因不再写进成员错题本。**
   「brief 给错」「派工给错」「Router 的锅」这类归因会被错题本闸门退回来，
   改记进 `.superagent/lessons/_router.md`（用契约的 7 字段条目模板）。
   - 检查：成员错题本里若有这样的归因，迁到 `_router.md`。

另有一条运行时要求：**`hooks.json` 的 matcher 变了，必须新开会话才生效**（见上面排查第 1 条）。

## 它管什么、不管什么

| | 行为 |
|---|---|
| **写** `write` `edit` `multiedit` `notebookedit` `bash` | 严格：必须精确落在白名单内，否则拦 |
| **读** `read` `glob` `grep` `list` `search` | 宽松：允许读 scope 所在目录树 |
| **复合** `run_code` | 只判危险操作（代码里夹带的 `mavis agent delete` / `website_deploy` 等一律拦）；不扫代码文本里的路径，作用域交回内层调用：每个内层写/读调用各自触发 PreToolUse 重新判定 |
| **危险** `mavis_agent_create` `mavis_agent_delete` `mavis_agent_update` `website_deploy` `miniapp` / `miniapp_publish`，以及 `mavis` 的 `agent create` / `agent delete` / `agent update`、`miniapp` 的 `publish` | 子代理会话里一律拦：账号级或对外可见的不可逆动作，必须由你亲自发起。Router 父会话（你本人）不受此拦。**建号（`mavis_agent_create` / `mavis agent create`）同样在拦** —— 账号成员是跨项目全局可见的，子代理自己建号会让账号成员与项目名录脱钩 |

四条硬边界：

1. **只约束被派工的子代理。** Router 父会话不受 worker scope 约束。
2. **worker 自述完成不算完成。** 派工后必须由独立 verifier 验收。
3. **账号级与对外不可逆操作不由 worker 执行。** 删成员、改成员配置、部署上线、发布 Mini App ——
   这些交回给你亲自发起。
4. **权威面脚本父会话专属。** 提权 / 批准扩权 / 写履历 / 写错题本 / 登记成员这几个脚本，
   子代理执行会被护栏直接拒绝 —— 提权与批准的批准人还必须是真实的父会话 id。
   （这一条的**边界**见上面「诚实边界：护栏是护栏，不是沙箱」。）

## 什么时候它会主动接管（触发语义）

插件在**每一轮**用一句粗筛决定「这一轮要不要展开编排流程」：

| 这句话像什么 | 结果 |
|---|---|
| 在要求拆 / 分 / 并行 / 派谁 / 验收 | **展开**：注入完整路由指令 |
| 改 typo / 查文档 / 加注释 / 修 bug | **不展开**：静默，直接做 |
| 只是出现了「同时 / 多个 / 分别 / 各自 / 并行」 | **不展开**：那不是编排，是普通句子 |

口语也算数：「拆一下这块」「分头做」「谁负责这块」「各做各的」「放到后台做」「几个人一起做」
「复审一下」都能识别；完整判据见 `references/contract.md` 的 **S11**。

信号词必须**和动作词挨着**才算编排 ——「同时打开这两个文件」「批量导入」不是编排，「并行做」才是。

在本工作区**有可用专项成员**（名录里有专精成员、且他有过验收通过的成果）时，
即使这轮不是编排请求，也会多出一行极短提示告诉你「本工作区有可复用的专项成员」。
没有可用专项成员的工作区，这行不会出现 —— 单点小改零噪音。

## 它怎么定位自己：主 agent 是管理层，不是执行层

会话一开始，主 agent 会被明确告知它的定位：

| 归主 agent | 不归主 agent |
|---|---|
| 理解用户到底要什么、定方向 | 具体实现 |
| 拆解任务、组队 | 批量取证（多文件扫描、批量读） |
| 整合产出、给用户最终结论 | 独立验收（必须派独立 verifier） |

所以：**有专项成员 owns 这件事，就派工，不自己上手**；
没有专精成员但这事有方法论要求（要做「精」而不是「能」），先现场配置成员再派工；
只有单点小改（改 typo、查 API、加注释、改配置值）才自己直做。

**成员记忆是共享但隔离的**：教训、履历、方法论各归各的，派工时只注入目标成员自己的历史。
如果发现串味 —— 别人的教训出现在别人的 brief 里、两个成员抢同一个 `owns`、有人改了别人的记录 ——
那是缺陷，要改归属映射，不能默认放着不管。

## 派工粒度：一个项目一个窗口（v0.5.9）

**这一条是使用者能直接感觉到的变化。**

以前的大项目会被拆成十几个子步骤、每个子步骤各开一个窗口 ——
每个新窗口都要**重新读一遍**它需要读的东西（方法论、契约、台账、相关脚本），
既挤掉了它真正要干的活，也要重新铺垫「这个人知道什么、不知道什么」。

现在协议里多了一维：**一个大项目（同一族缺陷 / 同一批交付物 / 同一个验证目标）
由一个窗口从头负责到底**，项目内部的步骤（探针 / 夹具 / 回放 / 取证 / 记录）
由那个窗口自己完成，**不各自另开窗**（契约 `S4.6`）。

**你看到的变化**：

- 一次大任务**只会有一个窗口**从头跟到底，你不用再看十几个窗口各交一份半成品；
- 派工时多了一条必答问题：「这一单是大项目**新的一块**，还是它内部的一个步骤？」
  —— 是步骤就并进那个窗口，不新开；
- 同一专项的连续工作**优先复用已有会话**的规矩照旧有效 —— 现在判断「该不该复用」多了一个维度：
  **这个会话的边界覆盖不覆盖本单要动的路径**。

**诚实边界：这条目前没有代码兜底。** 程序层的组队冲突闸门只看**写范围是否重叠**，
只读类派工**不触发**冲突闸门 ⇒ 程序**拦不住**「同一个项目被拆成十几个窗口」，
这条要靠**派工方遵守**。程序层的「项目键」是后续版本的事。

## 不想用编排？

默认就是 **0 个成员**。改 typo、查 API、单点小改一律直接做 ——
走完全套编排比直接干更慢更贵。只有当任务需要同时做多件不同性质的事、
或某件事有明确的方法论要求、需要做到「精」而不是「能」时，才值得组队。

## 卸载

删掉整个插件目录即可：

```powershell
Remove-Item -Recurse -Force 'C:/Users/yang2/.minimax/plugins/super-agent-router'
```

派工台账留在插件数据目录（`${PLUGIN_DATA}/dispatches.json`），项目侧数据留在项目的
`.superagent/`（名录、方法论、错题本）。两者都不会自动清掉 —— 需要的话自行删除。
