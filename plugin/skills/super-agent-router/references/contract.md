# 编排契约（单一事实源）

> 本文件是**条目模板、编号规则、scope 语义、通道语义、台账口径的唯一出处**。
> brief / 模板 / 验收标准一律**引用本文件**，不得复述——复述即漂移。
> 引用方式：brief 里写「条目模板见 `plugin/skills/super-agent-router/references/contract.md` 第一节」，不要把字段再抄一遍。

## S1 条目模板（7 字段）

任何「缺陷清单 / 验收结论 / 复盘记录」类产出，一律使用下面这套字段，字段名、顺序、字段行独立成行：

```
### <前缀>-<两位序号>
- 触发条件：
- 影响：
- 复现步骤：
- 证据：
- 状态：已复现 | 推断
- 修法方向：
- 还需要什么：
```

### 编号命名空间

| 场景 | 前缀 | 规则 |
|---|---|---|
| 成员产出 | 2~4 位小写缩写 + `-` | 成员自选一个唯一前缀（如 `RG-` 运行时守卫、`CF-` 上下文流），**成员之间不得重名** |
| 合并台账 | `D-` | 由父会话在合并时统一分配，两位数递增 |

硬规则：

- 同一份文件内编号从 01 递增，不跳号、不重号。
- 「条目统计」行必须与实际条数、状态计数自洽（总条数 / 已复现 / 推断）。
- 缺第 7 字段「还需要什么」视为**条目不完整**——已完全确认时写「无，代码路径已确定」。
- 字段名不得改写、不得合并到别的字段段落里（塞进「修法方向」末尾不算）。

## S2 scope 语义

`SCOPE:` 行内每一条路径白名单条目，有两种形态：

| 形态 | 写法 | 授予的权限 |
|---|---|---|
| 可写条目 | `plugin/scripts/guard.mjs`、`plugin/scripts/` | **读 + 写** |
| 只读条目 | `ro: plugin/scripts/` | **只读**，不授予任何写权限 |

判定规则：

1. **读放行**（read / glob / grep / list / search）：允许读 scope 条目**所在目录树**。
   例：条目含 `plugin/scripts/guard.mjs`，则 `plugin/scripts/` 下所有文件可读。
2. **写放行**（write / edit / bash 等写命令）：必须精确命中某个**非 `ro:`** 条目，
   或落在某个以 `/` 结尾的非 `ro:` 目录条目之下。`ro:` 条目永不授予写权限。
3. **只读条目的读放行**与可写条目相同（同样按所在目录树），只是不参与写判定。
4. **派工写冲突检测**（scopeClash）：只比较**可写**条目。`ro:` 条目与任何条目都不构成写冲突。
5. 条目形态可混用：`ro: plugin/scripts/, docs/audit/report.md` 表示「整个 scripts 目录只读 + 报告可写」。
6. **私有记忆目录不得进 SCOPE**：``.superagent/lessons/`` 与 ``.superagent/methods/``
   （或它们之下的任何目录条目）**一律拒绝派工**。读放行按目录树放宽，
   写进白名单等于让 worker 读到**兄弟成员的错题本全文**与 **Router 私有账 ``_router.md``**。
   这些权限**本来就不需要写进 SCOPE** —— 被派工成员自己的方法论与错题本由 guard
   按**精确文件**单独放行（与 SCOPE 无关）。要给别人看某成员的记录，走「Router 转写进 brief」这条契约通道。
   实测依据：独立验收（sa-context-trace）在本轮**真的读到了**兄弟成员规则全文与 `_router.md` 94 行，均未被拦。

### 边界自检三连（父会话派工前必查）

1. **读得到吗**：把成员要读的每一个路径列出来，逐个确认它落在某个 scope 条目的所在目录树内。漏一个 = 成员必然撞墙。
2. **说得准吗**：brief 里每一句关于边界的描述（"整个目录可读"、"只有 X 能写"），必须与 S3 的通道语义一致。半真话比不说更危险。
3. **同源吗**：条目模板、编号规则、状态口径，必须直接引用 S1，不得在 brief 里复述。

## S3 通道语义（同一套 scope，不同工具的判定方式不同）

| 通道 | 判定对象 | 判定方式 |
|---|---|---|
| read / list | 目标路径 | 读判定（S2.1） |
| glob / grep | **有效检索根**（显式 `path` 优先，缺省用当前工作区） | 读判定。**判定对象不是 pattern 本身** |
| write / edit | 目标路径 | 写判定（S2.2） |
| bash | 命令里的路径 token | **按命令意图分流**：只读命令按读判定，其余按写判定 |
| 复合工具（`run_code` 等） | **不做作用域判定** | 只判危险操作（S5.4）；作用域交回内层调用 |

### bash 路径 token 的识别规则

只有满足下列之一才算「路径 token」：

- 含路径分隔符（`/` 或 `\`）；
- 以 `.` 开头的点目录（`.git`）；
- 含已知文件扩展名（`.mjs` `.js` `.ts` `.json` `.md` `.txt` `.py` 等）。

**不得**把带点的标识符当路径（`console.log`、`JSON.stringify`、`m.extractScope`、`v0.4.0` 都不是路径）。

### bash 的只读命令白名单

`cat` `head` `tail` `less` `more` `ls` `dir` `grep` `rg` `find` `type` `stat` `wc` `which` `node --version` `git status` `git log` `git diff` `git show`

命中白名单的命令按**读**判定（路径只要落在读放行范围内即放行）；其余命令按**写**判定。

### 复合工具（run_code）的判定语义

复合工具的载荷是**自由文本代码**，不是路径实参列表。因此：

1. 复合层**只做危险操作判定**（危险工具名 / 危险参数，见 S5.2、S5.4）；
2. 复合层**不对代码文本做路径扫描**：注释、字符串常量、引号里的命令串
   都不得参与作用域判定；
3. 复合层**不套用「取不到目标就 deny」**：那条规则防的是写通道失守，
   对复合工具不适用 —— 不含任何路径 token 的纯计算代码**必须放行**；
4. **作用域判定交回内层调用**：内层 `write` / `edit` / `bash` 各自触发 PreToolUse，
   判定对象是真实实参，比扫描整段代码文本精确。

> 反例（v0.5.0 修掉的误伤）：代码里只要出现一个 scope 外的路径字样
> （哪怕只是注释或字符串常量）、出现 `//` 注释、引号命令里带一个斜杠，
> 或代码不含任何路径 token，整次 `run_code` 就被拒 ——
> 以 `run_code` 为主力工具的 worker 会大面积撞墙。

### bash 通道的危险操作形态

bash 命令是**自由文本**，不能像工具名那样等值匹配 —— 见到 `delete` 就拦会大面积误伤
（`rm build/out.txt` 这类普通路径操作很常见）。要拦的是**命令形态**：

- 「CLI + 子命令 + 动作」的组合：`mavis agent delete <name>`、`mavis agent update <name>`；
- 对外发布类命令：`git push`、`npm publish`、`docker push`、`website_deploy`、`miniapp publish` 等。

判定落在**内层调用**这一层（bash 自己就是内层调用），所以 bash 通道必须自己认得出这些形态，
不能指望复合层兜底（见下节）。

### 容器调用的派发事实（v0.5.1 复测更正）

**容器调用的 PreToolUse 派发不是平台恒定行为 —— 它随会话而变。**

三组活体证据（调用形状完全相同：外层 `run_code` 装一段纯计算 + 一个危险字符串常量）：

| 时间 | 会话 | 结果 |
|---|---|---|
| 2026-11-10 10:22 | `mvs_b0accaba…`（guard 装了日志探针） | **未派发**：同会话容器内的 `read` 有日志条目，外层 `run_code` 一条都没有 |
| 2026-11-10 14:29 | `mvs_20e67557…` | **派发**：外层 `run_code` 被复合层当场 DENY |
| 2026-11-10 15:10 | `mvs_355c229f…`（金丝雀复测） | **派发**：外层 `run_code` 里的危险文本被 DENY，纯计算对照组放行 |

已逐棵核对的事实：`run_code` 是 2026-11-10 08:19 才进入 PreToolUse matcher 的；
11/9 物化的 60 棵 hook 缓存树**全部**没有它，11/10 08:11 之后物化的树全部有。
**推断（未逐棵验证）**：matcher 取自会话绑定的缓存树，所以老会话不派发、新会话派发。

因此：

1. 复合层的危险操作判定**会生效，但不保证每次都生效** —— 它是**纵深防御的加成**，不能当唯一防线；
2. 账号级与对外不可逆动作的拦截，**必须在各内层通道各自做到位**（尤其 bash 通道）——
   v0.5.0 把判定落到内层是必须的，不是多余的；
3. **不要用「合成载荷驱动 guard 脚本」推断平台是否派发** —— 合成载荷只验证**判定逻辑**，
   不验证**触发链路**，两者必须分开验；
4. **也不要用「一次阴性观察」推断平台行为** —— 10:22 那次的阴性观察本身是可信的
   （日志探针在同会话对 `read` 正常工作），但它只对那一个会话成立。
   判定派发行为必须带**金丝雀对照 + 时间戳 + 会话标识**三件套。

## S4 transcript 中的 brief 解析

`readBriefFromTranscript` 必须同时兼容两种 transcript 变体：

| 变体 | 首条 user 消息的形状 |
|---|---|
| `compatible` | `type:"user"` + `message.content[].type:"text"` |
| `codex` | `type:"response_item"` + `payload.role:"user"` + `payload.content[].type:"input_text"` |

定位 brief 的规则：

- **按语义定位，不按固定行号**：从文件开头逐行扫描，扫到第一条含 `SCOPE:` 的 user 消息为止。
- 禁止用 `slice(0, 8)` 这类固定窗口——会话前置消息条数不固定。

**解析失败必须 deny，不能放行。** 解析不到边界 = 边界不存在，此时放行等于没有管控。
deny 理由要写清：解析失败的具体原因（变体不认识 / 没找到 SCOPE 行 / 文件读不到）。

## S5 工具名分流与危险操作

1. **兜底表**：不在已登记工具名单里的**文件类**工具名，一律按**写**判定，不得默认放行。
2. **危险操作双判定**：账号级与对外不可逆操作，除了按工具名匹配，还要看**参数**：
   - `mavis` 工具的 `command` 参数为 `agent delete` / `agent update` → 拦；
   - `miniapp` 的 `action` 为 `publish` → 拦。
3. 危险操作清单：删除/修改成员、部署上线、发布 Mini App、GitHub 推送等对外可见动作。
   **同一份清单必须在 bash 通道同样生效** —— `mavis agent delete <name>` 这种 CLI 形态
   写在命令文本里，工具名匹配不到（见 S3「bash 通道的危险操作形态」）。
4. **命令形态判定，不是字样匹配**：bash 通道按**命令位置**上的「CLI + 子命令 + 动作」组合判定
   （如 `mavis agent delete|update`）；**按字样匹配（见到 delete/remove 即拦）不被认可** ——
   `rm build/out.txt`、`grep "mavis agent delete"` 这类普通操作会被大面积误伤。
   命令替换（`$(...)` / 反引号）载荷、`sh -c` / `eval` 载荷按其**内层命令**同判；
   只读分流仅对**无命令替换**的命令生效（`cat $(mavis agent delete x)` 是实打实的洞）。
   `website_deploy` / `miniapp publish` 在 bash 里**仅按命令位置**拦截
   （`cat website_deploy.md`、`grep "miniapp publish"` 不拦）—— 这两个词在 bash 里更像文件名或文本。
5. **包装器开关必须按包装器分别定义**：带值开关 / 布尔开关 / 前置位置参数三者分列。
   **禁止跨包装器的全局开关表** —— 布尔开关被当成带值开关时，命令词会被吞掉，
   判定落空即放行（`sudo -n mavis agent delete` 曾因此整体逃逸）。
   查表时**不得一律小写化**：`sudo -H`（set-home，布尔）与 `sudo -h`（host，带值）是两个不同的开关。
   认不出的开关按**宁可多判不可漏判**处理。
6. **包装器集合须穷举类别，载荷分两式**：POSIX `-c` 取**一个**参数，
   PowerShell `-Command` 与 cmd `/c` 取**余下全部**；载荷**整体再判一次**。
   `timeout` 的时长是**位置参数**不是开关。
7. **账号级 CLI 的子命令必须是第一个子命令**：`mavis agent delete|update` 算危险，
   `mavis list agent delete` **不算** —— 位置不对就不构成危险形态（过度拦同样是缺陷）。
8. **无法解析的载荷必须拒绝，不得放行**：`<(…)` 进程替换、base64 编码载荷
   （如 `powershell -EncodedCommand <base64>`）与 `$()` / 反引号同属**真执行**；
   解不出内容时按危险处理。
9. **命令位置不得用闭集包装器名单实现**（这是 D-25b/D-25d 的共同根因）：
   段首命中**数据命令清单** → 段内其余 token 与引号内内容皆为**数据**，不参与命令位置判定；
   否则段内**每个 token 都是命令候选**。这样 `exec` / `taskset` / `watch` / `at` / `parallel` /
   `script` / `chroot` / `strace` 以及**任何将来出现的包装器**都自动被覆盖 ——
   因为它们让段首不是数据命令，后续 token 自然进入候选。
   数据命令清单要尽量完整；**`tar` / `unzip` / `zip` / `gzip` 不得收进清单**
   （它们的 `--to-command` 会真执行，收进来等于开盲区）。
10. **载荷取参按 shell 语义**：`sh` / `bash` 的 `-c` 只取**一个**参数作命令串，
    余下是 `$0` / `$1` 位置参数（**不是**命令的一部分）；`powershell` / `cmd` 取**余下整段**；
    base64 载荷解不出即拒绝；`command -v` / `command -V` 是**查询**语义，该段**无命令位置**。
11. **启动器**（`npx` / `bunx`、`npm` / `pnpm exec|dlx`、`yarn dlx`）之后的**首个程序参数**
    按命令位置判定。
4. **复合工具只做危险操作判定**：`run_code` 等复合工具在复合层**不得**做作用域判定
   （见 S3）。命中危险工具名或危险参数时一律拦（`mavis` 的 `agent delete`、
   `miniapp` 的 `publish`、`website_deploy`）；复合层不做路径扫描，
   作用域判定交回内层调用各自触发 PreToolUse。

## S6 派工台账口径

1. **去重键不得只依赖 `turn_id`**：`turn_id` 缺失或为空时，用 `dispatch_id` 兜底，
   且**绝不允许**抹掉其它 agent 或其它 turn 的记录。台账里存在同名键时，只允许覆盖**完全相同**的那一条。
2. **名额回收要有三条路**：
   - 正常结束（SubagentStop）→ 立即回收；
   - **超时兜底**：超过 TTL 的 active 记录判死；
   - **读时自愈**：读取在飞名单时，把已超龄的 active 记录直接判死并落盘。
   只有第 1 条 = 派工被取消/中断/子会话异常退出时名额永久泄漏。
3. **台账里不许有只写不读的字段**：每个写入的字段要么被某处判定读取，要么删掉。
4. 派工状态 `state` 必须与真实情况一致；TTL 过后不允许继续停在 `active`。
5. **取消场景必须由发起方显式释放**：派工被父会话取消 / 中断、或子会话异常退出时，
   **不会触发 SubagentStop**；TTL 兜底要等满 2 小时，期间这条记录一直占着并发名额
   （`MAX_ACTIVE_DISPATCHES` = 6）。台账条目里**没有子会话 id**，
   所以「自动探测子会话是否还活着」不可行 —— 能自动拿到的只有终止事件，
   而取消场景下没有终止事件。**结论：取消场景由发起方显式释放**，
   入口是 `scripts/release-slot.mjs`：
   `node scripts/release-slot.mjs --dispatch dsp_xxx --reason parent_cancelled`
   （或 `--parent mvs_xxx` 释放该父会话下全部在飞派工）。
   **入口必须用开关形式**：PowerShell 的原生参数解析会吃掉 JSON 里的双引号，
   `node x.mjs '{"id":"a"}'` 在 PS 里实际收到 `{"id:a}`（非法 JSON）——
   开关不含引号，跨 shell 一致。JSON 形式仍兼容，但不得作为文档里的推荐写法。
   释放只把 `active` 翻成 `aborted`，`done` / `aborted` 的记录一个字节都不动；
   目标不存在或台账读不出来时**必须报错**，不许静默成功 ——
   否则调用方以为名额放掉了，实际还在占着。
   **释放入口只对发起方开放**：worker 的 SCOPE 不含插件脚本目录，
   通过 bash 通道调它会被 scope 判定拦下（回归里有这条断言）。

## S7 记录闸门（履历 / 错题本 / 名录）

1. **`verified_by` 必须真实**：不能只校验「不等于 agent 名」。要求它在派工台账里存在一条
   `agent == verified_by` 且 `state == 'done'` 的记录——即确实有一个叫这个名字的验收方跑过验收。
2. **归因公平正则要能识别多种语序**：`brief 给错`、`给错的 brief`、`派工给错`、`派工 brief 有误`、
   `Router 的锅` —— 任何指向编排层的归因都不得写进成员错题本。
3. **记录可见性不得按名录顺序截断**：摘要取样应按「有记录的成员」排序后取，
   或对所有成员公平取，不得因为排在名录后面就结构性不可见。
4. **索引口径统一**：同一个文件里，段首定位不得混用相对偏移与绝对索引。

## S8 收尾契约校验（watchdog）

SubagentStop 时，除了检查「有没有声称完成」，还要检查**产出是否满足 S1**：

- 编号前缀一致、序号递增不跳号；
- 每条 7 个字段齐备且独立成行；
- 「条目统计」行与实际条数/状态计数自洽。

任一不满足 → **block** 并明确指出缺哪一项（缺哪个字段 / 哪个编号跳号 / 统计行对不上），
让 worker 一次性补齐，而不是让它反复小修小补。

## S9 归因先过 Router 自检

任何要写进**成员错题本**的条目，先回答一句：**这是成员的锅吗？**

- 是 → 可以写进 `.superagent/lessons/<成员名>.md`；
- 否（Router 给错的 brief / 需求本身矛盾 / 环境不具备）→ **不写进成员错题本**，
  改为记进 Router 自己的错题本 `.superagent/lessons/_router.md`，并在编排层改进项里跟进。

Router 自己的错题本同样受 S1 的 7 字段模板约束，并由 SessionStart 注入 Router 上下文。
（这一条此前只写在文档里、代码从未实现 —— 独立验收查实后已补实现：
`session-start.mjs` 现在会读 `_router.md` 的条目，按 S1 模板抽「编号 + 触发条件 + 修法方向」注入。
注意 `_router.md` 用的是 S1 的 7 字段格式，与成员错题本的 4 字段格式不同，
所以不能复用抽「`- **规则**：`」那条正则 —— 抽出来会是空的。）

## S11 触发语义（何时注入编排指令）

UserPromptSubmit 的粗筛决定「这一轮要不要展开编排流程」。判据分三档，语料与判据见
`docs/audit/d27-acceptance.md`：

| 档 | 含义 | 期望 |
|---|---|---|
| A 编排意图 | 用户在要求拆 / 分 / 并行 / 派谁 / 验收 | **命中** |
| B 单点动作 | 改 typo / 查文档 / 加注释 / 修 bug | **不命中** |
| C 伪信号 | 出现「同时 / 多个 / 分别 / 各自 / 并行」但不是在要求编排 | **不命中** |

判定规则的唯一出处是 lib.mjs 的 judgeTriggerIntent()：

1. **意图词命中即命中** —— 覆盖书面说法（派工 / 组队 / 分工 / 验收 / 复盘）与口语动词短语
   （拆一下 / 拆解 / 分头做 / 谁负责 / 派谁 / 各做各的 / 放到后台 / 复审 / 评审），
   外加机制自指（主动触发 / 触发机制）与多项请求（还有其他的 / 另外 / 顺便）。
2. **信号词必须与动作词邻近同现**（窗口 12 字符）—— 「并行 / 同时 / 多个 / 分别 / 各自 / 一起」
   单独出现不算意图：「同时打开这两个文件」「批量导入」是单点动作，不是编排。
   「并行」还要求带动作后缀（并行做 / 并行跑），否则「并行度调高一点」会被误触发。
3. **SCOPE 提示命中即命中** —— 用户文本里出现 SCOPE: 段。
4. **不得用长度门槛代替判定** —— 中文口语指令通常只有 3~12 字，
   prompt.length > 40 这类硬门槛会把整类口语请求挡在门外（v0.5.0 的漏判 83% 就是这么来的）。

**未命中时的兜底**：仅当「roster 存在 + 有专项成员 + 该成员有实战记录」时，注入**一行**极短提示；
否则**必须 0 字节输出**（单点小改零噪声）。兜底只提示「可以查 roster」，**不改写 owns 归属**。

**载荷坏了必须留痕**：UserPromptSubmit 载荷解析失败、或 prompt 字段不在，
都必须写一条痕迹到 **PLUGIN_DATA 目录下的 `gate-trace.jsonl`**
（运行时 PLUGIN_DATA 本身就是本插件的专属目录 `.../plugin-data/hooks/super-agent-router`，
所以痕迹就在它**下一层**；不要再多拼一层 `hooks/super-agent-router` —— 那是 D-29 修掉的坑），
**不得**静默退出 —— 静默会让「永远不命中」和「判定为不该命中」在日志里长得一样。
## S12 主 agent 定位（管理层不做苦力）

SessionStart 注入必须写明**主 agent 的定位**：它是管理层，不是执行层。判据：

| 情形 | 谁做 |
|---|---|
| 意图理解、拆解、组队、整合、给用户结论 | **主 agent 自己**（不委派） |
| 已有专项成员 `owns` 这件事 | **派工**，主 agent 不亲自上手 |
| 无专精成员但有方法论要求 | 先现场配置成员（方法论文件 → 建成员 → 登记 roster）再派工 |
| 单点小改（typo / 查 API / 加注释 / 改配置值） | 主 agent 直做 |
| 独立验收 | 派 `verifier`，worker 自述不算 |

**注入文本里不得出现与「管理层定位」矛盾的表述**：「不预置成员」与「不自己做专项活」是两件事，
必须分开写 —— 只写前者会被读成「有成员也别派、自己干」。

**成员记忆共享但隔离**：教训、履历、方法论各归各的；派工只注入目标成员自己的历史。
发现串味（别人的教训进了别人的 brief、两个成员抢同一个 `owns`、有人改了别人的记录）
按缺陷处理并改归属映射，不得默认放着不管。

## S13 权限自动审核、扩权与权限等级

### S13.1 三层：发现 → 记账 → 批准

越界管控**自动**做前两件，**不自动**做第三件：

| 环节 | 谁做 | 落地 |
|---|---|---|
| 发现（谁被拦了、想访问什么） | **自动** | guard 的 `denyOutOfScope()` |
| 记账（写进台账待审清单） | **自动** | 台账 `scope_requests[]`，同目标 `hits` 累加去重 |
| 批准（把目标并入该派工的 scope） | **父会话** | `scope-amend.mjs --grant <id>` |

**为什么没有「自动批准」**：让被约束者自己决定边界 = 授权模型被拆掉。
自动的是发现与记账；批准权始终在父会话（管理员）手里。

### S13.2 批准的四条硬规矩

1. **读请求只授读**：批准一条读请求只加 `ro:` 条目，写仍被拦 —— 批准读 ≠ 批准写。
2. **必须落在仍在飞的派工上**：派工已结束（done/aborted）则拒绝扩权 —— 事后再补权限没有意义，重新派工即可。
   **两条扩权路径同口径**：`--grant <id>`（批准一条待审请求）与 `--dispatch <id> --add <path>`
   （直接加条目）都必须查派工状态 —— 只查一条路径，口径就会分裂。
3. **批准必须留痕**：记录批准人与时间，扩权要可审计。
4. **批准人必须是真实的父会话 id**：`--grant` / `--dispatch --add` 的 `--approver`
   要等于该派工的 `parent_session_id`；`--tier` 的 `--approver` 必须是派工台账里
   **存在过的父会话 id**（待审清单 `--list` 会直接给出这个值，父会话照抄即可）。
   这是**纵深防御**，不是主防线 —— worker 的派工原文里就带着 `PARENT SESSION:`，
   所以它挡不住蓄意自提权。文档与代码都不得把它写成「绝对禁止」。

批准后**同时**更新三处：派工记录的 `scope`、子会话绑定的 `scope`、以及 `scope_amended`。
第三处是关键：worker 首次调用工具时边界来自 transcript 里的派工原文，不读台账 ——
只改前两处，批准对「还没发起过工具调用」的 worker 无效。

### S13.3 权限等级（tier）

每个成员都有一条**权限等级**，声明在项目级 `.superagent/roster.json`：

| 等级 | 含义 |
|---|---|
| `scoped`（默认） | 逐路径白名单；白名单外一律拦，越界自动记账 |
| `full` | 项目工作区内自由读写，不必逐路径枚举 |

**每个成员都是平等的** —— `full` 不是某些成员的特权，任何成员都可以被管理员提权；
但**提权这个动作在管理员手里**：
`scope-amend.mjs --tier full --agent <名> --approver <父会话 id>`，
写进 roster.json 并留痕 `.superagent/changes.log`。

**诚实边界（不得写成「worker 无权改自己的等级」——那句话按现状不成立）**：
机制做三件事：

1. **权威面脚本列为父会话专属（主防线）**：提权 / 批准扩权 / 写履历 / 写错题本 / 登记成员
   这几个脚本只允许父会话执行 —— 子代理上下文里执行它们，护栏直接拒绝
   （即使它的 SCOPE 覆盖了插件目录）。
2. **admin CLI 校验批准人（纵深防御）**：批准人必须是真实的父会话 id（见 S13.2 第 4 条）。
3. **留痕**：提权与批准都进 `.superagent/changes.log` 与派工台账。

但 **hook 是护栏不是沙箱**（S13.5）：worker 若能执行一段落盘的脚本，脚本内部的写入
不受判定约束。真正的防线是运行时权限 + 审计留痕 + 验收时复核
（`references/review.md` 的扩权复核清单）。

**等级按派工时快照**：派工那一刻把成员的 tier 写进派工记录，子会话绑定继承这份快照 ——
会话中途发生的等级变更对**已在飞**的会话不生效（下一个派工才按新等级生效）。

`full` 仍然**不等于**无限权限，下列四条照旧生效：

1. **`.superagent/` 编排层私有状态目录除外** —— 那是成员互相篡位与自提权的战场。
   成员自己的方法论与错题本走 guard 的 `exactPaths`（按精确文件放行），与 tier 无关。
2. **工作区之外的路径仍拦**，并仍自动记账待审（父会话可逐条批准）。
3. **账号级 / 对外不可逆动作照旧硬拦**（删成员、改成员、部署、发布）—— 与 tier 无关。

**第四条边界（容易漏，必须写明）：写冲突检测仍按**声明的** SCOPE 比对。**
两名 full 等级成员若声明的 SCOPE 不重叠，组队闸门不会拦它们 ——
但两人实际都能改动项目内任意文件，可能撞车。
所以 full 成员的 SCOPE **仍要写清楚它实际要动的范围** —— 那是给人看的意图声明，
也是冲突检测的唯一依据。full 放开的是「白名单外的项目内路径」，不是「冲突检测」。

### S13.4 派工闸门 1c：SCOPE 里的 .superagent/ 有三种形态，三种判法

读模式按目录树放宽，**文件条目的读范围是它所在的整个目录** ——
所以 `.superagent/` 下的条目必须逐形态判，不能一刀切也不能全放：

| 形态 | 判定 | 理由 |
|---|---|---|
| 目录条目（`ro: .superagent/`） | **拒派** | 树就是整棵 `.superagent/` ⇒ 能读到兄弟成员的错题本全文与方法论全文 |
| 可写文件条目（`.superagent/roster.json`） | **拒派** | 能改 `tier` 字段 ⇒ **自己给自己提权** |
| 只读文件条目（`ro: .superagent/roster.json`） | **允许，但精确生效** | 不展开目录树 ⇒ 只读得到那一个文件 |
| `.superagent/lessons/`、`.superagent/methods/` 下任何条目 | **拒派**（闸门 1b） | 那是每个成员自己的记忆，不是共享资产 |

「精确生效」是代码保证，不是约定：`inScope` 的读模式遇到 `.superagent/` 条目直接跳过树根展开，
所以「读一个 roster.json」读不到兄弟成员的错题本。

**第二道防线**：worker 的边界也可以**直接从 transcript 的 brief** 建起来（不经 dispatch），
那条路绕过闸门 1c —— 所以 guard 在建边界时自己再封一次
（brief 里含 `.superagent/lessons/` 或 `.superagent/methods/` ⇒ 直接拒绝建立边界）。

成员自己的方法论与错题本由 guard 按精确文件（`exactPaths`）单独放行，与 SCOPE 无关；
需要别人的历史，走「Router 转写进 brief」这条契约通道。

### S13.5 诚实边界

hook 是**护栏不是沙箱**：worker 若能执行一段落盘的脚本，脚本内部的 fs 写入不受本判定约束。
tier 的真正保证是「提权由管理员执行 + roster.json 可审计 + changes.log 留痕 + 运行时权限」，
不是「脚本层绝对拦得住」。

把权威面脚本列为父会话专属（S13.3 第 1 条）能**降低误用**，但它同样不是沙箱：
把脚本复制一份、改个名字再执行，或用内联代码直接写文件，都不在判定范围内。
这一层的兜底是运行时权限 + 审计留痕 + 验收时复核。
