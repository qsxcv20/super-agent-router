# 编排契约（单一事实源）

> 本文件是**条目模板、编号规则、scope 语义、通道语义、台账口径的唯一出处**。
> brief / 模板 / 验收标准一律**引用本文件**，不得复述——复述即漂移。
> 引用方式：brief 里写「条目模板见 `plugin/skills/super-agent-router/references/contract.md` 第一节」，不要把字段再抄一遍。

## S1 条目模板（7 字段）

任何「缺陷清单 / 验收结论 / 复盘记录」类产出，一律使用下面这套字段，字段名、顺序、字段行独立成行：

```
### <前缀>-<两位序号>
- 触发条件：
- 影响：
- 复现步骤：
- 证据：
- 状态：已复现 | 推断
- 修法方向：
- 还需要什么：
```

### 编号命名空间

| 场景 | 前缀 | 规则 |
|---|---|---|
| 成员产出 | 2~4 位小写缩写 + `-` | 成员自选一个唯一前缀（如 `RG-` 运行时守卫、`CF-` 上下文流），**成员之间不得重名** |
| 合并台账 | `D-` | 由父会话在合并时统一分配，两位数递增 |

硬规则：

- 同一份文件内编号从 01 递增，不跳号、不重号。
- 「条目统计」行必须与实际条数、状态计数自洽（总条数 / 已复现 / 推断）。
- 缺第 7 字段「还需要什么」视为**条目不完整**——已完全确认时写「无，代码路径已确定」。
- 字段名不得改写、不得合并到别的字段段落里（塞进「修法方向」末尾不算）。

## S2 scope 语义

`SCOPE:` 行内每一条路径白名单条目，有两种形态：

| 形态 | 写法 | 授予的权限 |
|---|---|---|
| 可写条目 | `plugin/scripts/guard.mjs`、`plugin/scripts/` | **读 + 写** |
| 只读条目 | `ro: plugin/scripts/` | **只读**，不授予任何写权限 |

判定规则：

1. **读放行**（read / glob / grep / list / search）：允许读 scope 条目**所在目录树**。
   例：条目含 `plugin/scripts/guard.mjs`，则 `plugin/scripts/` 下所有文件可读。
2. **写放行**（write / edit / bash 等写命令）：必须精确命中某个**非 `ro:`** 条目，
   或落在某个以 `/` 结尾的非 `ro:` 目录条目之下。`ro:` 条目永不授予写权限。
3. **只读条目的读放行**与可写条目相同（同样按所在目录树），只是不参与写判定。
4. **派工写冲突检测**（scopeClash）：只比较**可写**条目。`ro:` 条目与任何条目都不构成写冲突。
5. 条目形态可混用：`ro: plugin/scripts/, docs/audit/report.md` 表示「整个 scripts 目录只读 + 报告可写」。
6. **私有记忆目录不得进 SCOPE**：``.superagent/lessons/`` 与 ``.superagent/methods/``
   （或它们之下的任何目录条目）**一律拒绝派工**。读放行按目录树放宽，
   写进白名单等于让 worker 读到**兄弟成员的错题本全文**与 **Router 私有账 ``_router.md``**。
   这些权限**本来就不需要写进 SCOPE** —— 被派工成员自己的方法论与错题本由 guard
   按**精确文件**单独放行（与 SCOPE 无关）。要给别人看某成员的记录，走「Router 转写进 brief」这条契约通道。
   实测依据：独立验收（sa-context-trace）在本轮**真的读到了**兄弟成员规则全文与 `_router.md` 94 行，均未被拦。

7. **切分必须尊重路径里的空格**（F-04）：

   - 先按**逗号**（`,` 与 `,`）切 —— 逗号是条目分隔符；
   - 每个片段：**被引号包住**（`"…"` / `'…'`）或**以盘符开头**（`X:\` / `X:/`）→
     **整体**算一个条目（引号剥掉）；否则才按**空格**切；
   - **相对**路径里带空格 → **必须用引号包住**。理由：带空格的相对路径与不带空格的
     相对路径在切分前无法区分，没有可靠的自动判据 —— 与其猜错（猜错就静默截断），
     不如要求显式加引号；
   - 看起来像路径却解析不出来的 token → 计入 `rejected`（派工闸门拒派）；
     自然语言片段 → 丢弃。两者都不得**静默收窄**白名单。

   理由：Windows 上绝对路径带空格是常态（**本仓库自己的路径就带空格**），
   按空格切会把一条路径切成两段 —— 前半截被当成条目收进白名单、后半段被丢掉，
   于是这条白名单**静默不生效**（目标被判成越界）。这是一次「判定落空」而不是报错。

### 边界自检三连（父会话派工前必查）

1. **读得到吗**：把成员要读的每一个路径列出来，逐个确认它落在某个 scope 条目的所在目录树内。漏一个 = 成员必然撞墙。
2. **说得准吗**：brief 里每一句关于边界的描述（"整个目录可读"、"只有 X 能写"），必须与 S3 的通道语义一致。半真话比不说更危险。
3. **同源吗**：条目模板、编号规则、状态口径，必须直接引用 S1，不得在 brief 里复述。

## S3 通道语义（同一套 scope，不同工具的判定方式不同）

| 通道 | 判定对象 | 判定方式 |
|---|---|---|
| read / list | 目标路径 | 读判定（S2.1） |
| glob / grep | **有效检索根**（显式 `path` 优先，缺省用当前工作区） | 读判定。**判定对象不是 pattern 本身** |
| write / edit | 目标路径 | 写判定（S2.2） |
| bash | 命令里的路径 token | **按命令意图分流**：只读命令按读判定，其余按写判定 |
| 复合工具（`run_code` 等） | **不做作用域判定** | 只判危险操作（S5.4）；作用域交回内层调用 |

### bash 路径 token 的识别规则

只有满足下列之一才算「路径 token」：

- 含路径分隔符（`/` 或 `\`）；
- 以 `.` 开头的点目录（`.git`）；
- 含已知文件扩展名（`.mjs` `.js` `.ts` `.json` `.md` `.txt` `.py` 等）。

**不得**把带点的标识符当路径（`console.log`、`JSON.stringify`、`m.extractScope`、`v0.4.0` 都不是路径）。

### bash 的只读命令白名单

`cat` `head` `tail` `less` `more` `ls` `dir` `grep` `rg` `find` `type` `stat` `wc` `which` `node --version` `git status` `git log` `git diff` `git show`

命中白名单的命令按**读**判定（路径只要落在读放行范围内即放行）；其余命令按**写**判定。

### 复合工具（run_code）的判定语义

复合工具的载荷是**自由文本代码**，不是路径实参列表。因此：

1. 复合层**只做危险操作判定**（危险工具名 / 危险参数，见 S5.2、S5.4）；
2. 复合层**不对代码文本做路径扫描**：注释、字符串常量、引号里的命令串
   都不得参与作用域判定；
3. 复合层**不套用「取不到目标就 deny」**：那条规则防的是写通道失守，
   对复合工具不适用 —— 不含任何路径 token 的纯计算代码**必须放行**；
4. **作用域判定交回内层调用**：内层 `write` / `edit` / `bash` 各自触发 PreToolUse，
   判定对象是真实实参，比扫描整段代码文本精确。

> 反例（v0.5.0 修掉的误伤）：代码里只要出现一个 scope 外的路径字样
> （哪怕只是注释或字符串常量）、出现 `//` 注释、引号命令里带一个斜杠，
> 或代码不含任何路径 token，整次 `run_code` 就被拒 ——
> 以 `run_code` 为主力工具的 worker 会大面积撞墙。

### bash 通道的危险操作形态

bash 命令是**自由文本**，不能像工具名那样等值匹配 —— 见到 `delete` 就拦会大面积误伤
（`rm build/out.txt` 这类普通路径操作很常见）。要拦的是**命令形态**：

- 「CLI + 子命令 + 动作」的组合：`mavis agent delete <name>`、`mavis agent update <name>`；
- 对外发布类命令：`git push`、`npm publish`、`docker push`、`website_deploy`、`miniapp publish` 等。

判定落在**内层调用**这一层（bash 自己就是内层调用），所以 bash 通道必须自己认得出这些形态，
不能指望复合层兜底（见下节）。

### 容器调用的派发事实（v0.5.1 复测更正）

**容器调用的 PreToolUse 派发不是平台恒定行为 —— 它随会话而变。**

三组活体证据（调用形状完全相同：外层 `run_code` 装一段纯计算 + 一个危险字符串常量）：

| 时间 | 会话 | 结果 |
|---|---|---|
| 2026-11-10 10:22 | `mvs_b0accaba…`（guard 装了日志探针） | **未派发**：同会话容器内的 `read` 有日志条目，外层 `run_code` 一条都没有 |
| 2026-11-10 14:29 | `mvs_20e67557…` | **派发**：外层 `run_code` 被复合层当场 DENY |
| 2026-11-10 15:10 | `mvs_355c229f…`（金丝雀复测） | **派发**：外层 `run_code` 里的危险文本被 DENY，纯计算对照组放行 |

已逐棵核对的事实：`run_code` 是 2026-11-10 08:19 才进入 PreToolUse matcher 的；
11/9 物化的 60 棵 hook 缓存树**全部**没有它，11/10 08:11 之后物化的树全部有。
**推断（未逐棵验证）**：matcher 取自会话绑定的缓存树，所以老会话不派发、新会话派发。

因此：

1. 复合层的危险操作判定**会生效，但不保证每次都生效** —— 它是**纵深防御的加成**，不能当唯一防线；
2. 账号级与对外不可逆动作的拦截，**必须在各内层通道各自做到位**（尤其 bash 通道）——
   v0.5.0 把判定落到内层是必须的，不是多余的；
3. **不要用「合成载荷驱动 guard 脚本」推断平台是否派发** —— 合成载荷只验证**判定逻辑**，
   不验证**触发链路**，两者必须分开验；
4. **也不要用「一次阴性观察」推断平台行为** —— 10:22 那次的阴性观察本身是可信的
   （日志探针在同会话对 `read` 正常工作），但它只对那一个会话成立。
   判定派发行为必须带**金丝雀对照 + 时间戳 + 会话标识**三件套。

## S4 transcript 中的 brief 解析

`readBriefFromTranscript` 必须同时兼容两种 transcript 变体：

| 变体 | 首条 user 消息的形状 |
|---|---|
| `compatible` | `type:"user"` + `message.content[].type:"text"` |
| `codex` | `type:"response_item"` + `payload.role:"user"` + `payload.content[].type:"input_text"` |

定位 brief 的规则：

- **按语义定位，不按固定行号**：从文件开头逐行扫描，扫到第一条含 `SCOPE:` 的 user 消息为止。
- 禁止用 `slice(0, 8)` 这类固定窗口——会话前置消息条数不固定。

**解析失败必须 deny，不能放行。** 解析不到边界 = 边界不存在，此时放行等于没有管控。
deny 理由要写清：解析失败的具体原因（变体不认识 / 没找到 SCOPE 行 / 文件读不到）。

## S4.5 会话复用（同一专项的连续工作，不新开子会话）

**规则 → 给同一个专项成员派连续的工作时，优先复用它已存在的子会话，不要新开一个。**

### 为什么（这是上下文成本问题，不是风格问题）

每新开一个子会话，那位成员都要**重新读一遍它需要读的东西**（方法论文件、契约、台账、
相关脚本、既有报告），才能进入状态。这些重复读取：

- **浪费上下文预算**：成员的实际工作被「重新读仓库」挤掉；
- **浪费父会话的注意力**：父会话要重新写一遍「这个人知道什么、不知道什么」的铺垫；
- **窗口越堆越多**：几十个「边」里真正在干活的只有几条，其余全是重复的上下文副本。

同一批成员被反复重开，是因为「派工 = 新建任务」被当成了默认动作。
但**派工单的内容**（要修哪条缺陷、依据是什么、验收怎么判）才是贵的部分，
而那部分写在 brief 里 —— brief 可以**追加**到已有会话，不需要重开。

### 怎么做

1. **先查有没有可复用的会话**：同一专项成员此前派过工、且**上下文中已经加载了**本单要改的那些文件
   ⇒ 追加（`task_append`）而不是新派。
2. **追加的内容必须自包含**：新 brief 里**不要**写「如前所述」「继续刚才那个」——
   追加会并入它下一轮，措辞会被机制自己判定，独立可读才稳。
3. **边界会继承**：子会话的边界来自**它首次工具调用时建立的 binding**（brief 原文 ∪ 已批准扩权）。
   追加一轮**不会**自动扩大边界。要加路径，走管理员扩权（`scope-amend.mjs --dispatch ... --add ...`），
   或确认新任务在既有边界内。
4. **该新开还是该复用**：
   - **复用**：同一专项、同一批文件、改的是同一族问题、且该成员已经读过这些文件。
   - **新开**：换了专项归属（不同成员）、换了边界（SCOPE 差很多）、或该成员已经**太久没动**
     （上下文太旧、之前的中间状态已过期）。

### 归档 vs 复用：实测边界

**归档的会话不能再被复用**（实测：对已归档的子会话 `task_append` 返回 `TASK_CHILD_ARCHIVED`）。
⇒ 这两个动作**互斥**，归档前要先想清楚这个会话**将来还要不要复用**。

| 会话状态 | 窗口列表 | 还能追加复用 |
|---|---|---|
| 刚做完、产物已落盘、**短期内可能还要续** | 留在列表里 | ✅ 能（上下文完整保留） |
| 做完很久、产物已落盘、**不会再续** | **归档**（列表收敛） | ❌ 不能 |

**建议的做法**：

- 同一专项的**当前活跃会话**（正在跑、或下一单大概率接着用）⇒ 保留，不归档；
- 已经交付、且**该专项的下一步不在这些文件上**的旧会话 ⇒ 归档，把窗口列表收回来；
- 归档**不会**丢产物（代码与报告都在工作树里），只影响「能不能继续追加这一轮对话」。

**别为了「列表好看」把还能复用的会话归档掉** —— 复用省的是上下文，归档省的是列表长度，两者不能兼得时，
优先省上下文。

### ⚠️ 追加时 SCOPE 行的写法（实测踩过的坑）

**闸门取的是子会话 transcript 里的 SCOPE 行。** 追加指令会**并入该子会话的下一轮**，
于是追加内容里的 SCOPE 行会**参与边界解析**。若那一行写得不合规
（顿号分隔、带反引号、写在句子里），解析器会得到 **0 条条目** ⇒
「边界视为不存在」⇒ 护栏**整段拒绝**该子会话的所有工具调用
（连不带任何路径的调用也被拒）。

**实测**：一次「接手补报告」的追加指令里，SCOPE 写成
「本单 SCOPE：\`a\`、\`b\`、…」的顿号+反引号形式 ⇒
接手方**整轮无法调用任何工具**（读、写、bash 全被拒），
最后报告写不了盘、只能把正文以文字交回父会话。

**规则**：

- 追加内容里**要写 SCOPE 行，就写成协议格式**：
  `SCOPE: path/a.ts, path/b.ts`（逗号分隔、无反引号、行首 `SCOPE:`）；
- 追加内容里**根本不用提 SCOPE** ⇒ 就**别提** —— 不要写「本单 SCOPE：…」这种半吊子形式；
  原有边界会继承，不需要重复声明；
- 追加内容里提到的**路径**仍会被当作边界声明的一部分被解析 ——
  写路径时确认它落在原有边界内，否则会被当成越界。

**失败方向是安全的**（拒绝而非放行），但代价是整个会话瘫掉 —— 所以这条要在追加前就避开。

### 怎么知道有没有在乱开

复用率是一个**该盯的指标**：同一专项成员的「子会话数」应当远小于「派工单数」。
如果一个专项成员开了十几个会话却只干了两三件事，那就是在重复启动，不是在协作。

## S4.6 派工粒度：一个项目一个窗口（项目级覆盖检查）

**规则 → 派工粒度是「一个大项目」，不是大项目的每个子步骤。一个项目由一个窗口从头负责到底；项目内部的步骤由那个窗口自己完成，不得各自另开窗口。**

### 为什么（这是上下文成本问题，和 S4.5 是同一件事的两端）

S4.5 管的是「同一专项的**连续工作**别重开」，但它漏了更上面的一层：
**一个大项目被拆成十几个子步骤、十几个子步骤各开一个窗口** —— 那是同一种浪费的更严重形态。

一个项目下面的步骤（活体探针、夹具、回放、取证、判读、记录、台账回写）**共享同一批事实**：
后一步的结论常常直接推翻前一步的假设。拆到不同窗口，每个窗口都要重新读一遍方法论、契约、
台账、相关脚本，**而且看不到上一步已经查出来的事实** ⇒ 不只是慢，还会重复踩同一个坑。

### 派工前必答的两个问题

1. **这一单是那个大项目的「新的一块」，还是它内部的一个步骤？**
   是步骤 ⇒ 并入那个窗口（追加），**不开窗**。
   「新的一块」的判据：独立的交付物 + 独立的验收标准 + 可以独立交付。
2. **这个大项目已经有窗口了吗？那个窗口的边界覆盖得住这一步吗？**
   覆盖得住 ⇒ 追加（边界不覆盖时先扩权，见 S4.5 第 3 条；覆盖不到才新开）。

### 大项目的定义

**同一专项的同一族缺陷 / 同一批交付物 / 同一个验证目标** = 一个大项目。
例：「把 D-86 闸门的活体拦截证据取到」是一个项目 ⇒ 探针怎么设计、夹具怎么造、回放怎么跑、
判读脚本怎么写、台账怎么回写，都是**它内部的步骤**，不是五个项目。

### 复用判据的第三个维度（补 S4.5）

S4.5 的复用判据是「**该成员是否已经读过本单要改的那些文件**」⇒ 只有**专项**与**文件**两个维度。
本条补第三维：**项目覆盖** —— 「这个大项目是不是已经有窗口在负责」。
三个维度（专项 / 文件 / 项目）**都答「否」才新开**；任一为「是」都先考虑追加。

### 无专项 owner 的步骤不得自成一窗

探针 / 取证 / 夹具 / 回放 / 记录这类**没有专项归属**的子步骤，被当成独立专项各自派工
= 系统性地制造窗口爆炸（它们在派工台账里彼此看不见，也各自重读一遍上下文）。
⇒ 它们**必须**并入项目主窗口，或并入该项目的验收窗口。

### 诚实边界：这道规则在程序层**拦不住**

派工台的组队闸门**只算写冲突**（scope.md：「只算**写冲突**（条目相同，或一方是另一方的目录前缀）。读范围天然重叠，不算冲突」）
⇒ **只读类派工（探针、审阅、取证）永远不触发冲突闸门**。
而插件的复用提示（`dispatch.mjs` 的「会话复用提示」）又是按「该成员已有会话的上下文**覆盖本单 SCOPE**」来算的
⇒ 读类派工的 SCOPE 天然覆盖很多会话 ⇒ 提示会变成「有 N 个会话覆盖」，**却不指出该追加哪一个**。
⇒ **「防重复开窗」这件事在程序层没有强制力**，本条是**协议层规则**，靠派工方（Router）遵守。
程序层的解法（给派工台账加「项目键」、对同一项目的重复派工做指向性提示）是另一条待办，
在它落地之前，这条规则只能靠人守。

## S5 工具名分流与危险操作

1. **兜底表**：不在已登记工具名单里的**文件类**工具名，一律按**写**判定，不得默认放行。
2. **危险操作双判定**：账号级与对外不可逆操作，除了按工具名匹配，还要看**参数**：
   - `mavis` 工具的 `command` 参数为 `agent delete` / `agent update` → 拦；
   - `miniapp` 的 `action` 为 `publish` → 拦。
3. 危险操作清单：删除/修改成员、部署上线、发布 Mini App、GitHub 推送等对外可见动作。
   **同一份清单必须在 bash 通道同样生效** —— `mavis agent delete <name>` 这种 CLI 形态
   写在命令文本里，工具名匹配不到（见 S3「bash 通道的危险操作形态」）。
4. **命令形态判定，不是字样匹配**：bash 通道按**命令位置**上的「CLI + 子命令 + 动作」组合判定
   （如 `mavis agent delete|update`）；**按字样匹配（见到 delete/remove 即拦）不被认可** ——
   `rm build/out.txt`、`grep "mavis agent delete"` 这类普通操作会被大面积误伤。
   命令替换（`$(...)` / 反引号）载荷、`sh -c` / `eval` 载荷按其**内层命令**同判；
   只读分流仅对**无命令替换**的命令生效（`cat $(mavis agent delete x)` 是实打实的洞）。
   `website_deploy` / `miniapp publish` 在 bash 里**仅按命令位置**拦截
   （`cat website_deploy.md`、`grep "miniapp publish"` 不拦）—— 这两个词在 bash 里更像文件名或文本。
5. **包装器开关必须按包装器分别定义**：带值开关 / 布尔开关 / 前置位置参数三者分列。
   **禁止跨包装器的全局开关表** —— 布尔开关被当成带值开关时，命令词会被吞掉，
   判定落空即放行（`sudo -n mavis agent delete` 曾因此整体逃逸）。
   查表时**不得一律小写化**：`sudo -H`（set-home，布尔）与 `sudo -h`（host，带值）是两个不同的开关。
   认不出的开关按**宁可多判不可漏判**处理。
6. **包装器集合须穷举类别，载荷分两式**：POSIX `-c` 取**一个**参数，
   PowerShell `-Command` 与 cmd `/c` 取**余下全部**；载荷**整体再判一次**。
   `timeout` 的时长是**位置参数**不是开关。
7. **账号级 CLI 的子命令必须是第一个子命令**：`mavis agent delete|update` 算危险，
   `mavis list agent delete` **不算** —— 位置不对就不构成危险形态（过度拦同样是缺陷）。
8. **无法解析的载荷必须拒绝，不得放行**：`<(…)` 进程替换、base64 编码载荷
   （如 `powershell -EncodedCommand <base64>`）与 `$()` / 反引号同属**真执行**；
   解不出内容时按危险处理。
9. **命令位置不得用闭集包装器名单实现**（这是 D-25b/D-25d 的共同根因）：
   段首命中**数据命令清单** → 段内其余 token 与引号内内容皆为**数据**，不参与命令位置判定；
   否则段内**每个 token 都是命令候选**。这样 `exec` / `taskset` / `watch` / `at` / `parallel` /
   `script` / `chroot` / `strace` 以及**任何将来出现的包装器**都自动被覆盖 ——
   因为它们让段首不是数据命令，后续 token 自然进入候选。
   数据命令清单要尽量完整；**`tar` / `unzip` / `zip` / `gzip` 不得收进清单**
   （它们的 `--to-command` 会真执行，收进来等于开盲区）。
10. **载荷取参按 shell 语义**：`sh` / `bash` 的 `-c` 只取**一个**参数作命令串，
    余下是 `$0` / `$1` 位置参数（**不是**命令的一部分）；`powershell` / `cmd` 取**余下整段**；
    base64 载荷解不出即拒绝；`command -v` / `command -V` 是**查询**语义，该段**无命令位置**。
11. **启动器**（`npx` / `bunx`、`npm` / `pnpm exec|dlx`、`yarn dlx`）之后的**首个程序参数**
    按命令位置判定。
4. **复合工具只做危险操作判定**：`run_code` 等复合工具在复合层**不得**做作用域判定
   （见 S3）。命中危险工具名或危险参数时一律拦（`mavis` 的 `agent delete`、
   `miniapp` 的 `publish`、`website_deploy`）；复合层不做路径扫描，
   作用域判定交回内层调用各自触发 PreToolUse。

## S6 派工台账口径

1. **去重键不得只依赖 `turn_id`**：`turn_id` 缺失或为空时，用 `dispatch_id` 兜底，
   且**绝不允许**抹掉其它 agent 或其它 turn 的记录。台账里存在同名键时，只允许覆盖**完全相同**的那一条。
2. **名额回收要有三条路**：
   - 正常结束（SubagentStop）→ 立即回收；
   - **超时兜底**：超过 TTL 的 active 记录判死；
   - **读时自愈**：读取在飞名单时，把已超龄的 active 记录直接判死并落盘。
   只有第 1 条 = 派工被取消/中断/子会话异常退出时名额永久泄漏。
   **诚实边界：判死的是台账记录，不是子代理。** TTL 到期只把这条派工从「在飞」里
   摘掉 —— `lib.mjs` 的 `reapExpiredDispatches()` 只翻转台账状态，
   **不与子会话做任何交互**。**正在跑的子代理不会被 TTL 停掉**，仍会继续消耗资源；
   止损要由父会话显式停（停后台任务用 `task_stop`，停子会话当前轮次用
   `mavis_session_interrupt`）。
3. **台账里不许有只写不读的字段**：每个写入的字段要么被某处判定读取，要么删掉。
4. 派工状态 `state` 必须与真实情况一致；TTL 过后不允许继续停在 `active`。
5. **取消场景必须由发起方显式释放**：派工被父会话取消 / 中断、或子会话异常退出时，
   **不会触发 SubagentStop**；TTL 兜底要等满 2 小时，期间这条记录一直占着并发名额
   （`MAX_ACTIVE_DISPATCHES` = 6）。台账条目里**没有子会话 id**，
   所以「自动探测子会话是否还活着」不可行 —— 能自动拿到的只有终止事件，
   而取消场景下没有终止事件。**结论：取消场景由发起方显式释放**，
   入口是 `scripts/release-slot.mjs`：
   `node scripts/release-slot.mjs --dispatch dsp_xxx --reason parent_cancelled`
   （或 `--parent mvs_xxx` 释放该父会话下全部在飞派工）。
   **入口必须用开关形式**：PowerShell 的原生参数解析会吃掉 JSON 里的双引号，
   `node x.mjs '{"id":"a"}'` 在 PS 里实际收到 `{"id:a}`（非法 JSON）——
   开关不含引号，跨 shell 一致。JSON 形式仍兼容，但不得作为文档里的推荐写法。
   释放只把 `active` 翻成 `aborted`，`done` / `aborted` 的记录一个字节都不动；
   目标不存在或台账读不出来时**必须报错**，不许静默成功 ——
   否则调用方以为名额放掉了，实际还在占着。
   **释放入口只对发起方开放**：worker 的 SCOPE 不含插件脚本目录，
   通过 bash 通道调它会被 scope 判定拦下（回归里有这条断言）。

## S7 记录闸门（履历 / 错题本 / 名录）

1. **`verified_by` 必须真实**：不能只校验「不等于 agent 名」。要求它在派工台账里存在一条
   `agent == verified_by` 且 `state == 'done'` 的记录——即确实有一个叫这个名字的验收方跑过验收。
2. **归因公平正则要能识别多种语序**：`brief 给错`、`给错的 brief`、`派工给错`、`派工 brief 有误`、
   `Router 的锅` —— 任何指向编排层的归因都不得写进成员错题本。
3. **记录可见性不得按名录顺序截断**：摘要取样应按「有记录的成员」排序后取，
   或对所有成员公平取，不得因为排在名录后面就结构性不可见。
4. **索引口径统一**：同一个文件里，段首定位不得混用相对偏移与绝对索引。
5. **并发写的锁参数是算出来的，不是拍脑袋**：等待超时必须**容得下编排层最大并发数轮持有者** ——
   `LOCK_WAIT_TIMEOUT_MS >= MAX_ACTIVE_DISPATCHES × RENAME_RETRY_WINDOW_MS`
   （同时最多 6 个派工在飞 × 持有者最坏临界区 8.8s = 52800ms）；
   偷锁阈值必须**大于**等待超时（防「偷走还在用的锁」）。
   这两条是**必要条件与充分条件之别**：前者区分「排队方被误判失败」，后者只防偷锁 ——
   断言要能区分改前改后，就得用前者。改任一常量，断言会顶出来（见 S14 与 `docs/audit/fix-f02.md`）。

## S8 收尾契约校验（watchdog）

SubagentStop 时，除了检查「有没有声称完成」，还要检查**产出是否满足 S1**：

- 编号前缀一致、序号递增不跳号；
- 每条 7 个字段齐备且独立成行；
- 「条目统计」行与实际条数/状态计数自洽。

任一不满足 → **block** 并明确指出缺哪一项（缺哪个字段 / 哪个编号跳号 / 统计行对不上），
让 worker 一次性补齐，而不是让它反复小修小补。

### S8.1 「声称产出」的判定口径

「有没有声称完成」这一关，判定**不是**「文本里出现了产出动词就算」——
那是 D-72 的老实现，它把**否定式陈述**（「X 没有创建」）与**引用的护栏拒绝原文**
一并当成产出声明，于是连续 block 诚实的交付报告，实质在逼成员去创建那个文件。
现在的判定分四层，每层独立成规则（实现见 `plugin/scripts/watchdog.mjs`）：

| 层 | 规则 | 落到哪 |
|---|---|---|
| 归属 | 路径归属到**它所在的子句**，不是它所在的行 | 行里有别的动词 ⇒ 不再把无关路径认领成产出 |
| 断言性 | **否定式判定**独立一条（不靠往动词表里加词）；另有**非断言语境**判定（疑问从句 / 引述句） | 「没有创建 / 未创建 / 不该创建 / 是否…被创建」都不是产出声明 |
| 路径形态 | **家目录写法先展开**（`~` / `$HOME` / `%USERPROFILE%`）；**通配符按「模式」整体识别**，不截成碎片 | 真实存在的家目录文件不再被判「不存在」；模式不当成文件去校验 |
| 存在性 | 路径存在性校验**只对肯定式产出**生效 | 肯定式声明里的文件不存在，**仍然必须被拦** |

三条硬规矩：

1. **否定式要单独一条判定，不能靠扩充动词表** —— 加词只能堵住已知的说法，下一种说法又会漏。
2. **不许因此打开新的放行口子** —— 肯定式产出陈述里提到、却并不存在的文件，**仍必须被拦**。
3. **「判存在性前必须展开家目录」** —— 不展开就会把真实存在的文件判成「不存在」，
   同样是误拦。**展开已下沉到 `lib.mjs` 的 `absolutizePath()` 内部**（v0.5.7，D-80 收口）：
   展开发生在「解析成绝对路径」这一步、**早于**「拼工作区根」，调用方不必各自记得展开。
   `expandHomePath(p, home)` 的签名与语义未变；取不到家目录时退回「不展开」，不造路径。

### S8.2 block 消息必须带规则编号

每条 block 消息带一个**稳定的规则编号**：
`R-CLAIM-PATH-MISSING` / `R-NO-EVIDENCE` / `R-EMPTY-DELIVERY` / `R-ENTRY-FORMAT`。

理由：验收断言要能**指认命中的是哪条规则**。只判「被拦」的话，
命中**别的**分支也会通过 —— 那是假绿（同族教训 D-70）。
文案会变，编号不会；断言按编号判定，不要按文案关键词判定。

## S11 触发语义（何时注入编排指令）

UserPromptSubmit 的粗筛决定「这一轮要不要展开编排流程」。判据分三档，语料与判据见
`docs/audit/d27-acceptance.md`：

| 档 | 含义 | 期望 |
|---|---|---|
| A 编排意图 | 用户在要求拆 / 分 / 并行 / 派谁 / 验收 | **命中** |
| B 单点动作 | 改 typo / 查文档 / 加注释 / 修 bug | **不命中** |
| C 伪信号 | 出现「同时 / 多个 / 分别 / 各自 / 并行」但不是在要求编排 | **不命中** |

判定规则的唯一出处是 lib.mjs 的 judgeTriggerIntent()：

1. **意图词命中即命中** —— 覆盖书面说法（派工 / 组队 / 分工 / 验收 / 复盘）与口语动词短语
   （拆一下 / 拆解 / 分头做 / 谁负责 / 派谁 / 各做各的 / 放到后台 / 复审 / 评审），
   外加机制自指（主动触发 / 触发机制）与多项请求（还有其他的 / 另外 / 顺便）。
2. **信号词必须与动作词邻近同现**（窗口 12 字符）—— 「并行 / 同时 / 多个 / 分别 / 各自 / 一起」
   单独出现不算意图：「同时打开这两个文件」「批量导入」是单点动作，不是编排。
   「并行」还要求带动作后缀（并行做 / 并行跑），否则「并行度调高一点」会被误触发。
3. **SCOPE 提示命中即命中** —— 用户文本里出现 SCOPE: 段。
4. **不得用长度门槛代替判定** —— 中文口语指令通常只有 3~12 字，
   prompt.length > 40 这类硬门槛会把整类口语请求挡在门外（v0.5.0 的漏判 83% 就是这么来的）。

**未命中时的兜底**：仅当「roster 存在 + 有专项成员 + 该成员有实战记录」时，注入**一行**极短提示；
否则**必须 0 字节输出**（单点小改零噪声）。兜底只提示「可以查 roster」，**不改写 owns 归属**。

**载荷坏了必须留痕**：UserPromptSubmit 载荷解析失败、或 prompt 字段不在，
都必须写一条痕迹到 **PLUGIN_DATA 目录下的 `gate-trace.jsonl`**
（运行时 PLUGIN_DATA 本身就是本插件的专属目录 `.../plugin-data/hooks/super-agent-router`，
所以痕迹就在它**下一层**；不要再多拼一层 `hooks/super-agent-router` —— 那是 D-29 修掉的坑），
**不得**静默退出 —— 静默会让「永远不命中」和「判定为不该命中」在日志里长得一样。
## S12 主 agent 定位（管理层不做苦力）

SessionStart 注入必须写明**主 agent 的定位**：它是管理层，不是执行层。判据：

| 情形 | 谁做 |
|---|---|
| 意图理解、拆解、组队、整合、给用户结论 | **主 agent 自己**（不委派） |
| 已有专项成员 `owns` 这件事 | **派工**，主 agent 不亲自上手 |
| 无专精成员但有方法论要求 | 先现场配置成员（方法论文件 → 建成员 → 登记 roster）再派工 |
| 单点小改（typo / 查 API / 加注释 / 改配置值） | 主 agent 直做 |
| 独立验收 | 派 `verifier`，worker 自述不算 |

**注入文本里不得出现与「管理层定位」矛盾的表述**：「不预置成员」与「不自己做专项活」是两件事，
必须分开写 —— 只写前者会被读成「有成员也别派、自己干」。

**成员记忆共享但隔离**：教训、履历、方法论各归各的；派工只注入目标成员自己的历史。
发现串味（别人的教训进了别人的 brief、两个成员抢同一个 `owns`、有人改了别人的记录）
按缺陷处理并改归属映射，不得默认放着不管。

## S13 权限自动审核、扩权与权限等级

### S13.1 三层：发现 → 记账 → 批准

越界管控**自动**做前两件，**不自动**做第三件：

| 环节 | 谁做 | 落地 |
|---|---|---|
| 发现（谁被拦了、想访问什么） | **自动** | guard 的 `denyOutOfScope()` |
| 记账（写进台账待审清单） | **自动** | 台账 `scope_requests[]`，同目标 `hits` 累加去重 |
| 批准（把目标并入该派工的 scope） | **父会话** | `scope-amend.mjs --grant <id>` |

**为什么没有「自动批准」**：让被约束者自己决定边界 = 授权模型被拆掉。
自动的是发现与记账；批准权始终在父会话（管理员）手里。

### S13.2 批准的四条硬规矩

1. **读请求只授读**：批准一条读请求只加 `ro:` 条目，写仍被拦 —— 批准读 ≠ 批准写。
2. **必须落在仍在飞的派工上**：派工已结束（done/aborted）则拒绝扩权 —— 事后再补权限没有意义，重新派工即可。
   **两条扩权路径同口径**：`--grant <id>`（批准一条待审请求）与 `--dispatch <id> --add <path>`
   （直接加条目）都必须查派工状态 —— 只查一条路径，口径就会分裂。
3. **批准必须留痕**：记录批准人与时间，扩权要可审计。
4. **批准人必须是真实的父会话 id**：`--grant` / `--dispatch --add` 的 `--approver`
   要等于该派工的 `parent_session_id`；`--tier` 的 `--approver` 必须是派工台账里
   **存在过的父会话 id**（待审清单 `--list` 会直接给出这个值，父会话照抄即可）。
   这是**纵深防御**，不是主防线 —— worker 的派工原文里就带着 `PARENT SESSION:`，
   所以它挡不住蓄意自提权。文档与代码都不得把它写成「绝对禁止」。

批准后**同时**更新三处：派工记录的 `scope`、子会话绑定的 `scope`、以及 `scope_amended`。
第三处是关键：worker 首次调用工具时边界来自 transcript 里的派工原文，不读台账 ——
只改前两处，批准对「还没发起过工具调用」的 worker 无效。

### S13.3 权限等级（tier）

每个成员都有一条**权限等级**，声明在项目级 `.superagent/roster.json`：

| 等级 | 含义 |
|---|---|
| `scoped`（默认） | 逐路径白名单；白名单外一律拦，越界自动记账 |
| `full` | 项目工作区内自由读写，不必逐路径枚举 |

**每个成员都是平等的** —— `full` 不是某些成员的特权，任何成员都可以被管理员提权；
但**提权这个动作在管理员手里**：
`scope-amend.mjs --tier full --agent <名> --approver <父会话 id>`，
写进 roster.json 并留痕 `.superagent/changes.log`。

**诚实边界（不得写成「worker 无权改自己的等级」——那句话按现状不成立）**：
机制做三件事：

1. **权威面脚本列为父会话专属（主防线）**：提权 / 批准扩权 / 写履历 / 写错题本 / 登记成员
   这几个脚本只允许父会话执行 —— 子代理上下文里执行它们，护栏直接拒绝
   （即使它的 SCOPE 覆盖了插件目录）。

   - **归属判据 = 插件包身份**（F-01）：一个文件属于本插件包，当且仅当它所在目录树里有
     `.minimax-plugin/plugin.json`，且该包的 `name` 与本插件一致。
     仓库 `plugin/`、安装目录 `~/.minimax/plugins/super-agent-router`、
     运行时缓存树 `sha256-tree-v1-*` 都满足这一条 ⇒ **每一份副本都被拦**。
   - **不得**用「脚本名裸匹配」（别的项目里也有 `roster.mjs`），
     **不得**用「路径里含 scripts/」这类模糊特征，
     **不得**锚在「运行中 guard 自己所在的那一份」——
     那样只覆盖一份副本，仓库副本上整条提权链可端到端兑现。
   - **哪一层管什么**：这条管的是 **bash 通道** —— 命令文本里出现
     「本插件包里的权威面脚本」就拒（执行与读取都算：读一份再改名执行是同一条链）。
     **write / edit / read 工具不受这条限制**（机制维护类成员要改的就是它们），
     改写仍受 scope 白名单与 `.superagent/` 私有目录规则约束。
     父会话不受影响 —— 父会话载荷里没有 `agent_type`。
2. **admin CLI 校验批准人（纵深防御）**：批准人必须是真实的父会话 id（见 S13.2 第 4 条）。
3. **留痕**：提权与批准都进 `.superagent/changes.log` 与派工台账。

但 **hook 是护栏不是沙箱**（S13.5）：worker 若能执行一段落盘的脚本，脚本内部的写入
不受判定约束。真正的防线是运行时权限 + 审计留痕 + 验收时复核
（`references/review.md` 的扩权复核清单）。

**等级按派工时快照**：派工那一刻把成员的 tier 写进派工记录，子会话绑定继承这份快照 ——
会话中途发生的等级变更对**已在飞**的会话不生效（下一个派工才按新等级生效）。

`full` 仍然**不等于**无限权限，下列四条照旧生效：

1. **`.superagent/` 编排层私有状态目录除外** —— 那是成员互相篡位与自提权的战场。
   成员自己的方法论与错题本走 guard 的 `exactPaths`（按精确文件放行），与 tier 无关。
2. **工作区之外的路径仍拦**，并仍自动记账待审（父会话可逐条批准）。
3. **账号级 / 对外不可逆动作照旧硬拦**（删成员、改成员、部署、发布）—— 与 tier 无关。

**第四条边界（容易漏，必须写明）：写冲突检测仍按**声明的** SCOPE 比对。**
两名 full 等级成员若声明的 SCOPE 不重叠，组队闸门不会拦它们 ——
但两人实际都能改动项目内任意文件，可能撞车。
所以 full 成员的 SCOPE **仍要写清楚它实际要动的范围** —— 那是给人看的意图声明，
也是冲突检测的唯一依据。full 放开的是「白名单外的项目内路径」，不是「冲突检测」。

### S13.4 派工闸门 1c：SCOPE 里的 .superagent/ 有三种形态，三种判法

读模式按目录树放宽，**文件条目的读范围是它所在的整个目录** ——
所以 `.superagent/` 下的条目必须逐形态判，不能一刀切也不能全放：

| 形态 | 判定 | 理由 |
|---|---|---|
| 目录条目（`ro: .superagent/`） | **拒派** | 树就是整棵 `.superagent/` ⇒ 能读到兄弟成员的错题本全文与方法论全文 |
| 可写文件条目（`.superagent/roster.json`） | **拒派** | 能改 `tier` 字段 ⇒ **自己给自己提权** |
| 只读文件条目（`ro: .superagent/roster.json`） | **允许，但精确生效** | 不展开目录树 ⇒ 只读得到那一个文件 |
| `.superagent/lessons/`、`.superagent/methods/` 下任何条目 | **拒派**（闸门 1b） | 那是每个成员自己的记忆，不是共享资产 |

「精确生效」是代码保证，不是约定：`inScope` 的读模式遇到 `.superagent/` 条目直接跳过树根展开，
所以「读一个 roster.json」读不到兄弟成员的错题本。

**第二道防线**：worker 的边界也可以**直接从 transcript 的 brief** 建起来（不经 dispatch），
那条路绕过闸门 1c —— 所以 guard 在建边界时自己再封一次
（brief 里含 `.superagent/lessons/` 或 `.superagent/methods/` ⇒ 直接拒绝建立边界）。

成员自己的方法论与错题本由 guard 按精确文件（`exactPaths`）单独放行，与 SCOPE 无关；
需要别人的历史，走「Router 转写进 brief」这条契约通道。

### S13.5 诚实边界

hook 是**护栏不是沙箱**：worker 若能执行一段落盘的脚本，脚本内部的 fs 写入不受本判定约束。
tier 的真正保证是「提权由管理员执行 + roster.json 可审计 + changes.log 留痕 + 运行时权限」，
不是「脚本层绝对拦得住」。

把权威面脚本列为父会话专属（S13.3 第 1 条）能**降低误用**，但它同样不是沙箱。
**哪一部分现在有代码保证、哪一部分仍然没有，写清楚**：

- **有代码保证**：凡是通过**本插件包里的官方脚本**（任何一份副本 —— 仓库 / 安装目录 /
  运行时缓存树，判据见 S13.3 第 1 条的插件包身份）提权或批准扩权，worker 一律被拦。
  这一条由 `tests/guard-test.mjs` 的 F-01 断言钉住。
- **仍然没有保证**：把脚本**复制一份、改个名字**再执行（复制品不在插件包目录树下，
  归属判不出来），或用**内联代码**直接写文件（复合层只判危险操作，作用域交回内层调用），
  都不在判定范围内。
- **不是防线的那一条**：「批准人必须是真实的父会话 id」是**纵深防御**，
  不是主防线 —— worker 的派工原文里就带着 `PARENT SESSION:`，它挡不住蓄意自提权。
  主防线是 S13.3 第 1 条那条「子代理不得执行权威面脚本」。

这一层的兜底是运行时权限 + 审计留痕 + 验收时复核。

## S14 测试专用故障注入钩子（默认关闭，生产须清空）

`plugin/scripts/lessons.mjs` 里有一个**测试专用**的故障注入钩子。
它存在的原因：D-59 / D-60 / D-61 都是 **Windows 上偶发**的文件系统错误
（rename 覆盖被占用文件报 EPERM、抢锁被拒报 EPERM、回读校验被并发覆盖）——
靠真实并发去撞，撞到与否看运气，断言就会**时敏**
（上一轮实测：同一个变异体一次跑出 2 条红、另一次跑出 0 条红）。
断言要确定性，就得能**指定**错误，而不是等它自己冒出来。

- **开关**：环境变量 `SAR_FAULT_INJECT`（逗号分隔的 token）+ `SAR_FAULT_RUN`（批次号）。
  不设 `SAR_FAULT_INJECT` ⇒ 钩子**完全关闭** —— 不加等待、不改返回值、
  正常写入的时序、返回值与文件内容与「没有钩子」时逐字一致（实测开销 1.06~1.11x，噪声量级）。
- **token 语义**（每个 token 只影响对应的那一个系统调用，互不串扰）：
  - `rename-eperm[:N]` —— 覆盖用的 `renameSync` 前 N 次抛 EPERM（模拟 Windows 上文件被占用）；
  - `lock-eperm[:N]` —— 排他创建锁文件前 N 次抛 EPERM（模拟 Windows 的 ERROR_SHARING_VIOLATION）；
  - `verify-fail` —— rename 成功后把目标文件改写成一份过期快照，使回读校验必然失败。
- `SAR_FAULT_RUN` 变化 ⇒ 计数归零（同一组 token 在同一批次里只触发 N 次）；
  回归里每个用例用不同批次号，避免上一条用例把额度用光。

**生产环境须知**：`SAR_FAULT_INJECT` 是**普通环境变量** ——
有人故意设它就能注入故障（这是「确定性断言」换来的代价，取舍写进 `docs/audit/fix-f02.md` §7）。
**部署到生产或长期运行时请显式清空**（`set SAR_FAULT_INJECT=`），或启动环境里不传这个变量。

## S15 无进展重复调用闸门（loop-gate）

子代理陷入「查证 → 验证 → 再查证」时，**跑的过程中**没有任何一层看得见：
S8 的 watchdog 挂在 `SubagentStop`（终点），只在 worker 停下来时看它最后一条消息；
普通 `task` 子代理也没有轮次上限。⇒ 本条给「跑的过程中」补一个判定点。

1. **判据只取行为，不取思维内容**：同一子会话内**连续发起 N 次完全相同的工具调用**、
   且中间没有任何别的工具调用时，**拦第 N+1 次**（不是拦第 N 次）。
   规则编号 `R-LOOP-SAME-CALL`；N 默认 **5**，可用 `SAR_LOOP_GATE_MAX_SAME` 覆盖（调小 = 更严）。
   「连续」以历史**末尾**为准 —— 本次调用尚未写入 transcript，计数 = 历史末尾连续条数 + 1。
2. **归一化指纹**（`plugin/scripts/loop-gate.mjs` 的 `fingerprint()`）：
   bash / run_code 取命令正文（空白折叠、换行折空格；`run_code` 的正文键叫 `code`，两个键都要认 ——
   不认的话复合工具的指纹恒为空，正常形态里连着几十次 `run_code` 会被整片误伤）；
   read 取 `path`（Windows 下大小写不敏感 + 斜杠归一）**并连 `offset`/`limit`** ——
   不同 offset/limit 读的是不同的一段，是**新信息**，不能算重复；
   glob / grep 取 `pattern` + `path`；其余工具取 arguments 的键排序稳定 JSON。
   **运行形态会改变计数口径（本机 PTC 运行时实测；D-91 已修）**：PTC 模式下 `bash` **不是顶层工具**，
   而是被包在 `run_code` 内部派发；宿主把 plugin PreToolUse 派发在**子调用**上 ⇒ 载荷是
   **内层**形态（`tool_name='bash'`、`tool_input={command}`），而**会话库的** transcript 的
   `message.content[]` 记的是**外层** `run_code`、内层调用记在
   `message.details.ptc.child_calls[]`（`tool_name` / `input` / `status`）——**但 hook 拿到的那个 transcript 不是会话库**（见本条下一段）
   ⇒ 两套序列的指纹永不相等 ⇒ 末尾连续数恒为 0 ⇒ 闸门**恒不触发**（D-91 的根因）。
   ⇒ 现在**按载荷形态择一计数**（`loop-gate.mjs` 的 `pickNamespace()` / `callsFromLines()`）：
   载荷是内层工具 ⇒ 数 `child_calls[]`；载荷是外层 ⇒ 数 `content[]` 的 toolCall。
   **两套序列绝不混数** —— 外层与内层在 transcript 里交替出现，混数会把连续段切碎，反而更拦不到。
   ⇒ **诚实边界**：内层记录落盘的参数是**子集**（实测 `bash{command}` / `read{path}` /
   `write{path}` / `edit{file_path}` / `grep{}` / `glob{}`）⇒ 参数没落全的内层记录**不可比**
   （`innerComparable()`）⇒ 打断连续段但**不计入** ⇒ 宁可少拦不误伤。
   **hook 拿到的 transcript 不是会话库**（D-97 已修）：宿主给 plugin PreToolUse hook 的
   `transcript_path` = `%TEMP%/minimax-plugin-hooks/transcripts/<sha256(sessionId).slice(0,32)>.compatible.jsonl`
   —— 一份 **Claude 兼容投影**，**不是**会话的 `messages.jsonl`。投影里**没有** `details.ptc.child_calls[]`
   （PTC 内层调用在投影中不可见），tool call 是 `type:'tool_use'`+`input`（不是 `type:'toolCall'`+`arguments`）
   ⇒ 只认会话库形态的解析器在**活体文件上 owned = 0** ⇒ 末尾连续数恒 0 ⇒ 闸门**恒不触发**（D-97 的根因）。
   ⇒ 现在**按文件形态择一命名空间**（`loop-gate.mjs` 的 `projectionCallsOf()` / `callsFromLines()`），
   **来源之间也择一**（**投影优先 + 会话库回退**，由 `resolveSessionTranscript()` 按 `session_id` 定位会话库），
   **两套口径绝不混数**（会话库口径的 5 个锚点 `pickNamespace()` / `innerCallsOf()` / `innerComparable()` /
   `incomparableFp()` / `callsFromLines()` 在 D-97 修复中**逐字未动**）。
   ⇒ 投影口径的计数单元是**外层 `run_code` 条目**，必须先把「内层 payload」对齐到「外层条目」：
   取外层 `code` 里**最后一个**内层调用（`innerTailOf()`，按花括号配平截取、跳过字符串字面量里的括号），
   再逐键比指纹键集（`tailMatches()`）；工具名不同 ⇒ `mismatch`（打断连续段）；键取不出
   （变量/表达式/模板插值）⇒ `unknown`（打断连续段但**不计入**）；全部键归一后相等 ⇒ `match`。
   ⇒ **计数基准**：宿主在执行内层调用**之前**就把外层 `tool_use` 落盘 ⇒ 投影口径把**当前外层条目排除**
   在计数之外（等价 §1 的「历史末尾连续条数 + 1」）；会话库口径相反（当前内层调用不在文件里）⇒
   两个来源的「当前调用是否已落盘」语义不同，分别处理。
   ⇒ **诚实边界（投影口径）**：同一段外层 `code` 里连发 6 次相同内层调用（模型把循环写进 `code`）
   ⇒ 只数到 1 次外层条目 ⇒ **漏拦**（fail-open 方向，不误伤）；载荷参数在 `code` 里是变量/表达式
   ⇒ 取不出 ⇒ `unknown` ⇒ 该次**不被拦**（不误伤）。

   实测后果（**会话库口径，D-91 期实测**）：PTC 形态下连发 6 次逐字相同的 `bash` **会被拦**；
   连发 29 次逐字相同的 `grep` **仍放行**（参数没落盘 ⇒ 无法判「是否同一次调用」）。
   **投影口径（D-97）**：真实投影字节 + 仓库实现 ⇒ 连续 6 次逐字相同调用 **DENY**（**本地回放**）；
   4 次以内仍全放行（不误伤）。**客户端活体拦截证据**以装入新副本并重启后的复验为准 ——
   未取到之前**不许**写成「已生效」。
3. **只对子代理生效**：载荷里没有 `agent_type`（父会话 / Router）一律放行 —— 与 S2 同一口径。
4. **本闸门是效率闸门，不是安全闸门：读不到就放行。**
   transcript 读不到 / 解析不出历史 / 载荷异常 ⇒ **放行**并往 stderr 留痕。
   这与 S2~S5 的 fail-closed 口径**故意相反**，理由是两个代价不对称：
   拦错的代价是**子代理干不了活**（它被卡住、交不出东西），放行的代价只是**少拦一次循环**。
   留痕不能省 —— **静默放行 = 机制看起来在跑、其实没跑**（D-86 这一族缺陷的形态）。
   另：S2~S5 的越界判定由 `guard.mjs` **独立承担**，本闸门失效**不放宽任何 scope 判定**。
5. **尾窗是下界，不是全量**：只读 transcript 尾部窗口（实测最大子会话 transcript 55 MB / 431 条消息，
   整读会让每次 hook 变成秒级）。真实 transcript 里**请求行与工具结果行交替**（行长 p90=20KB、最大 132KB），
   一次大结果就能把重复请求挤出固定窗口 ⇒ 连续数被**少算** ⇒ 静默放行。
   ⇒ 末尾连续段没被「指纹不同」的调用断开时**自适应扩读**（×4，上限 `SAR_LOOP_GATE_MAX_SCAN_BYTES`，默认 8MB）；
   触顶仍不确定 ⇒ 按**下界**少拦一次，但必须 stderr 留痕
   （**诚实边界**：这条留痕在生产是否可见未验证 —— 闸门本身不写台账）。
6. **登记的 matcher 必须显式列出工具名**：宿主对 MINIMAX 格式的 matcher 走**精确等值**
   （`alternatives.includes(value)`，**不是子串、也不是正则**）⇒ 写 `task` **不覆盖** `task_output`。
   而真实数据里最长的连跑族**正是 `task_output` 轮询** ⇒ matcher 必须显式列
   `task_output` / `task_query` / `task_stop`。
7. **归属键：哪些行算「本子会话的调用」**（这条直接决定拦不拦，必须写死）：
   归属键 = `turn_id` **去掉 `:` 后缀后取末尾的 uuid 段**（取不到 uuid 就用整串小写）；
   载荷的 `turn_id` 同样归一后与之比对。规则：
   - **A1** 行内**没有** `turn_id` ⇒ **计入**（没有归属信息 ≠ 不属于）；
   - **A2** 载荷**没有** `turn_id` ⇒ **计入**（没有参照键 ⇒ 不据此排除）；
   - **A3** 行的归属键与载荷相同 ⇒ **计入**；
   - **A4** 行的归属键与载荷不同 ⇒ **不计入**（别的子会话 / 父会话的行不参与本子会话的连续计数）；
   - **留痕**：窗口内**全部**调用都不属于本归属键 ⇒ **放行**并往 stderr 留痕
     （否则「归属键对不上」会表现为静默失效 —— 这正是 D-86 这一族缺陷的形态）。
   **方向性**：A4 只会让连续数变少 ⇒ **少拦一次，不会误伤**。
   **归属键的粒度 = 一个 turn**：本机实测里，一个子代理任务的**全部**工具调用共享同一个
   `turn_id`（形如 `turn_task_bg_bg_<uuid>`）⇒ 跨轮漏拦不成立；而**压缩快照与父会话
   transcript 会混装多个归属键**（实测 434 个文件里 122 个多键）⇒ A4 正是为它们准备的。
   **为什么用 `turn_id` 而不是 `sessionId`**：实测 434 个真实 transcript，真实行的顶层键只有
   `{message, message_id, turn_id}`，`sessionId` 键几乎不存在 ⇒ 用 `sessionId` 做归属过滤是
   **永不生效的死代码**（注释宣称 ≠ 代码在做）。而宿主派发给本插件（MINIMAX 格式）的载荷
   `turn_id` 与 transcript 行的 `turn_id` **同源同形** —— 实测派工台账里**带 `turn_id` 的
   派工记录，其 `turn_id` 逐字出现在对应会话的 transcript 行里**（12/12 全中；该值正是插件
   从 hook 载荷读到的同一个值）⇒ `turn_id` 是可用的归属键。

8. **活体验证状态（诚实边界，2026-11-12 实测）**：本闸门的**判定逻辑已坐实** —— 用真实子会话
   transcript + 真实载荷本地回放仓库版 `loop-gate.mjs`，第 6 次逐字相同调用即 deny（消息原文与本条一致），
   归属键不匹配时按 A4 放行（只少拦、不误伤）。
   PTC 形态另有一条回放证据（`tests/d91-ptc-replay.mjs`）：真实 PTC transcript + 真实**内层**载荷
   ⇒ 第 6 次即 deny（外层形态同时不回归）—— 这是「机制对不对」那一问的证据。
   但**「运行中的客户端里真被拦下过」这条活体证据尚未取到**：宿主把插件 hook 绑定在
   **注册时解析的缓存树**上（台账 D-88）⇒ **升级插件后必须重启 MiniMax Code 客户端**；
   2026-11-12 重启后活体树已换新（D-88 已实锤换绑成功），但闸门仍不拦的原因是
   **比对的是另一套命名空间**（台账 D-91，已在本轮修好）⇒ 取活体证据需要**重装 + 再重启**。
   写这一条是因为「看起来装上了、其实没跑」正是 D-86 这一族缺陷的形态，不能让读者以为装完就生效。

**误伤风险与阈值依据（N = 5）**
- 实测：430 个真实 transcript（803 MB）里，最长严格连续段 14 次（run_code）/ 10 次（task_output）；
  独立复验抽样 **60** 个真实 transcript 的**实际末尾调用**跑真实闸门 ⇒ **误拦 0**（60 ALLOW / 0 DENY）。
- 首要误伤面：**后台任务轮询**（`task_output` 同参轮询）。它确实是无进展循环，但也可能是合法等待
  （任务跑 150 秒、轮询 5 次）。逃生口：deny 文案要求说明卡点；agent 改一个 `wait_ms` 即换指纹、不再被拦。
- N = 5 的取舍：真实连跑 10~14 次说明 5 抓得住；再低会误伤「建目录失败后重试」这类正常重试。
  依赖长时后台等待的团队可调 `SAR_LOOP_GATE_MAX_SAME=8`（约 4 分钟等待窗口）。
- **PTC 形态的诚实边界**：内层记录只落盘**部分参数** ⇒ 参数没落全的内层调用（grep/glob 参数全空、
  read 只记 path、write/edit 只记定位字段）**不可比** ⇒ 打断连续段但**不计入** ⇒ 只能拦
  「参数落全」的那族（实测 bash）；实测一个真实 PTC 会话里连发 **29 次**逐字相同的 grep **仍放行**
  （参数没落盘 ⇒ 无法判「是否同一次调用」）—— 这是 fail-open 方向的诚实边界，不藏。
- **覆盖形态的诚实边界**：本规则只覆盖「**严格连续**」这一族；「查证 → 验证 → 再查证」这类
  **被别的调用打断**的打散形态覆盖有限（实测 run≥4 的事件 41 条，绝大多数是被打断的重复）。
  要覆盖打散形态需要「同一指纹累计次数」口径 —— 那是另一条规则，本版没有。
