# Scope 管控边界

派工时声明的 `SCOPE` 不是建议，是**程序层可拦截的硬边界**。
本插件的 `PreToolUse` Hook 会按下面的规则判定。

## 管控分类

| 类别 | 工具 | 判定 |
|---|---|---|
| **写** | `write` `edit` `multiedit` `notebookedit` `bash` | **严格**：必须精确落在白名单内 |
| **读** | `read` `glob` `grep` `list` `search` | **宽松**：允许读 scope 所在目录树 |
| **危险** | `mavis_agent_create` `mavis_agent_delete` `mavis_agent_update` `website_deploy` `miniapp` / `miniapp_publish`，以及 `mavis` 的 `agent create` | **一律拦**，不论有没有 scope。建号与删除、改写**对称** —— 账号成员是跨项目全局可见的，子代理自己建号会让账号成员与项目名录脱钩 |
| **复合** | `run_code` | **只判危险操作**；作用域交回内层调用（见下） |

## 只约束子代理（v0.4.0 起）

派工发生在**父会话**（Router 发起），工具执行发生在**子会话**（worker 执行）。
插件的判定基准是工具调用载荷里有没有 `agent_type` 字段：

- **有** → 子代理会话 → 按 scope 严格判定
- **没有** → Router 父会话 → 直接放行

这条分水岭是必须的：Router 要汇总产出、跑验收、做复盘，
它必须能读写 worker scope 之外的文件。早期版本用同一个 session_id 索引
父与子两层，结果 worker 查不到自己的 scope（管控对真正要约束的人失效），
Router 反而命中（被自己派出的 worker 锁死）。

worker 的 scope 来自**它自己 transcript 里的派工原文** —— 那是 Router 亲手写下的
白名单，是唯一权威来源，不需要任何 id 猜测或时序启发式。

## 组队闸门（v0.4.0 起）

两道闸门在**派工时**就拦，不等到 worker 动手：

| 闸门 | 判什么 | 触发后果 |
|---|---|---|
| **scope 重叠** | 新 SCOPE 与本会话仍在飞的派工是否有写冲突 | 拒绝派发，报出冲突路径 |
| **派工数上限** | 并发在飞 > 6 或单会话累计 > 30 | 拒绝派发 |

- 只算**写冲突**（条目相同，或一方是另一方的目录前缀）。读范围天然重叠，不算冲突。
- worker 结束后（`SubagentStop`）它的名额会被回收，所以「派完 → 验收 → 再派」不会误报。
- 超过 2 小时没回收到结束信号的视为失联，不再计入在飞。**这只回收台账名额，不会停掉还在跑的子代理** —— 要停得由父会话显式停（停后台任务用 `task_stop`，停子会话当前轮次用 `mavis_session_interrupt`）。

## 写：严格

目标必须精确等于某个 scope 项，或落在显式以 `/` 结尾的目录项之下。

```
SCOPE: src/app.ts
  写 src/app.ts        → 放行
  写 src/app/sub/x.ts  → 拦（src/app.ts 是文件，不是目录）

SCOPE: src/app/
  写 src/app/x.ts      → 放行
  写 src/app/sub/y.ts  → 放行（目录涵盖其下）
  写 src/other.ts      → 拦
```

## 读：宽松

读操作允许读到 **scope 所在目录树** —— Worker 需要看邻近文件理解代码，
这是正当的探查，不该被拦。

```
SCOPE: src/app/login.ts
  读 src/app/login.ts     → 放行
  读 src/app/session.ts   → 放行（同目录，理解上下文）
  读 src/app/sub/x.ts     → 放行（同目录树）
  读 config/prod.yaml     → 拦（无关目录）
```

## 绝对路径一样算

MCode 的工具接受绝对路径，scope 通常写相对路径。插件会自动把绝对路径
折算成相对工作区的路径再比对，**两种写法都能命中**，不会出现"绝对路径永远不匹配"。

## 危险操作：一律拦

这几类不碰工作区文件，但执行后是账号级或对外可见的**不可逆**动作：

| 工具 | 为什么拦 |
|---|---|
| `mavis_agent_delete` | 删除成员是账号级不可逆操作，历史会话不会随之清理 |
| `mavis_agent_update` | 改成员的 description/system_prompt 是账号级变更，需人工确认 |
| `mavis_agent_create` | 建号是账号级全局可见的变更，需人工确认（与删除、改写对称） |
| `website_deploy` | 部署会把内容发布到公网 |
| `miniapp` publish | 发布会替换线上运行实例 |

这类动作**即使没有 scope 声明也会被拦** —— 它们不受派工范围保护，
必须由用户亲自发起或明确授权。

**同一条清单在 bash 通道同样生效。** `mavis` 是本机真实存在的 CLI，
命令文本里的 `mavis agent delete <name>` 会被 shell 真的执行 —— 工具名匹配不到它，
所以 bash 通道必须按**命令形态**（CLI + 子命令 + 动作）识别这类动作，而不是见到 `delete` 就拦。
同理，部署与 Mini App 发布在 bash 里出现的形态也要拦。

判定细节（v0.5.0 定稿）：

- **按命令位置判，不按字样判** —— `rm build/out.txt`、`grep "mavis agent delete"` 这类普通操作**不拦**；
- 命令替换（`$(...)` / 反引号）载荷、`sh -c` / `eval` 载荷，按其**内层命令**同判
  （`cat $(mavis agent delete x)` 是实打实的洞）；
- 只读分流仅对**无命令替换**的命令生效；
- `website_deploy` / `miniapp publish` 在 bash 里**仅按命令位置**拦
  （`cat website_deploy.md`、`grep "miniapp publish"` 不拦）—— 这两个词在 bash 里更像文件名或文本。
- **包装器开关按包装器分别定义**（带值 / 布尔 / 位置参数分列），不能共用一张全局开关表
  —— 布尔开关被当带值时命令词会被吞，判定落空即放行；
- **账号级 CLI 的子命令必须是第一个**：`mavis agent delete` 算，`mavis list agent delete` 不算；
- `<(…)` 进程替换与 base64 编码载荷同属真执行；**解不出来就拒绝，不放行**。
- **命令位置不用闭集包装器名单实现**（这是同一族绕过的共同根因）：
  段首是数据命令 → 段内都是数据；段首不是 → 段内每个 token 都是命令候选。
  这样 `exec`、`taskset`、`watch`、`at`、`parallel`、`script`、`chroot`、`strace`
  以及将来出现的任何包装器都自动被覆盖。数据命令清单里**不收** `tar`/`unzip`/`zip`/`gzip`
  （`--to-command` 会真执行）。
- **载荷取参按 shell 语义**：`sh -c` 的命令串只有**一个**参数（后面跟的是 `$0`/`$1`，不是命令）；
  `command -v` 是查询语义，那一段没有命令位置。

## 复合工具（run_code）：只判危险操作，作用域交回内层调用

`run_code` 的载荷是**一整段代码**，不是路径实参列表。插件在复合层只做危险操作判定：

| 代码里出现 | 复合层判定 |
|---|---|
| 危险工具名 / 危险参数（`mavis` 的 `agent delete`、`miniapp` 的 `publish`、`website_deploy`） | **拦** |
| 只**提到** scope 外的路径（注释、字符串常量、引号里的命令串） | **不拦** —— 作用域由内层调用各自判定 |
| 纯计算代码（不含任何路径 token） | **不拦** |

原因：复合层若对整段代码文本扫路径，注释里的一个路径字样、引号命令里的一个斜杠，
就会把整次调用拒掉 —— 以 `run_code` 为主力工具的 worker 会大面积撞墙。
内层 `write` / `edit` / `bash` 调用各自触发 PreToolUse，判定对象是真实实参，
边界照样守得住，而且比扫描整段代码文本精确。

> **运行时事实（v0.5.1 复测更正）**：容器调用的 PreToolUse 派发**不是平台恒定行为，随会话而变**。
> 2026-11-10 10:22 的子会话里，外层 `run_code` 在 guard 的入参日志里没有任何条目（容器内的子调用才有）；
> 但 14:29 与 15:10 的子会话里，同样形状的调用被派发并被复合层当场 DENY（金丝雀复测）。
> 所以上表的复合层判定**会生效，但不保证每次都生效** —— 它是一条**纵深防御的加成**，
> 真正稳定在拦人的是**内层调用各自判定**。这条事实决定了安全设计的落点：
> **危险操作的识别必须在内层通道做到位**（尤其 bash 通道要认得出 `mavis agent delete` 这类命令形态），
> 不能把复合层当成唯一防线。

## 绕过路径

| 想干的事 | 正解 |
|---|---|
| 需要改 scope 外的文件 | 先更新 scope 重新派工，不要自行扩大范围 |
| 需要读别的目录 | 在 brief 里写明，或派一个 scope 覆盖该目录的成员 |
| 需要删成员 / 部署上线 | 交回给用户，由用户亲自执行 |

**不要尝试用 bash 绕。** bash 命令里的路径同样会被逐段检查。
## v0.5.0：通道语义与只读条目

上面的「写严格 / 读宽松」是**总体**描述。同一个 scope 在不同工具通道上的判定方式
并不相同，v0.5.0 把这套差异写成了硬规则（完整判据见 `references/contract.md` 的 S2、S3）：

| 通道 | 判定对象 | 判定方式 |
|---|---|---|
| read / list | 目标路径 | 读判定：允许 scope 条目所在目录树 |
| glob / grep | **有效检索根**（显式 `path` 优先，缺省用工作区） | 读判定。判定对象不是 pattern 本身 |
| write / edit | 目标路径 | 写判定：必须精确命中白名单 |
| bash | 命令里的路径 token | **按命令意图分流**：只读命令按读判定，其余按写判定 |
| 复合工具（`run_code`） | **不做作用域判定** | 只判危险操作；作用域交回内层调用 |

### 只读条目 `ro:`

想让成员读一个目录、却不想给它写权限时，用 `ro:` 前缀：

```
SCOPE: ro: plugin/scripts/, docs/audit/report.md
  读 plugin/scripts/guard.mjs   → 放行（ro 条目按所在目录树放行读）
  写 plugin/scripts/guard.mjs   → 拦（ro 条目永不授予写权限）
  写 docs/audit/report.md       → 放行（普通条目）
```

`ro:` 条目**不参与派工的写冲突检测** —— 两个人都只读同一个目录不构成冲突。

### bash 的路径 token 识别

只有含路径分隔符、以 `.` 开头的点目录、或含已知扩展名的 token 才算路径。
`console.log`、`JSON.stringify`、`v0.4.0` 都不是路径，不会被当成越界目标；
而目录型目标（`rm -rf config`、`.git`、`node_modules`）能被识别，不会整体逃逸。

### 解析不出边界 = 拒绝

worker 的 scope 来自它自己 transcript 里的派工原文。v0.5.0 起，解析兼容 `compatible`
与 `codex` 两种 transcript 变体，且按语义定位（找到含 `SCOPE:` 的那条 user 消息），
而不是固定扫前几行。

**解析不出来时一律拒绝，不再放行** —— 解析不到边界等于没有边界，
此时放行等于整套管控不存在。

### 派工前的边界自检三连

1. **读得到吗**：成员要读的每个路径，是否都落在某个 scope 条目的所在目录树内
2. **说得准吗**：brief 里每句关于边界的描述，是否与上面的通道语义一致
3. **同源吗**：条目模板、编号规则、状态口径，是否直接引用契约文件而非复述

### 子会话不触发 SessionStart / UserPromptSubmit（v0.5.0 实测确认）

`plugin/hooks/hooks.json` 声明的 hook 全部挂在**父会话（Router）**的事件流上：
子会话**不会**触发 `SessionStart`，也**不会**触发 `UserPromptSubmit`。
这是运行时的事件结构事实，没有对应事件可挂，代码层面关不掉。

因此协议里的「SessionStart 注入编排协议」只对 Router 生效。对 worker 而言：

| worker 需要的东西 | 怎么到达 |
|---|---|
| 编排协议要点 | **随 brief 走** —— Router 在 brief 里写清，别指望 hook 自动注入 |
| 派工白名单（SCOPE） | brief 正文 + 子会话 transcript（guard 从那里解析） |
| 该成员的历史教训 | **guard 直接注入 worker 上下文**（v0.5.0 起，不再只挂父会话） |
| 该成员的实战记录（履历） | **不进 worker** —— 它是**匹配时给 Router 的参考**（「这个人做成过什么」），不是开工教材。开工前 worker 只需要**教训** |

Router 侧的纪律：派工 brief 本身就是 worker 唯一的协议载体，
所以 brief 必须写全——目标、边界、验收标准、交付要求，一条都不能省。

### 权限等级（tier）与自动审核（v0.5.4）

scope 是「这次派工允许碰哪些路径」；**权限等级是「这个成员平时有几分权限」**。
两者的**变更入口**都归父会话：机制把权威面脚本（提权 / 批准扩权 / 写履历 / 写错题本 /
登记成员）列为父会话专属，子代理执行它们会被护栏拒绝；
但 hook 是护栏不是沙箱（契约 S13.5），所以「成员自己改不了」这句话按现状**不成立**——
真正的防线是运行时权限 + 审计留痕 + 验收时复核（`review.md` 的扩权复核清单）。

| 等级 | 语义 |
|---|---|
| `scoped`（默认） | 逐路径白名单；白名单外一律拦，越界自动记账 |
| `full` | 项目工作区内自由读写，不必逐路径枚举 |

声明位置是项目级 `.superagent/roster.json` 的成员条目（`tier` 字段），
不是派工台账 —— 台账是半持久的（TTL 2 小时、截断 200 条），权限等级必须活过台账的生命周期。

**full 的四条例外**（与契约 S13.3 一致）：

1. `.superagent/` 编排层私有状态目录除外 —— 成员互相篡位与自提权的战场；
2. 工作区之外的路径仍拦，仍自动记账待审；
3. 账号级 / 对外不可逆动作照旧硬拦；
4. **写冲突检测仍按声明的 SCOPE 比对** —— full 放开的是「白名单外的项目内路径」，
   不是「冲突检测」；full 成员的 SCOPE 仍要写清楚它实际要动的范围。

**自动审核的链路**：worker 撞墙 → guard 自动记账（台账 `scope_requests[]`，
同目标 `hits` 累加）→ 父会话 `scope-amend.mjs --list` 看待审清单 →
`--grant` / `--deny` 裁决。批准只授该次请求的粒度：
**读请求只给 `ro:`，批准读不等于批准写**；批准必须落在仍在飞的派工上
（`--grant` 与 `--dispatch --add` 两条路径同口径）；
批准人必须是该派工的**父会话 id**（`--list` 会直接给出这个值）。

**等级按派工时快照**：派工那一刻把成员的 tier 写进派工记录，子会话绑定继承这份快照 ——
会话中途的等级变更对已在飞的会话不生效（下一个派工才按新等级生效）。

派工前的**边界自检三连**在 full 等级下同样要做 —— 尤其第一条：
full 只放开「工作区内」，成员要读的路径若在工作区外，仍需父会话逐条批准。

还要记住第四条：**冲突检测仍按声明的 SCOPE 比对**。
full 成员的 SCOPE 要写清楚它实际要动的范围，否则两名 full 成员声明不重叠时机制不拦，
而两人实际都可能动同一个文件。
