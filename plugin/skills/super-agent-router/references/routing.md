# 路由规则

## 直做快路径（优先级最高）

满足任一条就直接做，**不组队、不建成员**：

- 改 typo、修注释、调格式
- 查 API 用法、读文档
- 单文件、小改动、spec 明确
- 回答问题、解释代码

判定直做后直接执行。**默认成员数 = 0。**

## 双事实源交叉核对

成员存在于两个地方，含义不同：

| 来源 | 是什么 | 范围 |
|---|---|---|
| `mavis_agent_list` | 成员**是否存在** | 账号级全局，跨项目 |
| `.superagent/roster.json` | 成员的**专项元数据** | 项目级 |

**只读 roster 会漏掉别处建的成员，只读 list 又不知道谁擅长什么。**
所以每次路由都要两边都读，然后交叉核对：

| list | roster | 结论 |
|---|---|---|
| 有 | 有 | 复用 |
| 有 | 无 | **收编**：补登记元数据，**不要重建** |
| 无 | 有 | 陈旧条目：标记待清，不派工给它 |
| 无 | 无 | 需要新建 → 走造人闸门 |

## 匹配流程

1. 先判直做快路径 → 命中就直接做，结束
2. 读 roster.json + 跑 mavis_agent_list，交叉核对
3. 把任务拆成「要做哪些事」
4. 对每一件事，找 `owns` 覆盖它的专精成员
   - 命中 → 复用，并读它的 `.superagent/methods/<name>.md`
   - 未命中 → 判断**当前任务**是否值得建专项
     - 值得 → 现场配置（见 `bootstrap.md` 三步）
     - 不值得 → 用通用 `worker` 直做

**关键**：成员「能做」某事 ≠ 这件事有人做到精。不要因为通用成员沾边就复用。

## 实战记录（履历）怎么参与匹配

插件的 `gate.mjs` 会把各成员的实战记录摘要注入上下文，作为「该派给谁」的参考：

- **参与匹配**：这人做成过类似的事 → 匹配时可以优先考虑
- **不参与归属**：`owns` 归属声明永远以 `roster.json` 为准，不因战绩自动收窄

理由：归属声明是人工可审计的资产。让模型根据战绩自行收窄 `owns`，
等于让系统自己给自己发权限 —— 不可审计，也不可追责。

想收窄归属，由人改 `roster.json`，走 git 记录。
详见 `records.md`。

## 现场配置 vs 预置

成员**永远在运行时配置**，不预先打包。理由：

- 预置的专项方法论是基于假想场景写的，与真实任务不符
- 方法论的价值随任务经验增长，现场写才准
- 预置成员会诱导「因为有现成的就用它」，掩盖了「这事到底需不需要专精」

插件包里只放：内置成员引用 + 通用 worker + 协议本身。**不放任何业务专项。**

## 造人闸门

全部满足才可现场配置：

- [ ] 当前任务确实需要「做到精」，不是通用 worker 能对付的
- [ ] 交叉核对后确实没有同类专精成员
- [ ] 能一句话说清负责哪一件事
- [ ] 能写出可勾选的验收清单
- [ ] 方法论文件已写好
- [ ] 本次会话尚未配置过成员
- [ ] roster 总数 < 12
- [ ] 新建成员的 description 不含项目细节（成员是账号级全局可见的）

## 名称规范

- 专项成员：`sa-<专项领域>-<专项动作>`
- 避开内置名：explore / worker / verifier / mavis
- 避开显示名：General / Coder / Verifier

## 组合约束

- scope 交集为空
- scope 并集覆盖任务
- 职责正交（实现 vs 验证、取数 vs 成稿）
- 默认 1 个成员，最多 2 个
- 一个 brief 只给一个成员
