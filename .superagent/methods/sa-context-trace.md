# sa-context-trace

## 归属

上下文注入与传递链路追踪：查清「子会话到底拿到了哪些上下文、分别从哪来、
以什么格式到达、哪些根本没到达」。产出一份上下文来源清单与缺口清单。

## 适用

- 要回答「这个成员到底看到了什么」这类问题
- 怀疑某段上下文（注错题本规则、注实战记录、注 brief、注方法论路径）实际没到位
- 要评估「是否需要给同组成员做共享上下文」——先得知道现在各自拿到的是什么

## 不适用

- 不改机制代码（追踪 ≠ 修复）
- 不做缺陷审计结论（那是 sa-orchestration-audit 的事；本单只负责「事实」）
- 不做发布

## 方法

1. **从接线表入手。** 读 `plugin/hooks/hooks.json`，列出每个 hook 事件绑定了哪个脚本、
   什么 matcher、什么超时。这是「上下文从哪条线进来」的地图。
2. **逐个 handler 读注入点。** 对每个脚本，找到它**往外输出什么**、**输出时机**是
   会话开始、工具调用前还是子代理结束时。分清三种载体：
   plain-text stdout（直接进模型上下文）、hookSpecificOutput（判定用）、JSON（写状态用）。
3. **用真实 transcript 验证，不靠读代码推测。** 子会话 transcript 的第一条 user 消息里，
   应该同时能看到派工原文、`SCOPE:` 行、父会话标记、成员名。
   找到实际的 transcript 文件并把关键行摘出来 —— 这是事实，不是推断。
4. **列「谁注入给谁」的矩阵。** 维度：来源 × 接收方（Router / worker / verifier）。
   空白格就是缺口。
5. **把缺口翻译成判断依据。** 每个缺口回答一句：它会导致哪种具体后果？
   「成员看不到上一次的验收发现」和「成员看不到上一次的验收发现」不是同一句话，
   前者要接「轮次之间靠谁传递」。
6. **给共享上下文的判断，但只给事实基础。** 结论由 Router 下；本单负责把事实摆齐。

## 验收清单

- [ ] 每个上下文来源都含：来源文件与行 / 注入时机 / 载体格式 / 验证方法
- [ ] 至少有一条来自**真实 transcript 样本**的原文摘录（不是代码推断）
- [ ] 有一张「来源 × 接收方」矩阵，空格明确标为缺口
- [ ] 每个缺口配一句「会导致什么具体后果」
- [ ] 产出的结构与同批另一份清单**字段完全一致**（同字段、同顺序、同命名）
- [ ] 全程只改动 SCOPE 内的文件

## 易错

- 只读代码就断言「注入了」—— 没在真实 transcript 里看到过，就只能说「代码路径会注入」
- 把「子会话拿不到」和「子会话不该拿到」混为一谈
- 漏掉 Hook 的会话激活时序：hooks.json 是会话开始时解析的
- 顺手把链路上的问题修了 —— 追踪者一动手，事实就不再独立
