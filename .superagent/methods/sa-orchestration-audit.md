# sa-orchestration-audit

## 归属

编排机制的行为缺陷审计：沿着 guard / dispatch / watchdog / gate 的**判定代码路径**逐条走，
找出「在什么输入下会放行不该放行的、拦掉不该拦掉的、判错方向」的行为漏洞。
产出一份**每条都能复现**的缺陷清单。不是代码风格评审，不是需求讨论。

## 适用

- 怀疑某条判定路径在某类输入下失效（漏拦、误拦、放行了越界操作）
- 怀疑两个机制叠加时互相干扰（台账与绑定不同步、名额与状态不一致）
- 机制改动之前，需要先知道现状哪里是脆的

## 不适用

- **不改机制代码本身** —— 审计与修复必须分开，否则审计结论不可信（执行者不可自证）
- 不做发布（那是 sa-plugin-release 的事）
- 不做 GitHub 推送等对外可见动作

## 方法

1. **先画判定分支，不先下结论。** 对每个脚本，把「输入条件 → 判定结果」列成表：
   哪个字段决定走哪个分支、哪个分支是放行、哪个分支是 deny。
   审计对象是**分支**，不是文件。
2. **找「默认放行」的地方。** 放行分支比拦截分支危险得多 —— 拦截漏了会报错，
   放行漏了会静默失效。特别注意：解析不到边界就放行、空数组就放行、
   异常捕获里就放行。
3. **找「静默失效」。** 机制写进台账但没人读、字段名对不上、键建了没被查询、
   常量定义了没被引用 —— 这些都不报错，只是机制根本没生效。
4. **对每个候选缺陷，写出最小复现。** 复现要能落到具体输入或具体命令，
   写不出复现步骤的条目**直接删掉**，不要留在清单里充数。
5. **区分「已复现」与「推断」。** 清单里每条都要标状态。
   推断出来的要写清楚推断依据，并说明还需要什么才能确认。
6. **给出修法，但只给方向。** 修法要落到「改哪个文件、改哪段判定」，
   不要写「建议加强校验」这种无法执行的话。

## 验收清单

- [ ] 每条缺陷都含：触发条件 / 影响 / 复现步骤 / 证据（文件行号或命令真实输出）/ 修法方向
- [ ] 每条都标明状态：已复现 或 推断（推断要写推断依据）
- [ ] 清单里没有「看起来不太对」这类无法判定为对错的条目
- [ ] 审计覆盖了 guard、dispatch、watchdog、gate 四个脚本的**判定分支**，不只是主流程
- [ ] 产出的结构与同批另一份清单**字段完全一致**（同字段、同顺序、同命名）
- [ ] 全程只改动 SCOPE 内的文件（只读审计，脚本源码一个字都没改）

## 易错

- 只读主流程就下结论 —— 缺陷大多在异常分支和默认分支里
- 把「代码写得不够优雅」当缺陷 —— 不可复现的一律删
- 顺手把发现的问题修了 —— 审计者一动手，结论就失去独立性
- 只看本仓库的副本，不看实际被加载的那份（安装目录 / 运行时缓存）
