## 状态：v0.4.0 已发布，并通过独立验收

插件已被 MCode 识别并启用（`v2/plugin-hook-cache/` 有完整包副本）。
**必须新开一个会话** —— Hook 按会话激活，旧会话不会重新注入协议。

v0.4.0 修的是一条更底层的错配：**派工发生在父会话，工具执行发生在子会话**，
而 v0.3.x 用同一个 session_id 索引两层，于是两头都错。

## v0.4.0 修了什么（真实跑一遍编排闭环查出来的）

本轮不是读文档推的，是**真跑**出来的：现场配置专项成员 → 派工 → 独立验收 → 记履历。

| 漏洞 | 探测方式 | 后果 | 修法 |
|---|---|---|---|
| guard 按 session_id 找 scope，台账记的却是「发起方」会话 | worker 在子会话改 scope 外文件 | 越界管控对真正要约束的 worker 完全失效 | 改按子会话绑定，scope 从子会话自己的 transcript 派工原文解析 |
| Router 父会话被 worker 的 scope 套住 | 派完第一个工，Router 写自己的收尾文件 | Router 被自己派出的 worker 锁死 | 载荷无 `agent_type` 即放行 —— 只约束被派工的子代理 |
| 组队 scope 重叠无人检测 | 同一会话连派两个重叠 scope | 两个 worker 互相覆盖，验收无法判断谁的改动生效 | dispatch 闸门：写冲突即拒，报出冲突路径 |
| 单会话派工数无上限 | 同一会话连派 7 个 | 编排失控，用派工代替思考 | dispatch 闸门：并发在飞 6 / 累计 30 |
| worker 结束后名额不回收 | 派工后不看台账 state | 在飞数只增不减，会话把自己锁死 | watchdog 在 SubagentStop 回收名额 |
| worker 读不到自己的方法论 | worker 读 .superagent/methods/ 被拦 | 「把一件事做到精」的载体被切断 | guard 读模式放行该成员的方法论与错题本 |
| watchdog 把版本号当文件路径 | 交付报告里写 0.4.0 | worker 被逼反复改写交付说明 | 路径校验收窄到带产出动词的句子 |
| 发布只同步脚本、漏同步清单 | 安装目录 version 仍是 0.3.2 | 机制生效了但「版本身份」没发布出去 | 部署改全量同步（tools/deploy-plugin.mjs） |

新增 chain-test 第 6～15 组锁住这些行为，八套回归全绿。

## 仍需注意

- **Hook 按会话激活**：装完或升级后必须新开会话才生效。
- **guard 是护栏不是沙箱**：脚本一旦落盘就能绕过工具级判定。
  真正的边界是运行时权限 + 人工确认，别把 hook 当安全边界。
- **平台原生 Agent Team 与本插件互补**：原生管「要不要拆、拆几个」，
  本插件管「派给谁 + scope 边界 + 验收闭环 + 错题本与履历沉淀」。

| 沉淀 | 记两条实战记录 + 写一条错题本 | 教训在下一单派工前被 Hook 自动注入（已实测生效） |

### 这一轮暴露的、我自己的问题

1. **brief 给不全边界** —— SCOPE 只列一个文件，成员读不到其余脚本；且 brief 里写的「整个目录可读」与 bash 通道的写判定语义不符。40 分钟撞墙是我的锅，不是成员的。
2. **模板没有单一事实源** —— 给两个 worker 的条目模板是 6 字段，给 verifier 的是 7 字段，于是验收反过来判产出「字段模板不一致」。
3. **编号没有全局命名空间** —— 两份清单都从 F-01 编起，合并必撞 8 组号。契约给了字段格式却没给编号规则。
4. **归因公平正则有语序漏洞** —— `lessons-gate.mjs` 的 `brief\s*给错` 匹配不到「给错的 brief」，Router 的锅能写进成员错题本。
5. **Router 自己没有错题本** —— 归因指向 Router 的错误无处沉淀，只能靠单次记忆。
6. **派工被取消时名额不回收** —— 只有 SubagentStop 一条通路；本轮实测取消后台账 `state` 仍停在 `active`。
7. **追加 brief 不更新已绑定的 scope** —— 同一子会话内放宽边界不生效，只能重派。

### 关于「同组要不要共享上下文」

结论：**不共享原始上下文；共享「产出契约 + 经验收裁决的结论」，由父会话做切片器。**
本轮的实证：两名成员互不通信、各自产出，字段结构完全一致（契约有效），但编号各自从 F-01 起（契约缺命名空间）；
2 组重复缺陷需要人工合并（缺跨成员查重），1 条假发现只有独立验收能抓出来（共享原始上下文反而会让错误一起传播）。
详见 `docs/audit/defect-ledger.md` 第二节。

### 我自己又犯了一次同一类的错（已进 `.superagent/lessons/_router.md` RT-04）

上一轮我把「合成载荷能 DENY」当成了「这层防护在真实运行时成立」，
验收报告也照着这个前提写了「改判条件①满足」。实际上**平台根本不对 `run_code` 容器派发事件**，
整层防护是空的 —— 而这个空档正好掩护了 D-25：复合层能识别 `mavis agent delete`，却没人调用它。

**教训：合成载荷只验「判定逻辑」，不验「触发链路」。** 「机制对」与「链路通」是两个问题，
合并成一个结论就会造出「防护存在」的假象。验收里凡是问「某工具受不受保护」，
必须有一条**该工具在真实运行时的触发记录**，不能只有合成载荷。

## v0.5.0 定稿：D-25 族的彻底闭环与一条方法论教训

D-25 是本轮**复验收尾时从运行时取证里挖出来的 P0**：bash 通道的危险操作清单不覆盖账号级动作，
`mavis agent delete <name>` 可以绕过护栏（`mavis` 是本机真实存在的 CLI，命令文本会被 shell 真的执行）。

它经历三轮修复，每一轮独立复验都挖出新的同族残余：

| 轮次 | 主体 | 复验结论 | 新查出的残余 |
|---|---|---|---|
| 第 1 轮 | 命令形态判定（CLI+子命令+动作）、命令替换、包装器、只读分流 | PASS_WITH_RESIDUAL | D-25b（布尔开关吞 token → 4 条形态放行）、D-25c（`mavis list agent delete` 过度拦） |
| 第 2 轮 | 包装器开关按包装器分别定义、包装器集合补齐、载荷两式取参、子命令位置 | PASS_WITH_RESIDUAL | D-25d（`exec` 家族 17 条形态放行 —— 闭集包装器表是结构性缺口）、D-25e（两例过度拦） |
| 第 3 轮 | **命令位置从「闭集名单」改为「数据段/执行段」二分** | 父会话活体复核 43 条必拦全 DENY / 21 条负例全 ALLOW / 0 异常 | — |

### 这条线上最有价值的不是修好了一个洞，是认出了根因

**「命令位置」如果用闭集包装器名单实现，就永远会被绕过** —— 补 10 个名字，下一个变体照样漏。
真正的判据是区分**数据段**与**执行段**：
段首是数据命令 → 段内都是数据（`grep "mavis agent delete" src` 放行）；
段首不是 → 段内每个 token 都是命令候选（`exec`、`taskset`、以及将来任何包装器自动覆盖）。

这条已经写进契约 S5 第 9 条与 `references/scope.md`。

### 同一条线上我犯的两次错（都已进 `.superagent/lessons/_router.md`）

- **RT-04**：把「合成载荷能 DENY」当成「这层防护在真实运行时成立」。合成载荷只验**判定逻辑**，不验**触发链路** ——
  平台不对 `run_code` 容器派发事件（D-26），所以那层防护是空的，而当时验收写的是「改判条件①满足」。
- **误伤与漏放是同一枚硬币**：为了堵漏放而把判定放宽，误伤会逼着 worker 绕过护栏 ——
  `mavis list agent delete`、`command -v`、`sh -c` 未加引号这三例都是**过度拦**。
  护栏要判的是**形态**，不是字样，也不是「看起来像危险词」。
