# 父会话作业规则（每次派工前必看）

## 1. 会话复用优先（用户明确要求）

**同一专项的连续工作，优先「追加到已有子会话」，不要新开。**

新开一个子会话 = 那位成员要**重新读一遍**它需要读的东西（方法论、契约、台账、相关脚本、既有报告）。
用户原话：「每一次都开新的窗口会造成很大的上下文浪费……每一次那个成员都要重新读一整个仓库」。

**派工前查** `docs/audit/.tmp-parent/reuse-registry.md`：

- 该成员有会话，其**冻结边界**覆盖本单要动的路径 ⇒ **追加**（`task_append`）；
- 覆盖不了 ⇒ 才新开。

**追加时的三条硬规矩**（都是本轮实测踩出来的）：

1. 追加内容**必须自包含**（会被并入它下一轮，措辞会被机制判定）；
2. 追加内容里**不要写 SCOPE 行**，除非写成合规格式（`SCOPE: a, b, c` 逗号分隔、无反引号、行首 SCOPE）——
   写成顿号+反引号 ⇒ 解析出 0 条 ⇒ **整个会话的工具调用全被拒**；
3. 复用会话的**边界是冻结的**（派工时定死，已结束的派工不能再扩权）⇒ 下单前先核对边界覆盖度。

**归档与复用互斥**：归档过的会话不能再被追加（`TASK_CHILD_ARCHIVED`）。
⇒ 归档前先想清楚这个会话将来还要不要续。**别为了列表好看把还能复用的会话归档掉。**

## 2. 复用率是��盯的指标

同一专项成员的「会话数」应当**远小于**「派工单数」。
2026-11-10 收敛前后：sa-mechanism-fix 13 → 6，sa-gate-integrity 7 → 2，全专项 45 → 13。
若某个专项又开了十几个会话却只干了两三件事，那就是在重复启动。

## v0.5.0 定稿：D-25 族的彻底闭环与一条方法论教训

D-25 是本轮**复验收尾时从运行时取证里挖出来的 P0**：bash 通道的危险操作清单不覆盖账号级动作，
`mavis agent delete <name>` 可以绕过护栏（`mavis` 是本机真实存在的 CLI，命令文本会被 shell 真的执行）。

它经历三轮修复，每一轮独立复验都挖出新的同族残余：

| 轮次 | 主体 | 复验结论 | 新查出的残余 |
|---|---|---|---|
| 第 1 轮 | 命令形态判定（CLI+子命令+动作）、命令替换、包装器、只读分流 | PASS_WITH_RESIDUAL | D-25b（布尔开关吞 token → 4 条形态放行）、D-25c（`mavis list agent delete` 过度拦） |
| 第 2 轮 | 包装器开关按包装器分别定义、包装器集合补齐、载荷两式取参、子命令位置 | PASS_WITH_RESIDUAL | D-25d（`exec` 家族 17 条形态放行 —— 闭集包装器表是结构性缺口）、D-25e（两例过度拦） |
| 第 3 轮 | **命令位置从「闭集名单」改为「数据段/执行段」二分** | 父会话活体复核 43 条必拦全 DENY / 21 条负例全 ALLOW / 0 异常 | — |

### 这条线上最有价值的不是修好了一个洞，是认出了根因

**「命令位置」如果用闭集包装器名单实现，就永远会被绕过** —— 补 10 个名字，下一个变体照样漏。
真正的判据是区分**数据段**与**执行段**：
段首是数据命令 → 段内都是数据（`grep "mavis agent delete" src` 放行）；
段首不是 → 段内每个 token 都是命令候选（`exec`、`taskset`、以及将来任何包装器自动覆盖）。

这条已经写进契约 S5 第 9 条与 `references/scope.md`。

### 一、D-26 翻案：平台**会**为容器调用派发 PreToolUse，但**随会话而变**

上一轮写进契约 S3、`scope.md`、README 与 RT-04 的「平台不对 `run_code` 容器派发 PreToolUse」——**是错的**。
三次观测的调用形状完全相同（外层 `run_code` 装一段纯计算 + 一个危险字符串常量），结论却相反：

| 时间 | 会话 | 观测 |
|---|---|---|
| 10:22 | `mvs_b0accaba…`（日志探针） | 容器内 `read` **有**条目，外层 `run_code` **无**条目 |
| 14:29 | `mvs_20e67557…` | 外层 `run_code` 被复合层**当场 DENY**（拒绝原文逐字可查） |
| 15:10 | `mvs_355c229f…`（**金丝雀复测**） | 危险文本被 DENY，纯计算对照组放行 |

⇒ **派发是会话相关的运行时事实，不是平台性质。** 根因查实：已逐棵核对 67 棵 hook 缓存树 ——
`run_code` 是 **2026-11-10 08:19** 才进 PreToolUse matcher 的；11/9 物化的 60 棵树**全部**没有它，
11/10 08:11 之后物化的树**全部**有。**推断（未逐棵验证）**：matcher 取自会话绑定的缓存树，
所以老会话不派发、新会话派发 —— 这也正好解释了 README 里「新增匹配项只在新会话里生效」那条。

**处置不变，理由改对**：判定落在内层通道（尤其 bash）仍然是必须的 —— 但理由不再是
「平台不派发所以没办法」，而是「**派发不可靠，不能当唯一防线**」。
复合层从「预留防线 / 当前不生效」改称「**纵深防御的加成**」。

### 三、D-27：主动触发粗筛漏判（已修）

**症状**：粗筛只认名词化/书面说法（派工 / 组队 / 分工 / 验收 / 复盘），且 `prompt.length > 40`

### 四、v0.5.2：派工取消后的名额回收（D-28）

**症状**：派工被父会话 `task_stop` 取消（或子会话异常退出）时，**不触发 SubagentStop**。
名额回收的三条路全都覆盖不到：正常结束不覆盖、TTL 兜底要等满 2 小时、读时自愈同样以 TTL 为准。
于是这条记录一直占着并发名额（上限 6 个），表现为「机制突然不让我派工了」，
但报的是「在飞派工已达上限」，完全不指向真正原因。

**实测**：派工 `dsp_mwab22ks_4iccn9`（`sa-mechanism-fix`）被取消后，台账 `state` 停在 `active`，
父会话只能靠**一次性临时脚本**手工调 `markDispatchAborted` 才把名额拿回来。
`markDispatchAborted` 虽然已从 lib.mjs 导出，但**没有任何 CLI / 脚本 / 文档告诉调用方怎么用** ——
机制没有入口，纪律就落不了地。

**修法**：新增 `plugin/scripts/release-slot.mjs`（契约 S6.2 第 5 条）：

```powershell
node scripts/release-slot.mjs '{"dispatch_id":"dsp_xxx","reason":"parent_cancelled"}'
node scripts/release-slot.mjs '{"parent_session_id":"mvs_xxx"}'
```

只把 `active` 翻成 `aborted`，`done` / `aborted` 的记录一个字节都不动；
目标 id 不存在或台账读不出来时**报错退出**，不静默「假装释放成功」——
否则调用方以为名额放掉了，实际还占着。
常驻回归 `tests/dispatch-release-test.mjs`（20 条断言），回归从九套变十套，两份副本均 0 FAIL。

**顺手更正的一处长期错误**：hooks.json 实际是 **4 类事件 / 7 条规则**，
但「5 类」在思维导图、`context-flow.md`、`verification-v050.md`、缺陷台账四处传了一整轮，四处已统一改掉。

### 六、D-30：变异自检套件并发不安全（会假红）

`tests/d27-mut-test.mjs` 的 `copyPlugin()` 用固定临时目录名 + 先删后拷。
父会话与验收方同时跑全量回归时互相踩：本轮安装副本那份报了

—— 这三条是 **watchdog** 断言，与 D-27 判定毫无关系，正是被抹掉副本的受害者。

### 七、v0.5.3：主 agent 的管理层定位 + 独立验收 FAIL 的逐条修复

**用户要求**：对话开始的主 agent 尽可能作为管理层、不做苦力；并验证成员的互相关联性、上下文记忆共享性、
错题本持久性、成员持久性与可复用性，以及会不会因上下文/错题本混乱互相篡位。

**第一点怎么落地**：本机主 agent（内置 `mavis`）是**内置模板**，
`mavis agent update` 直接返回「Built-in Agent templates are immutable.」—— 提示词本身不可改
（原文备份在 `docs/audit/main-agent-system-prompt.before-2026-11-10.md`）。
真正能在「对话开始」注入到主 agent 的、已装且每次会话都生效的位置，是**插件的 SessionStart 注入**。
于是把这条定位写进注入，并落成契约 S12 + 回归断言：

- 「你的定位是管理层，不是干活的」：有专项成员 owns 就派工；没有但有方法论要求就先现场配置成员再派工；只有单点小改才直做。
- 分工边界：意图理解 / 拆解 / 组队 / 整合 / 给用户结论归主 agent；实现 / 批量取证 / 独立验收**不归**它。
- 成员记忆共享但隔离：发现串味（别人的教训进了别人的 brief、两个成员抢同一个 `owns`、有人改了别人的记录）按缺陷处理并改归属映射。
- 并把「不预置成员」与「不自己做专项活」**分开表述** —— 只写前者会被读成「有成员也别派、自己干」。

**独立验收（verifier）判 FAIL**，7 条发现已逐条修完（见 CHANGELOG 0.5.3 变更 2）。最值得记住的两条：

- **F1（FAIL 的直接原因）**：D-26 翻案时，契约 / scope.md / guard.mjs / 台账 / 错题本 / README 都改了，
  却漏了 `plugin/scripts/lib.mjs` 里**同一句**错误表述，还拿它当现行事实写进了注释。
  **翻案不能只改「被指出的那一处」** —— 同一句错误散落多个文件时，必须全仓 grep 同一措辞再逐个改。
- **F2**：README 给的命令用户照抄跑不通 —— PowerShell 的原生参数解析会吃掉 JSON 里的双引号。
