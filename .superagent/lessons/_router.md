# Router 自己的错题本

这是**编排层**的错题本（契约 S9），不是任何成员的。

## 什么时候往这里记

先回答一句：**这是成员的锅吗？**

- 是 → 写进成员的 `.superagent/lessons/<成员名>.md`（成员格式：现象 / 根因 / 规则 / 下次派工）。
- 否（Router 给错的 brief / 需求本身矛盾 / 派工口径与通道语义不符 / 环境不具备）→ 写进本文件。

成员错题本与本文件的分工是**互斥**的：同一件事只进其中一处。成员已经承认的那部分失误留在成员账上，
编排层该负的那部分责任留在本文件 —— 两者相加才是完整事实，把编排层的锅塞进成员账上，
既让成员背了不该背的锅，也让编排层的问题永远没人看见。

## 条目格式

按契约 **S1 的 7 字段模板**（S9 明确：Router 自己的错题本同样受 S1 约束），
**不是**成员错题本那套 4 字段格式：

```
### <前缀>-<两位序号>
- 触发条件：
- 影响：
- 复现步骤：
- 证据：
- 状态：已复现 | 推断
- 修法方向：
- 还需要什么：
```

## 编号命名空间

本文件前缀 **RT-**（Router）。理由：`D-` 留给父会话合并台账统一分配；
成员清单的前缀由成员自选（成员之间不得重名）。`RT-` 与两者都不冲突，
且**本文件自己声明命名空间** —— 这正是 RT-03 记的那条教训的正面做法。

同一份文件内编号从 01 递增，不跳号、不重号。

### RT-01
- 触发条件：派工 brief 的 SCOPE 行只列了一个具体文件（如 `plugin/scripts/record-gate.mjs`），而成员的工作需要读**同目录下的其它脚本**；brief 正文里又写了「整个目录可读」这类边界描述。
- 影响：成员读不到需要的文件，直接撞越界拦截。本轮有成员因此 40 分钟未交付。更糟的是 brief 的边界描述与真实通道语义不符：读放行按「scope 条目**所在目录树**」判定，写判定按「条目本身」精确命中，bash 的路径 token 另有识别规则 —— brief 说「整个目录可读」是半真话，比不说更危险，成员会据此以为能读而实际被拦。
- 复现步骤：1) 取一次只列单个文件的 SCOPE 派工；2) 在同一会话里检索同目录的另一个脚本（检索根写目录本身、不带尾斜杠）；3) 观察拦截文案「目标 plugin/scripts 不在白名单内（读操作允许范围为 scope 所在目录树）」；4) 同一目录改用带尾斜杠的检索根再试一次，放行；5) 同一会话 `bash` 写命令里的目录型 token 另行判定。三次结论各不相同，brief 只说了其中一种。
- 证据：本单执行过程中的直接观测：检索根写 `plugin/scripts` 被拦，写 `plugin/scripts/` 放行 —— 同目录两种结论（机制侧对应 D-22，lib.mjs 读模式未把目录本身算命中）。历史侧：`.superagent/lessons/sa-orchestration-audit.md` 记「反复撞越界拦截，40 分钟未能交付清单」，且该条自带的归因说明写明「SCOPE 未覆盖待审计文件是 Router 派工侧的边界问题（不记在成员账上）」。`docs/audit/verification.md` V-15 记载同样的活体复现（带尾斜杠放行、不带则拦）。
- 状态：已复现
- 修法方向：派工前逐条做「读得到吗」自检 —— 把成员要读的每一个路径列出来，确认它落在某个 scope 条目的**所在目录树**内（不是落在那个文件本身）；要授权一个目录，SCOPE 必须写成以 `/` 结尾的目录条目；brief 里的边界描述必须与契约 S2/S3 的通道语义逐字一致，不写「整个目录可读」这种半真话。
- 还需要什么：需要契约明确「目录条目」在读、写、bash 三条通道上的判定是否一致 —— 当前 S2/S3 的表述在「bare 目录」上与 lib.mjs 的实际行为不一致（D-22 由机制 owner 修，契约表述是否要跟着改，本单无权定）。

### RT-02
- 触发条件：Router 给不同成员手写 brief 时，条目模板靠自己复述或凭记忆写，没有从单一事实源引用。
- 影响：两名 worker 拿到 6 字段模板、verifier 拿到 7 字段模板，产出格式天然不一致；验收反过来判产出「字段模板不一致」——**产出被判不合格的根因在派工方，不在成员**。模板一旦分叉，「缺第 7 字段」这类检查也无法机械化。
- 复现步骤：1) 取出本轮两份 worker brief 与一份 verifier brief 的条目模板；2) 逐字段对比三者；3) 看验收结论里「字段模板不一致」的判定落点。
- 证据：`docs/audit/verification.md` 第四节「差异 1（第 7 字段不一致，不通过）」原文：「runtime-guards.md 的 2 条推断条目各带独立字段『- 还需要什么：』（共 2 处）；context-flow.md 的 8 条里 0 处有该字段，其 2 条推断条目把『还需要什么确认』塞进『修法方向』段末」；同一报告的 VERDICT 段把「为两份清单补回独立『还需要什么』字段，或契约降为 6 字段并同步」列为转为 PASS 的必要条件之一。
- 状态：已复现
- 修法方向：brief 里只写模板出处（条目模板见 `references/contract.md` 第一节），不抄字段。派工方在 brief 里**引用**模板而不是**复述**模板 —— 复述即分叉。派工前的自检加一条：brief 里出现字段清单本身就是错误，出现模板出处引用才是对的。
- 还需要什么：需要一条可执行的检查把「brief 复述了字段清单」变成报错 —— 目前 brief 是自然语言，guard 只看路径不看内容，这条约定没有任何机制会在漏写时报警。

### RT-03
- 触发条件：两份成员清单各自从 `F-01` 开始编号，彼此不知道对方用了哪一段号。
- 影响：合并必撞 8 组号（`F-01`~ `F-08`），且是同号不同义；合并时只能靠读正文人工去重，去重过程本身不可靠、不可复核。编号冲突让「缺陷台账」这种要长期维护的资产在第一次合并就带上歧义。
- 复现步骤：1) 取出两份清单的编号列；2) 求交集；3) 数出撞号组数；4) 试着按编号引用其中一条，看是否唯一。
- 证据：`docs/audit/verification.md` 第三节「编号冲突」：「F-01 至 F-08 共 8 个编号在两份清单中各指一条不同缺陷……两名成员互不通信、看不到对方编号，无人可能自行避让」，并在结论中把「为两份清单分配全局唯一编号」列为转为 PASS 的必要条件之一。契约侧已收敛出 S1 的「编号命名空间」表（成员产出用自选前缀、合并台账用 `D-`），但表只规定了「合并时怎么办」，没有规定「产出前怎么办」。
- 状态：已复现
- 修法方向：编号在**派工时**分配，不在产出时分配 —— brief 里直接写明本单的编号前缀与起始号（例如「本单前缀 RG-，起始 01」），成员的清单从 brief 给的号开始写；合并台账的 `D-` 号仍由父会话在合并时统一分配。同一份文件内从 01 递增、不跳号不重号这条硬规则继续保留。
- 还需要什么：需要把「brief 必须写明本单的编号前缀与起始号」变成可检查项 —— 目前它只是约定，没有任何机制会在 brief 漏写时报警；同样，「brief 复述字段模板」也没有检查（见 RT-02）。

### RT-04
- 触发条件：用「合成 PreToolUse 载荷直接驱动 guard 脚本」的方式验收「某工具会不会被拦」，并据此认为该工具在真实运行时受保护。
- 影响：**把「判定逻辑正确」误当成「平台会触发它」**。当时的验收结论写的是「改判条件①满足」，但支撑它的只有合成载荷（判定逻辑确实对，DENY），**没有一条真实运行时的触发记录**。后果是整层防护的维护状态被误标：先是被写成「平台根本不派发 → 整层防护是空的」（这个结论本身后来也被证伪），再顺带掩盖了真正的洞 —— bash 通道成了账号级不可逆操作的旁路。
- 复现步骤（阴性样本）：1) 给活动 hook 树的 `scripts/guard.mjs` 装一行临时日志（把 `readStdin()` 收到的原始载荷追加到日志），同步到安装副本（运行时从安装副本物化新树）；2) 开新子会话，做一次外层 `run_code` 调用与一次容器内 `read` 调用；3) 读日志 —— 只有 `read` 有条目，外层 `run_code` 没有任何条目；4) 全库统计 tool_calls：1640 次 `run_code` 中护栏直接拒答 **0** 次，同期内层被拒 153 次，而 `bash` 直接被拒 114 次、`read` 42 次；5) 把探针还原（三处副本 sha256 回到 `7f4e24732fa3`）。**金丝雀样本（补做，才把结论翻回来）**：新开子会话，外层 `run_code` 的代码里放一个危险字符串常量 → 实测**被拒**（拒绝原文只可能由 `tool_name === 'run_code'` 分支产生）；纯计算对照组放行。
- 证据：探针日志 `C:/Users/yang2/AppData/Local/Temp/sar-hook-log.jsonl` 条目分布 = write 1 / bash 2 / read 1，**无 run_code**（其中 read 条目来自探针子会话的容器内子调用，证明日志探针在该会话内正常工作）—— 阴性观察本身可信；全库统计脚本 `C:/Users/yang2/AppData/Local/Temp/sar-blocked-scan3.py`。反证：运行时 transcript `01895dd02f0202496fb64cc7e8b9cccb.compatible.jsonl`（会话 `mvs_20e67557…`，2026-11-10T06:29:58Z）与金丝雀复测会话 `mvs_355c229f…`（2026-11-10 15:10）的 `run_code` 工具结果里都带着**本插件自己的**拒绝原文，该原文只可能由 `guard.mjs` 的 `tool_name === 'run_code'` 分支产生 ⇒ 平台**确实**派发了容器事件。缓存树逐棵核对：`run_code` 于 2026-11-10 08:19 才进 matcher，11/9 物化的 60 棵树全部没有它，11/10 08:11 之后物化的树全部有。台账侧记为 D-26；独立验收报告 `docs/audit/verification-v050-recheck.md` 第五节残留项 1 记的是同一个现象（当时未能证实）。
- 状态：已复现；**结论已被本轮证伪并更正**（见 D-26）
- 修法方向：验收里把**「机制对不对」与「链路通不通」分成两问**，各要各的证据 —— 前者用合成载荷，后者只能用真实会话 + 可观测的触发记录。凡是「某工具受不受保护」的结论，必须有一条**该工具在真实运行时的触发记录**（被拦或放行都要有），不能只有合成载荷。**再给 Router 自己加一条更狠的：一次阴性观察也不能写成平台事实** —— 阴性样本同样需要**金丝雀对照**（同一形状的阳性样本会不会被拦）、**时间戳**与**会话标识**三件套，缺一件就只能写成「该会话如此」，不能写成「平台如此」。本条教训的两次翻车是同一条链：先是「合成载荷=链路通」，再是「一次阴性=平台不变」。
- 还需要什么：需要平台侧确认 `run_code` 这类容器调用的派发规则（按会话绑定到哪棵 hook 缓存树？老树 matcher 里没有 `run_code` 是不是原因？），以及载荷里的代码字段名（当前机制读 `tool_input.code` / `program` / `script`）。这决定复合层在老会话里到底有没有保护 —— 本轮只确认了「绑定新树的会话会派发」。

### RT-05
- 触发条件：用一次**阴性观察**（某件事「没发生」）加上一个**没有阳性对照的 0/N 统计**，推出一个「机制不存在 / 平台如此」的平台级结论，并把它写进契约、README 与错题本。
- 影响：把一次会话级观测**升级成了平台性质**，而且写进了会被人长期引用的文档里 —— 读者据此停止复核，整层防护的维护状态被误标。本轮实例：10:22 的日志探针显示「只有内层 `read` 有条目、外层 `run_code` 无条目」，全库统计「1640 次 run_code 调用 0 次被护栏直接拒答」，于是写下「平台不对容器调用派发 PreToolUse，复合层是预留防线」。金丝雀复测（2026-11-10 15:10）证明平台**确实派发**并当场 DENY；14:29 独立复现一次。**阴性样本本身没错，错的是推广。**

- 修法方向：**凡是「X 没发生」的结论，配金丝雀（同一形状的阳性对照）、时间戳、会话/环境标识三件套，缺一件只能写成「该次如此」。** 报告里出现 0/N 时必须能指出「这 N 个里哪几个本该命中」，否则 N 再大也是零信息。另加一条文档纪律：**平台行为要写成「可复现 + 什么条件下会变」，不要写成永恒的平台事实** —— 会话相关、缓存相关、租约相关的行为尤其如此。

### RT-06
- 触发条件：给同一专项成员派**连续**的工作时，每次都新开一个子会话（而不是追加到它已有的会话）。
- 影响：**上下文预算被重复读仓库吃掉**。每新开一个子会话，那位成员都要重新读一遍它需要读的东西（方法论、契约、台账、相关脚本、既有报告）；父会话还要重新写一遍「这个人知道什么、不知道什么」的铺垫；窗口列表越堆越多。2026-11-10 实测：sa-mechanism-fix 一个专项开了 **13** 个会话，而真正的不同任务只有两三件。
- 复现步骤：1) 同一专项连续派三单（改同一族缺陷）；2) 每次用 `task` 新开子会话；3) 数该专项的会话数 —— 会话数 ≈ 派工单数，而不是远小于派工单数。
- 证据：用户两次明确指出（「每次都开新的窗口会造成很大的上下文浪费……每一次那个成员都要重新读一整个仓库」「成员已经配好了，这个成员的窗口就这么多，不需要再重新开新的窗口了……每一个成员都知道自己有改过什么、没改过什么，就不用说给他一大段规则告诉他上衣改了都改了什么」）；2026-11-10 实测 `task_append` 唤起已结束的子会话（mode: activated）后，该会话准确复述了自己上一轮改过的四层判定、707 条断言与 5 个变异体 —— **上下文完整保留**。
- 状态：已复现
- 修法方向：派工前先查「该成员是否已有会话，其边界覆盖本单要动的路径」——覆盖就追加，不覆盖才新开；把可复用会话登记成一张表（哪个会话、已加载了什么、边界是什么），不要靠记忆。已落：契约 S4.5、`.superagent/STATUS.md` 的父会话作业规则、`dispatch.mjs` 派工回执的复用提示。
- 还需要什么：复用会话的**边界是冻结的**（派工时定死，已结束的派工不能再扩权）—— 所以「边界不同的活仍需新开」，这不是复用失效，是边界设计的必然结果。

### RT-07
- 触发条件：往一个**已结束**的子会话追加指令时，追加内容里写了一个**不合规的 SCOPE 行**（如「本单 SCOPE：反引号包着的路径、顿号分隔」这种形式）。
- 影响：该子会话**整轮的所有工具调用被护栏拒绝**（读、写、bash 全被拒，连不带任何路径的调用也拒）—— 报错是「brief 里找到了 SCOPE 行，但条目一个都解析不出来」。成员既写不了文件、也读不了契约，最后只能把报告正文以文字交回父会话。
- 复现步骤：1) 对一个已结束的子会话 `task_append`；2) 追加内容里写一个顿号分隔、带反引号的 SCOPE 行；3) 该子会话下一轮的任意工具调用都被拒；4) 改成合规格式（`SCOPE: a.ts, b.ts`，逗号分隔、无反引号、行首 SCOPE）后恢复正常。
- 证据：2026-11-10 D-75 那单的接手实例实测（连续 4 次被拒，含一条完全无路径的 `Write-Output`）；父会话侧复现 `extractScopeDetail('SCOPE: plugin/scripts/lib.mjs, ...')` 解析出 5 条正常条目 ⇒ 解析器没问题，问题在**格式**。
- 状态：已复现
- 修法方向：追加内容里的 SCOPE 会**参与边界解析** ⇒ 追加时要么**根本不写 SCOPE**（原有边界会继承），要么写成协议格式。已落契约 S4.5 的专节。
- 还需要什么：无。

### RT-08
- 触发条件：清理一个**带尾随空格**的重复目录时，用 `mavis-trash.cmd <路径>`（路径末尾多一个空格）。
- 影响：`mavis-trash.cmd` 用 %* 传参，cmd 把引号内路径的**尾随空格 trim 掉** ⇒ 删除目标变成了**正常的那个目录** ⇒ 派工台账文件 dispatches.json（39 条派工 + 41 条 binding + 61 条待审请求）被移走。台账空了 ⇒「记录丢了 ⇒ 视同没有在飞派工」⇒ **冲突检测与名额检测全盲**。
- 复现步骤：1) Windows 上建一个末尾带空格的同名目录与正常目录；2) `mavis-trash.cmd` 传前者；3) 后者的内容被移走（回收站里能看到对应的回收项）。
- 证据：2026-11-10 实测（用 cmd 的 set 变量喂环境变量时 cmd 把尾随空格带进变量值，意外造出第二个目录；随后清理时误删真台账）。已从回收站完整恢复并用 node 校验（39/41/61，计数与原值一致）；同时修了机制侧的判定（isPluginOwnDataDir 现在逐字比对目录名，台账 D-82 + 5 条专属断言）。
- 状态：已复现
- 修法方向：路径尾部空白是**路径身份的一部分**，任何按路径做删除/查找的操作都不能先 trim。工具侧：`mavis-trash.cmd` 的 %* 传参对尾随空格路径不可靠（会 trim、会删错目录）—— 父会话用「直接调 mavis-trash.js」绕过，但**根治要宿主侧修**。
- 还需要什么：宿主侧 `mavis-trash.cmd` 应改用引号传参或 stdin，否则尾随空格路径永远危险。
