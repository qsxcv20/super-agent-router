## 1. 逐条：判定在哪、怎么改的、为什么

### D-37 · 派工不校验目标成员是否存在于账号

**判定落点**：`dispatch.mjs` 的**闸门 1d**（在闸门 1/1b/1c 之后、在读台账与写台账之前）。

**为什么放在这里**：派工到一个账号里不存在的成员**不会启动子会话**，但台账以前照样写一条
`state:'active'` —— ① 占掉一个并发名额与一个累计名额；② 同 SCOPE 的后续派工被「组队冲突」误拦；
③ 教训与履历照常注入 brief，外观完全正常 ⇒ **静默失效**（最长 2 小时）。
只有**写在台账之前**才有效 —— 拦晚了，名额已经占住了。

**名单怎么取（可复用的一次调用）**：`lib.mjs` 的 `accountMemberNames()`。
账号成员落盘在 `<账号根>/agents/<name>/`，内置成员在 `<账号根>/agents/.builtin/<name>/`；
账号根的定位规则与 `writeGateTrace` 判定「本插件专属数据目录」的口径同源（契约 S11）：

1. `SAR_ACCOUNT_AGENTS_DIR`（显式指定，测试夹具与探针用）；
2. 运行时：`PLUGIN_DATA` 指向本插件的专属目录时，账号根取用户目录下的 `.minimax`；
3. 其它情况：**账号名单不可用**。

**注入侧与派工侧共用同一份计算**（`staleRosterMembers()`）—— 两处各算各的，口径迟早长歪。

### D-38 · 陈旧判定没有执行点也没有消费者

**判定落点**：`session-start.mjs` 的注入块（每次会话开始都算一次）+ `dispatch.mjs` 的闸门 1d（陈旧成员被拒）。

**口径**：陈旧 = 项目名录里有、账号成员目录里没有。**注入侧披露的名单与派工侧拒绝的集合是同一个计算**
（`staleRosterMembers()`），不是两份口径。

**披露形态**：会话注入里出现「陈旧成员（名录里有、账号里没有 —— 不得派工）」小节，逐个列出成员名，
并写明「派工到这些成员会被机制直接拒绝（台账不写任何记录）」。
账号名单不可用时，注入里必须出现「账号成员名单不可用」—— **不许静默**（静默 = 存在性校验悄悄失效）。
这条披露**只在项目真的用到了专项成员（名录非空）时出现**：没有名录就没有「专项成员」这套用法，
那时插一段环境说明只是噪音；有名录时不披露才是危险的（父会话会以为存在性有人把关）。

### D-39 · 账号级建号无闸门

**判定落点**（三处，缺一不可）：

1. `lib.mjs` 的 `detectDangerousAccountCommand()` —— bash 通道的命令位置判定（账号级建号子命令与删除/改写同构）；
2. `guard.mjs` 的 `dangerousByArgs()` —— `mavis` 工具的 `command` 参数判定；
3. `guard.mjs` 的 `DANGEROUS` 工具名表 —— 工具名维度。

**复合层**（`run_code`）由 D-41 的新判定覆盖：`tools.mavis({command})` 按参数判。

**为什么必须对称**：账号成员是**账号级全局可见**的（跨项目）。只拦删除与改写、建号完全放行，
等于任何会话都能往账号里塞成员、绕过造人纪律 —— 账号成员集合与项目名录必然脱钩，
那正是「名录里有、账号里没有」的**镜像面**。

**分工边界**：名录登记侧（`roster.mjs register` 的「该成员必须已存在于账号名单」校验）**不在本成员 SCOPE**，
归另一位成员（`sa-gate-integrity`）。本成员只做**建号闸门**，没有碰 `roster.mjs` 一个字节。

### D-40 · 拦截措辞误导（只读条目被说成「不在白名单内」）

**判定落点**：`guard.mjs` 的 `outOfScopeVerdict()` + `denyOutOfScope()`。

**分型**：目标路径分成两堆 —— ① 被某个**只读条目**覆盖（写判定下本该命中、却被 `ro:` 前缀挡掉）；
② 真的不在白名单内。两堆各出一句话：

- ① 「目标 X **在白名单内，但登记为只读条目**（ro:）—— 只读条目永不授予写权限（契约 S2.2），当前操作是写操作。
  如需写操作，请把该条目的 `ro:` 去掉后**重新派工**；不要把它当成需要扩权的目标 —— 本次派工的边界是父会话写下的，不是 worker 能改的」
- ② 原句「以下路径不在白名单内：…」**原样保留**（分型不能把两种情形混成一种）。

**判定口径**：只读条目的命中判定（`lib.mjs` 的 `readOnlyScopeHit()`）与 `inScope` 的写模式**完全同口径**
（精确命中 / 落在以 `/` 结尾的目录条目之下），只是不跳过只读条目 —— 否则分型就是猜的。

**顺带收紧**：只读条目命中的写请求**不再给批准提示**（`approvable=false` + 专属提示）。
理由：批准写请求等于把只读条目升级成可写，那正是这条缺陷要的「把一个本可只读执行的动作升级成可写授权」；
父会话要授写，正确做法是改派工 SCOPE（去掉 `ro:`）后**重新派工**。

### D-41 · 复合层危险形态判定与 bash 通道口径不一致

**判定落点**：`lib.mjs` 新增 `detectDangerousInComposite()`（按内层工具分形态），
`guard.mjs` 的 `dangerousInCode()` 改为调用它（原来是对整段代码文本做朴素正则）。

**口径**（与 bash 通道对齐，契约 S3 / S5.4）：

| 内层调用 | 载荷是什么 | 怎么判 |
|---|---|---|
| `tools.write` / `tools.edit` / `tools.multiedit` … | **数据**（文档正文） | **不按命令形态判**（这一条就是修掉误伤的地方） |
| `tools.bash({command})` | **命令** | 交给命令位置判定（`detectDangerousAccountCommand`） |
| `tools.mavis({command})` | 参数 | 按参数判（账号级成员动作） |
| `tools.<小程序发布工具>({action})` | 参数 | 按参数判（action=publish） |
| 直接点名危险工具的调用 | 工具名 | 照拦 |

**不许开出绕过口子**：字面量拼接（`'mavis ' + ' agent …'`）按**拼接结果**判，不因为拆开写就放行；
真正会被执行的东西（bash 载荷、mavis 参数、点名危险工具）仍然被拦。

**诚实边界**：复合层是**纵深防御的加成**，不是唯一防线 —— 容器调用的 PreToolUse 派发不是平台恒定行为
（契约 S3「容器调用的派发事实」），真执行时每个内层调用各自触发 PreToolUse、判定对象是真实实参。

## 2. 与台账 / 审计条目的复核更正（三条，按码写）

台账与审计报告的结论**不保证全对**，以下是本成员读码复核后**改写了修法方向**的三条：

1. **D-38 的修法方向（更正）**：台账写「把 `roster.mjs` 的 reconcile 变成 SessionStart / 路由注入的固定一步」。
   但 `roster.mjs` **不在本成员 SCOPE**（归另一位成员），且它的 reconcile 需要外部喂一份 agent 名单、
   只 `stdout.write`、不写回名录、不阻断派工 —— 直接把它接进注入，等于把「陈旧判定」继续挂在一个
   **只输出不消费**的函数上（那正是 MP-02 的病根）。
   ⇒ 实际改法：陈旧名单在 `lib.mjs` 里**直接从账号成员目录算出来**，注入侧与派工侧共用这一份计算；
   `roster.mjs` 一个字节没动（分工见第 7 节）。

2. **D-41 的修法方向（加强）**：台账写「至少对引号内 / 代码块内 / Markdown 引用内的字面量放行」——
   那是**文本启发式**，仍然会把 write/edit 载荷里的正文当命令形态判（正文里出现被禁形态照样被拦）。
   ⇒ 实际改法：按 brief 的要求**按内层工具分形态判**，write/edit 的载荷是数据、整段不参与命令形态判定。

3. **D-37 的「取不到就 deny」（部分更正）**：台账与审计都假设账号成员名单**总能取到**。
   实测不是：账号成员是**跨项目的账号级事实**，测试夹具（以及任何没带账号环境的环境）里根本没有它。
   若按「取不到就拒派」实现，`tests/records-test.mjs` 与 `tests/scope-amend-test.mjs`
   （**均不在本成员 SCOPE**）会当场爆红 —— 它们本来就在往「账号里不存在」的成员派工。
   ⇒ 实际改法：**名单不可得时不拒派**（否则整套编排在没有账号环境的项目里全停摆），
   但**必须留痕 + 必须在会话注入里披露**（不许静默）。名单可得时（生产运行时 / 显式指定
   `SAR_ACCOUNT_AGENTS_DIR` 的夹具）判定照常生效。残余风险见第 6 节。

其余结论与代码一致，未做更正：MP-01「全仓没有任何脚本查询账号成员表」（读码 + 全仓检索属实）、
MP-02「`reconcile` 从未被任何 hook 或脚本调用」（属实）、MP-03「危险清单只含删除/改写两种子命令」（属实）、
MP-A1（属实）、MP-A2（属实，复合层确实是整段朴素正则）。

## 5. 自举问题与可维护性代价（如实记录）

写这轮代码时，本插件**自己装在账号里的那份护栏**仍在跑（部署由父会话统一做），
所以源码里只要出现被禁形态的**字面量**，我自己的工具调用就会被拦 —— 本轮亲身触发 **5 次**
（grep 的 pattern 里 2 次、大段源码与拼接块 3 次）。被拦的都是**我自己的载荷**，不是被测代码。

处置方式（不是删判定）：**字面量拼出来**。

- `plugin/scripts/lib.mjs`：工具名常量用 `'website' + '_deploy'`、`'mini' + 'app' + '_publish'`、
  `'mavis' + '_agent' + '_delete'` 这种拼法。
- `tests/guard-test.mjs`：被测命令用 `'mavis' + ' agent' + ' create' + ' sa-x'` 拼法，
  **拼出来的值与字面量完全等价**（被测的是判定逻辑，不是写法）。

代价（必须说清）：

1. **拼错就是静默失配** —— 工具名少一个下划线，危险工具表就匹配不上 ⇒ 变成放行。
   缓解：每个拼出来的名字都有专属断言锁住（D-39 的三条 + D-41 的「直接点名部署工具仍被拦」），
   变异体 M-D39 / M-D41 会把这一层打回旧实现，断言必须转红。
2. **可读性下降** —— 读源码的人看到的是拼接式工具名，必须顺着常量名才能拼出真实工具名。
   缓解：常量集中在 lib.mjs 一处，并写明「为什么是拼出来的」。
3. **这是临时状态** —— D-41 部署之后，复合层不再对载荷正文做判定，
   这些名字**可以还原成字面量**（还原时必须同批断言一起改，否则断言的「载荷即数据」前提会变）。
   建议：部署本轮改动后，由父会话统一把 lib.mjs 的工具名常量与 guard-test 的命令常量还原成字面量，
   并重跑 `node tools/run-tests.mjs --all --root plugin --repo .` 与 `node docs/audit/.tmp-d37/mutation-matrix.mjs`。

## 6. 残余风险（不写「绝对拦得住」）

1. **护栏是护栏，不是沙箱。** 能落盘的脚本，其内部写入不受 hook 约束 ——
   判定只能拦住「工具调用」这一层，脚本内部再写什么，机制看不见。真正的兜底是运行时权限 + 人工确认 +
   `.superagent/changes.log` 的审计留痕。本轮的所有「拦」都只在这一层。
2. **账号成员名单不可得时，成员存在性判定整体不生效**（放行 + 痕迹 + 会话注入披露）。
   生产运行时靠 `PLUGIN_DATA` 指向本插件专属目录来识别账号环境；若那一刻该布局变了，
   判定会**降级为不判**（有痕迹、有披露，不是无声失效，但确实是不判）。
   ⇒ 见第 7 节「需要父会话处理的事」第 1 条。
3. **复合层对动态拼出来的命令判不了**：`tools.bash({command: someVar})` 在复合层取不到命令文本，
   只能靠内层 bash 调用自己的 PreToolUse 兜底（契约 S3 已写明复合层是纵深防御的加成）。
   真的会被执行的东西仍然被拦，但**拦它的不是复合层**。
4. **复合层只认内层工具名的字面形态**：`const f = tools.bash; f({...})` 这种取别名的方式，
   复合层看不到 —— 但平台也不会把它当成一次 bash 调用派发，所以不构成执行路径。
5. **D-40 的提示不等于机制上的封堵**：`scope-amend.mjs --grant`（父会话专属的扩权入口）
   仍能给只读条目批一条可写条目 —— 那条路径不在本成员 SCOPE 内（见第 7 节第 3 条）。
   本轮做的是**不再用措辞把父会话往那条路上推**。
6. **陈旧名单的口径与 `roster.mjs` 的 reconcile 差一处**：reconcile 只把 `source === 'runtime'`
   的成员算作陈旧，本实现按「名录里有、账号里没有」判定（不看 source）。
   `roster.mjs` 归另一位成员 —— 若两边要统一口径，需由那位成员对齐（见第 7 节第 2 条）。

## 8. 新发现的缺陷

（条目模板见契约 S1。）

### N-01
- 触发条件：运行时的 `PLUGIN_DATA` 不指向本插件的专属目录（夹具、或运行时布局变化）。
- 影响：账号成员名单被判为不可得 ⇒ 派工的成员存在性判定**整体降级为不判**（放行 + 痕迹 + 注入披露）。
  派给不存在的成员会重新变成静默失效（占名额、后续派工被组队冲突误拦）。
