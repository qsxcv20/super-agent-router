# D-73 修复报告：账号成员名单不可得时的降级口径（不占名额、不堵后续派工、看得见）

> 缺陷条目出处：docs/audit/defect-ledger.md 的 **D-73**（本报告不复述缺陷正文）。
> 条目模板出处：plugin/skills/super-agent-router/references/contract.md 第一节（S1）。
> 取舍来源：同文件 S6（派工台账口径）与 D-37 那轮已定的取舍（见 2.1）。
> 本单与 D-77 同属一条机制链：**D-73 的新台账字段走 D-77 修好的统一写入口**。

## 1. 缺陷与影响（摘要）

运行时 PLUGIN_DATA 不指向本插件的专属目录时，账号成员名单**读不出来**（不是「空名单」）。
改前 dispatch.mjs 的闸门 1d 在这种情形下只写一条痕迹就**放行** ⇒
派给账号里不存在的成员 ⇒ 子会话不会启动，但台账照样写一条 state:'active' ⇒
① 占掉一个并发名额与一个累计名额；② 同 SCOPE 的后续派工被「组队冲突」误拦；
③ 教训与履历照常注入 brief ⇒ 外观完全正常 ⇒ **静默失效**（最长 DISPATCH_TTL_MS = 2 小时）。

## 2. 取舍与口径

### 2.1 D-37 那轮已定的取舍（本单**不推翻**）

账号成员是**账号级事实**，没有账号环境的项目（测试夹具）根本没有这份名单 ——
据此拒派等于让整套编排在没有账号环境的项目里全停摆，连正常派工都发不出去。
**降级路径仍然放行，不改成拒派。**

### 2.2 本单修的是「降级本身」的三件事

> 降级路径必须把「我无法核验」这件事，变成一件**不会悄悄吃掉名额、也不会悄悄堵死后续派工**的事。

### 2.3 我给出的口径（请父会话裁决）

口径分两层，缺一不可：

**第一层：降级口径什么时候成立。**

    降级口径成立 = 账号成员名单不可得
                且 项目**确实在用专项成员**（名录读得到且非空，或名录读不出来）

**为什么要有「项目在用专项成员」这一条**（这是本单最需要裁决的一处取舍）：

- 项目压根没用过专项成员时（没有 roster.json，或名录为空），
  「派工目标是不是专项成员」这件事**不存在** ⇒ 降级口径不适用。
- 若不设这一条，**所有**没有账号名单的环境（包括全部测试夹具）里的
  组队冲突闸门与并发名额上限会**整体失效** ——
  实测：chain-test 的 5 条既有断言（scope 重叠被拒 / 目录 scope 重叠被拒 /
  单会话派工数超限被拒 / 超限提示 / 跨会话写冲突被拒）当场全红。
  这些断言测的正是冲突闸门本身，不该被「名单不可得」这条降级路径关掉。
- 代价（诚实边界，见 N-53）：**没有专项成员名录的项目里，降级路径仍会占名额** ——
  即「派给不存在的成员占名额、堵后续派工」在那类项目里**没有**被本单修掉。

**第二层：降级口径成立时，名录内与名录外的口径不同。**

| 成员 | 存在性口径 | 派工 | 占名额 | 参与 SCOPE 冲突判定 | 痕迹与披露 |
|---|---|---|---|---|---|
| **名录内**（roster_declared） | 项目自己声明存在的 | 照常 | 是 | 是 | 痕迹 + 注入里说明「按项目声明照常派工」 |
| **名录外**（unverified） | 既没核验过、也没登记过 | 照常放行（不拒派） | **否** | **否** | 痕迹（更响）+ 注入里说明「完全无法确认能否启动子会话」 |
| 正常路径（account_verified） | 账号名单可得且核验通过 | 照常 | 是 | 是 | — |

**名录内为什么照常派工**：名录是项目级可审计资产，名录里登记过的成员
**至少是项目自己声明存在的** ⇒ 名录是项目自己的承诺。
**名录外为什么降级**：连项目都没声明它存在，且账号侧不可核验 ⇒
它的存在性完全没核验过，子会话可能根本没起来。

**注意「不占名额」对两类降级记录都成立吗** —— 不成立：
名录内成员**照常占名额、照常参与冲突判定**（它是项目声明存在的真派工）；
只有**名录外**的成员进入「不占名额、不参与冲突判定」的降级口径。
这正是 brief 里「名录内照常派工、名录外走降级路径」那条口径的落地。

### 2.4 降级「父会话看得见」的三个载体

1. **台账记录字段**：member_existence（account_verified / roster_declared / unverified）
   与 degraded（true / false）—— 父会话查台账即见；
2. **痕迹**：gate-trace.jsonl 里的 account_member_list_unavailable 一条，带
   session id、目标成员、存在性口径、降级与否、名录状态、原因；
3. **派工注入**：降级口径成立时，派工输出里有一段【降级提示】，
   说明「本次派工没有核验目标成员是否存在」「该记录不占名额、不参与冲突判定」。

## 6. 残余风险（诚实边界）

1. **两个降级派工之间不再互相挡**：降级派工不参与冲突判定 ⇒
   两个名录外的降级派工若 SCOPE 相同，会**同时**写同一处。
   这是 D-73 要求的直接代价（否则同 SCOPE 的后续派工会被误拦）。
   ⇒ 见 N-52。
2. **没有专项成员名录的项目里，降级路径仍占名额**：
   「派给不存在的成员占名额、堵后续派工」在那类项目里没有被修掉
   （口径收窄的代价，见 2.3 与 N-53）。
3. **降级记录仍留在台账里**（state:active + degraded:true）：
   这是为了可审计（父会话查得到），但**看台账的人若只数 state:active 会数多**。
   ⇒ 名额口径以 lib.mjs 的 countsAgainstSlots() 为准。
4. **降级窗口内的真实并发数可能超过上限**：降级派工不占名额 ⇒ 并发上限在降级窗口内偏松。
   代价换来的是「降级派工不吃掉名额、也不堵后续派工」。
5. **台账新字段必须有读取点**（契约 S6.3「不许有只写不读的字段」）：
   degraded 由 countsAgainstSlots() 读；member_existence 由 dispatch 的同名键覆盖分支
   读取旧值（口径是首次登记时的事实，不许被重放改写）⇒ 两个字段都有读取点。

## 8. 新发现的缺陷（编号从 N-51 起）

条目模板见契约第一节（S1）。

### N-51
- 触发条件：把「降级路径」实现成「名单不可得就一律不占名额、不参与冲突判定」。
- 影响：**所有**没有账号名单的环境里，组队冲突闸门与并发名额上限**整体失效** ——
  包括全部测试夹具。两个 worker 可以被派去写同一处而无人拦，
  单会话派工数上限形同虚设。
- 复现步骤：按上述实现后跑 chain-test ⇒
  「scope 重叠的派工被拒」「目录 scope 与其下文件重叠被拒」「单会话派工数超限被拒」
  「超限提示指向派工上限」「跨会话的写冲突被拒」5 条当场全红。
- 证据：本单实施过程中的实测（改前全量回归：chain-test exit=1 pass=65 fail=5）。
- 状态：已复现
- 修法方向：降级口径要有**适用范围**，不能只看「名单不可得」一个条件 ——
  「派工目标是不是专项成员」这件事由**项目名录**定义，没有名录就没有这一层。
  ⇒ 见 fix-d73.md §2.3 的两层口径。
- 还需要什么：需要父会话裁决该口径是否作为契约条款写进 S6。

### N-52
- 触发条件：降级派工不参与冲突判定（2.3 第二层）。
- 影响：两个**名录外**的降级派工若 SCOPE 相同，会同时写同一处 ⇒
  互相覆盖，验收无从判断谁的改动生效 —— 正是「组队冲突」闸门本来要防的事。
  这一条与 D-77 是不同的问题：D-77 修的是**台账**不丢记录，本条是**工作区文件**被覆盖。
- 复现步骤：降级环境（有名录 + 名单不可得）下派两条同 SCOPE 的名录外派工 ⇒
