## 2. 故障注入钩子（仅测试可见，默认关闭）

### 2.1 为什么需要它

D-59（rename 覆盖被占用文件报 EPERM）、D-61（Windows 抢锁报 EPERM）在真实环境里是**偶发**的。
靠真实并发去撞，撞到与否看运气 —— 这正是上一轮 D-61「一次 2 红、另一次 0 红」的来源。
断言要**确定性**，就得能**指定**错误，而不是等它自己冒出来。

### 2.2 开关与语义（实现见 `plugin/scripts/lessons.mjs` 的「故障注入钩子」段）

| 环境变量 | 作用 | 默认 |
|---|---|---|
| `SAR_FAULT_INJECT` | 逗号分隔的 token 列表，**不设即完全关闭** | 未设置 |
| `SAR_FAULT_RUN` | 批次号：值一变，计数归零（同一组 token 在同一批次里只触发 N 次） | 空串 |

| token | 作用点 | 语义 |
|---|---|---|
| `rename-eperm[:N]` | `writeFileLocked` 里的 `fs.renameSync` | 前 N 次抛 `EPERM`（Windows 上目标文件被占用时的真实错误码）。默认 N=1 |
| `lock-eperm[:N]` | `withFileLock` 里的 `fs.openSync(lock,'wx')` | 前 N 次抛 `EPERM`（Windows ERROR_SHARING_VIOLATION 的 Node 映射）。默认 N=1 |
| `verify-fail` | rename 成功后、落盘回读之前 | 把目标文件改写成一份**过期快照**（不含前序条目），模拟另一个写入方用旧快照覆盖 ⇒ 回读校验必然失败 |

**怎么关掉**：不设 `SAR_FAULT_INJECT` 就是关掉的（生产路径**默认就是关的**）。
要显式清掉，设 `SAR_FAULT_INJECT=`（空串）或 `SAR_FAULT_RUN` 换新批次号（计数归零）。

### 2.3 生产路径的保证（实测）

- **默认关闭时**：钩子函数体只剩一次 `process.env` 读取与字符串比较 —— 不加 sleep、不多一次 I/O、不改任何返回值。
- **落盘逐字节相同**：同一份内容，钩子关 / 钩子开（无效 token 空转）各写一份，**逐字节相同**（探针输出：`各 11 字节`）。
- **开销**：200 次写入，关 670ms / 开（空转）747ms（另一次测量 593ms / 629ms）⇒ 1.06x~1.11x，两次测量都在**运行噪声量级**（每次写入的耗时由 fs I/O 主导）。
- **只有一处读这个环境变量**：`plugin/scripts/lessons.mjs`（全仓 grep 只有它）。闸门脚本不读、不传。

探针：`docs/audit/.tmp-f02/probe-fault-neutrality.mjs`（真实输出见 §5.4）。

### 2.4 为什么钩子放在生产代码里（取舍，如实写）

放在生产文件里才能覆盖**真实路径**（闸门子进程 → `writeFileLocked` → `fs.renameSync`），
放在测试侧 mock 就测不到「Windows 那个错误码」这条真实分支。
代价是：环境里若有人**故意**设 `SAR_FAULT_INJECT`，写入路径会被注入故障。
这是**测试专用旋钮进入生产代码**的固有代价，用「默认关闭 + 只认一个带前缀的变量名」把风险面压到最小。
**若父会话认为不可接受**，可选方案：把钩子挪进一个仅测试构建才注入的模块（需要改构建流程），或由父会话在契约里写明「生产环境必须清空该变量」—— 见 §8 待父会话决定项。

## 3. 逐条：现象 → 结论 → 改哪段 → 哪条断言 → 回退后变红 → 残余风险

### D-59 —— Windows 上 rename 覆盖被占用文件报 EPERM

- **验收方说的现象**：实现正确（`lessons.mjs:474` 重试 40 次、只对 EPERM/EBUSY/EACCES 重试），但回退后回归 **0 红** —— 没有断言钉住它。
- **我的复核结论**：实现正确属实；「0 红」属实 —— 上一轮 `mutations.json` 里没有针对 rename 重试的变异体。
- **改哪一段**：`plugin/scripts/lessons.mjs`
  - 重试循环次数改用常量 `RENAME_MAX_ATTEMPTS`（40），退避改用 `RENAME_BACKOFF_BASE_MS`(25) / `RENAME_BACKOFF_STEP_MS`(10)；
  - 循环体第一行加 `faultRename();`（故障注入点，默认 no-op）；
  - 新增**导出常量** `RENAME_RETRY_WINDOW_MS`（= 40×25 + 10×(0+…+39) = **8800ms**，由同一组常量算出，不另写一份数字）。
- **加了哪条专属断言**（`tests/lessons-test.mjs` §17 / `tests/records-test.mjs` §21，走真实闸门子进程）：
  1. `D-59 rename 遇 EPERM 会重试（写入不静默少条目）` —— 注入 `rename-eperm:1`，写入仍须 `ok:true`；
  2. `D-59 重试后条目真的落盘` —— 文件里必须有新条目（防「返回成功但没写进去」）。
  3. 履历侧同款两条（`D-59 履历侧…`）—— 证明修的是共享代码。
- **回退后变红的真实输出**（§5.2 的 M1）：
  ```
  RED FAIL D-59 rename 遇 EPERM 会重试（写入不静默少条目） :: ["写入失败：故障注入：rename 覆盖被占用文件（Windows EPERM）"]
  RED FAIL D-59 重试后条目真的落盘
  ```
- **残余风险**：重试窗口仍是**实测驱动**的（8.8s）。若某台机器上杀软占用文件超过 8.8s，写入仍会失败 —— 但会**明确失败**（返回 `ok:false`），不谎报成功。窗口调大要连带调 D-62 的等待超时（两者有耦合，见 D-62 的断言 3）。

### D-60 —— 落盘回读校验失败未回滚，一次失败写入抹掉前序条目

- **验收方说的现象**：实现正确（`lessons.mjs:493-517` 有回滚），回退后 **0 红**。
- **我的复核结论**：实现正确属实；「0 红」属实。
- **改哪一段**：`plugin/scripts/lessons.mjs` —— 回读之前插入故障注入点 `faultVerifyOverwrite(file);`（默认 no-op）。回滚逻辑本身**未改**（本轮只补断言与注入点）。
- **加了哪条专属断言**：
  1. `D-60 回读校验失败时判失败（不谎报成功）` —— 注入 `verify-fail` 后必须 `ok:false`；
  2. `D-60 校验失败已回滚（前序条目未被这次失败写入抹掉）` —— **文件内容必须与写入前逐字节相同**（存量条目还在、新条目没落）。
  3. 履历侧同款两条（`D-60 履历侧…`）。
- **回退后变红的真实输出**（§5.2 的 M2）：
  ```
  RED FAIL D-60 校验失败已回滚（前序条目未被这次失败写入抹掉） :: 写入前 277 字 / 写入后 27 字 / 仍含存量=false
  RED FAIL D-60 履历侧校验失败已回滚（前序履历未被这次失败写入抹掉） :: 写入前 277 字 / 写入后 27 字
  ```
  （277 字 → 27 字 = 前序条目被整段抹掉，正是 D-60 的后果。）
- **残余风险**：
  - 断言判的是「失败写入对文件**无副作用**」这一**不变量**，不判错误文案 —— 文案里的「已回滚」三个字可以骗人，文件内容不会。
  - 回滚本身失败时仍返回 `ok:false`（不谎报），但文件可能已被覆盖（代码注释写明「至少没有谎报成功」）。这一极端情形**本轮未做断言**（要稳定复现「回滚也失败」需要再开一个注入点，未做）。

### D-61 —— Windows 抢锁报 EPERM 被误判成失败（锁本身是对的）

- **验收方说的现象**：实现正确（`EEXIST || EPERM` 一律当「暂时拿不到」），但暴露**时敏**：一次跑出 2 红、另一次跑出 0 红。
- **我的复核结论**：时敏的根因是它靠**真实 Windows 抢锁竞态**暴露 —— 撞到 EPERM 才红。本轮改用**指定错误**，时敏消失。
- **改哪一段**：`plugin/scripts/lessons.mjs` —— `withFileLock` 的 `fs.openSync(lock,'wx')` 前插入 `faultLockOpen();`（默认 no-op）。
- **加了哪条专属断言**：
  1. `D-61 抢锁遇 EPERM 当作「暂时拿不到」继续等（不误判失败）` —— 注入 `lock-eperm:1` 后写入仍须 `ok:true`；
  2. `D-61 等到锁之后写入真的落盘`。
- **回退后变红的真实输出**（§5.2 的 M3，**连跑 3 次，每次都红，且红的是同两条**）：
  ```
  RED FAIL D-61 抢锁遇 EPERM 当作「暂时拿不到」继续等（不误判失败） :: ["获取写锁失败：故障注入：排他创建锁文件被拒（Windows ERROR_SHARING_VIOLATION）"]
  RED FAIL D-61 等到锁之后写入真的落盘
  ```
- **残余风险**：钩子模拟的是「open 抛 EPERM」这一**错误码**，不是 Windows 上真实的 sharing-violation 时序；
  真实时序下还可能有别的错误码（如 `EBUSY`）落到「不是 EEXIST 也不是 EPERM ⇒ 直接判失败」的分支 —— 本轮**未覆盖** `EBUSY`（要不要一起当「暂时拿不到」是取舍：真权限问题也会走到超时，文案说清「拿不到锁」，不谎报成别的原因）。

### D-62 —— 锁等待超时（15s）短于持有者的重试窗口（8.8s）

- **验收方说的现象**：实现正确（60s / 180s），回退后 **0 红**。
- **我的复核结论**：实现正确属实；「0 红」属实。**另有一处要更正验收方的判据**：
  台账与 brief 把「偷锁阈值 > 等待超时」当作 D-62 的**真正正确性条件**，但**修复前的值也满足这条**（偷锁 60s > 等待 15s）——
  也就是说这条关系**区分不了改前改后**。真正区分的是**等待超时的量级**（排队容忍度），见下。
- **改哪一段**：`plugin/scripts/lessons.mjs`
  - 把锁参数从函数体里的字面量提成**导出常量**：`LOCK_WAIT_TIMEOUT_MS = 60000`、`LOCK_STALE_MS = 180000`；
  - 新增导出常量 `RENAME_RETRY_WINDOW_MS = 8800`（持有者一个临界区的最坏时长）；
  - `withFileLock` 改用常量。
- **加了哪条专属断言**（配置三条 + 行为两条）：
  1. `D-62 偷锁阈值 > 等待超时（不能把还在用的锁当陈旧锁偷走）` —— 台账写明的条件（**但它区分不了改前改后**，见 §3 的更正）；
  2. `D-62 等待超时 > 持有者最坏临界区（rename 重试窗口）` —— 60000 > 8800；
  3. `D-62 等待超时应容得下编排层最大并发数（6）轮持有者` —— **这条才是区分改前改后的那一条**：
     判据 = `LOCK_WAIT_TIMEOUT_MS >= MAX_ACTIVE_DISPATCHES × RENAME_RETRY_WINDOW_MS`。
     **为什么锚 `MAX_ACTIVE_DISPATCHES`**：编排层同时最多 6 个派工在飞（`lib.mjs:117`，导出常量），
     每个写入方的临界区最坏 8.8s ⇒ 等待超时必须容得下 6 轮 = **52800ms**。
     修复前 15000ms 只容得下 1 轮（第二个排队方即被误判失败）⇒ 15000 < 52800 ⇒ **红**。
     这条是**可验算**的：不是「感觉 60s 够了」，而是从两个系统常量算出来的。
  4. `D-62 锁被占用时排队写入方不被误判失败`（**行为**）—— 真起一个持锁子进程占锁 **16s**（**必须 > 修复前的 15s 超时**，否则旧口径也会绿 ⇒ 断言没有区分力），排队写入方必须等出来并成功；
  5. `D-62 排队写入方确实等到了锁释放` —— 实测等待 ≥ 持锁时长 − 500ms。
- **回退后变红的真实输出**（§5.2 的 M4）：
  ```
  RED FAIL D-62 等待超时应容得下编排层最大并发数（6）轮持有者 :: 等待超时=15000ms 需要>=52800ms
  RED FAIL D-62 锁被占用时排队写入方不被误判失败 :: {"ok":false,"errors":["获取写锁超时（15000ms）：sa-d62-queue.md 正被另一个写入占用 —— 不放行，避免写进去又被覆盖"]}
  RED FAIL D-62 排队写入方确实等到了锁释放（等 15092ms ≥ 持锁 16000ms） :: 实际等待=15092ms
  ```
  注意：`D-62 偷锁阈值 > 等待超时` 这条在 M4 下**仍然是绿的**（60000 > 15000）—— 这正是上面那处更正。
- **残余风险**：
  - 行为断言让 `lessons-test` 多花 **~16s**（基线 20.2s，其中 16s 是持锁等待）。这是确定性换来的代价，已在回归耗时里显式说明。
  - 「容得下 6 轮」是按 `MAX_ACTIVE_DISPATCHES` 推的**上限**，实际排队深度可能更大（同一账本被多次写）；若将来该常量调大，等待超时必须同步调大 —— 断言 3 会把它顶出来。
  - 偷锁阈值 180s：持有者崩溃留下的锁要等 180s 才被偷。正常路径不受影响（毫秒级完成）。

## 4. 顺手复核 D-52 那条并发断言的时敏性

### 4.1 复核结论

D-52 的断言在**修复后**是稳定的（每次 12/16 条全落盘），但它在**回退后**是概率性的 ——
错峰起跑时后起的进程读到的快照已含前几条，就丢不了条目，断言会「碰巧绿」（上一轮：同一变异体一次 2 红、一次 0 红）。
根因有两条：**错峰**（起跑时刻不齐）与**判据形态**（「条数 == 固定值」把「静默丢」与「明确失败」混成同一个红）。

### 4.2 改了什么（三处）

1. **起跑号牌**（`tests/lessons-test.mjs` 的 `makeBarrierRunner` / `spawnBarrier`、`tests/records-test.mjs` 同款）：
   所有写入方先在起跑线上等号，号令一发同时冲 ⇒ 读快照的窗口必然重叠 ⇒ 旧口径**必然**丢条目 ⇒ 红了就是稳定红。
   号牌脚本写在**临时目录**里（不进仓库），环境显式带 `MINIMAX_PROJECT_DIR` / `PLUGIN_DATA`（D-64 同族纪律：夹具不带全套环境就会写到真实项目里去 —— 本轮第一版就踩了这个坑，已修）。
2. **判据换成不变量**：`说成功的写入集合 == 实际落盘的条目集合`（一个不多、一个不少）。
   - 静默丢（返回 ok 却没落盘）⇒ 集合不相等 ⇒ **红**；
   - 明确失败（返回 ok:false）⇒ 集合仍相等 ⇒ **不红**，由另一条「无明确失败」断言单独盯着。
   这就把两类问题分开了：固定条数判据做不到这一点。
3. **逐条标记去掉子串歧义**：标记从 `并发+i` 改成 `并发标记+i+号`（`'并发标记1号'` 不是 `'并发标记10号'` 的子串，否则「逐条都在」会串）。

### 4.3 新增/改写的断言

| 断言 | 判据 |
|---|---|
| `D-52 并发写入不丢条目（说成功的都真落盘：12 并发 × 3 轮）` | 不变量：ok 集合 == 落盘集合 |
| `D-52 并发写入的每一条都在文件里` | 12 条标记逐条在文件里 |
| `D-52 并发写入无明确失败（每一次写入都真的落盘）` | 明确失败数 == 0 |
| `D-52 并发写入全部返回成功或明确失败（不谎报）` | 每次写入都有明确成败（无「无法判定」） |

### 4.4 区分力实测（§5.3）：三个 D-52 变异体连跑 3 次，每次都红

## 7. 残余风险汇总

1. **故障注入钩子在生产代码里**（§2.4）：默认关闭；风险是有人故意设环境变量。
2. **D-62 行为断言贵**（16s/次）：CI 时间会变长；若嫌慢可调小，但**不能调到 < 15s**，否则失去区分力。
3. **D-61 未覆盖 `EBUSY`**：抢锁若报 EBUSY，仍会被判成「获取写锁失败」。要不要一起当「暂时拿不到」是取舍，未做。
4. **「回滚本身失败」未做断言**：要稳定复现需要再开一个注入点，本轮未做（代码里保留了「至少没有谎报成功」的注释）。
5. **钩子模拟的是错误码，不是真实时序**：D-59/D-61 的断言证明的是「收到 EPERM 时怎么办」的**处置逻辑**正确，
   不是「Windows 一定会产生这个错误码」。错误码本身的来源是上一轮实测（真实并发 16 次有 2 次 EPERM）。
6. **只验了 Windows**（win32 / PowerShell 5.1 / Node v26.7.0）。Linux/macOS 未验证。
7. **变异检验只覆盖本轮这 7 个变异体**：不能证明「所有可能的重构都会红」。
