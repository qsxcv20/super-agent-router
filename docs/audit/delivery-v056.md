# Super-agent 编排系统交付报告（v0.5.0 → v0.5.6）

> 本文件是**交付说明**，不是宣传稿。每一句断言要么指得到一行代码，要么指得到一份可复现的输出；
> 指不到的断言不写。

## 0. 一句话

**会话即系统**：一个主 agent（管理层）把任务按专项归属路由给成员、组队派工、独立验收、复盘沉淀，
全部跑在插件的三个 Hook（SessionStart / PreToolUse / SubagentStop）上 ——
机制在插件包里（可分发），数据在项目里（可 git、可审计）。

## 1. 这套东西由什么组成

### 1.1 五个阶段（每个阶段都有代码强制，不是靠自觉）

| 阶段 | 落点 | 强制点 |
|---|---|---|
| 路由 | `.superagent/roster.json` + 成员账号表 | 名录是唯一路由依据；名录有而账号没有 ⇒ 派工被拒（D-37） |
| 组队 | 派工台账 `dispatches.json` | 同 SCOPE 的在飞派工冲突即拒；并发/累计名额有上限（上限可由管理员显式调整，D-69） |
| 派工 | `PreToolUse(task)` 钩子 | 派工必须带 SCOPE 白名单，否则**拒绝派发**；SCOPE 不得覆盖成员的私有记忆目录 |
| 验收 | `SubagentStop` + 独立 verifier | worker 自述不算完成；产出必须是可核验的文件 |
| 复盘 | 错题本 / 履历 | 写入过闸门（七字段、编号不跳号、履历验收方必须真实存在） |

### 1.2 三层结构

- **机制**（插件包 `plugin/`）：判定逻辑、协议文档、脚本。可分发、可升级。
- **数据**（项目 `.superagent/`）：专项名录、每个成员自己的错题本与方法论、变更留痕。可 git、可审计。
- **运行**（派工台账 `~/.minimax/v2/plugin-data/hooks/super-agent-router/`）：在飞派工、越界待审清单、名额计数。

## 2. 用户的诉求，逐条交代

### 2.1 「把子代理的权限放开到自动审核」

**已落地**：机制走三个 Hook，装在插件包里，跨项目可用。

| 层 | 谁做 | 做什么 |
|---|---|---|
| 发现 | **自动** | 撞墙当场写进台账 `scope_requests[]`，同目标重复撞墙只记一条 |
| 记账 | **自动** | 每条带 agent / 工具 / 模式 / 目标 / 次数 / 派工 id |
| 批准 | **父会话（管理员）** | 一条命令逐条批或拒，理由留痕 |

**为什么没有「自动批准」**：让被约束者自己决定边界 = 授权模型当场被拆掉。
自动的是发现与记账；**批准权始终在管理员手里**。

### 2.2 「加上『全部』这个等级，别限制得太死」

**已落地**：两个等级 `scoped` / `full`，`full` = 项目工作区内自由读写，不必逐路径枚举。

### 2.3 「每个成员都是平等的成员」

**已落地**：`full` **不是某些成员的特权** —— 名录里任何成员都可以被提权，提权命令对全体成员一视同仁。
当前名录 8 名成员：6 名 `full`（含全部 5 个专项成员与内置 `worker`）、2 名内置成员保持 `scoped`（`explore` / `verifier`）——
这两个是**内置成员**，不归本项目提权，名录里没有 `tier_granted_by`（它们本来就是 `scoped`）。

提权走管理员 CLI，批准人必须是**真实父会话 id**（不能写「router」这种自称），
写进 `.superagent/roster.json` 并留痕 `.superagent/changes.log`。
本轮已把 6 名成员的历史留痕**重新对齐**（先收回、再授予，批准人 = 真实父会话 id）——
机制只校验**新**提权的批准人，不校验存量值，这是台账 D-71。

### 2.4 「成员给管理员做事情肯定要权限」

**已落地**：批准权能**真的**给出权限，且升级**必须显式留痕**（台账 D-75）。

- 管理员 `--grant` 批准一条「只读条目上的写请求」时，只读会被升级成可写 —— **升级能力保留**
  （堵死批准权会与本条诉求相反）。
- 但升级**不许静默**：回执与变更账都要写明「哪个路径从哪个只读条目升级成了可写」。
- 实现：`plugin/scripts/lib.mjs` 的 `detectReadonlyUpgrades()`；`plugin/scripts/scope-amend.mjs` 的两条扩权路径
  （`--grant` 与 `--dispatch --add`）都走它；回执新增 `upgraded_paths` / `upgraded_from_readonly` / `upgrade_notice` 三个字段，
  **既有字段语义一个字不改**。
- 读请求仍只授读（`ro:`），不因批准而变成可写。

### 2.5 「为什么每次派工都新开一个窗口？成员每次都要重读整个仓库」

**已落地 —— 而且是三条可核验的机制改动，不只是纪律。**

用户的原话：「每一次都开新的窗口会造成很大的上下文的一个浪费……每一次那个成员都要重新读一整个仓库」。
这不是风格问题，是**成本**：新开一个子会话 = 那位成员要重读方法论、契约、缺陷台账、相关脚本与既有报告。

| 改动 | 落点 | 作用 |
|---|---|---|
| 契约 **S4.5「会话复用」** | `plugin/skills/super-agent-router/references/contract.md` | 同一专项的连续工作**优先追加到已有子会话**，不新开 |
| **派工回执的复用提示** | `plugin/scripts/dispatch.mjs` | 若该成员已有会话的边界覆盖本单，回执提示「优先追加而不是新开」（**只提示，不阻断**） |
| **父会话作业规则** | `.superagent/STATUS.md` | 每次派工前必查：覆盖就追加，不覆盖才新开；外加**复用率**指标（会话数应远小于派工单数） |
| **复用台账** | `docs/audit/.tmp-parent/reuse-registry.md` | 哪个会话、已加载了什么、边界是什么、适用/不适用场景 —— 不靠记忆 |

**实测出的三条边界**（都是踩出来的，写进了契约）：

1. **复用可行且保留上下文**：`task_append` 到**已结束**的子会话会把它唤起（`mode: activated`），上下文完整保留
   —— 实测唤起 D-72 那一单，它准确复述了自己改过的四层判定、707 条断言、5 个变异体与报告路径。
2. **复用 ⇒ 边界冻结**：`guard.mjs` 先 `findBinding(ledger, sessionId)`，命中就直接用旧 binding；
   已结束的派工不能再扩权 ⇒ **追加消息里写的 SCOPE 不生效**。
3. **追加消息里的 SCOPE 行有反作用**：闸门会拿 transcript 里的 SCOPE 行参与边界解析，
   写成顿号 + 反引号的形式 ⇒ 解析出 0 条 ⇒ **整个会话的工具调用全被拒**（实测让 D-75 那一单整轮瘫掉）。
   ⇒ 追加内容里要么不写 SCOPE，要么写成协议格式（`SCOPE: a, b, c`）。

**窗口收敛（本机实测）**：归档了 34 个「产物已落盘、下一步不在这些文件上」的老会话 ——
sa-mechanism-fix 13 → **6**，sa-gate-integrity 7 → **2**，sa-plugin-release 4 → **1**，
sa-orchestration-audit 4 → **1**，sa-context-trace 3 → **1**，verifier 19 → **2**；
全部成员 52 → **27**（explore 7 / worker 7 属其它项目，未动）。
**归档与复用互斥**：归档过的会话不能再被追加（`TASK_CHILD_ARCHIVED`）⇒ 归档前先想清楚这个会话将来还要不要续。

## 3. 权限机制是怎么设计的

### 3.1 三层：发现 → 记账 → 批准（**没有「自动批准」**）

| 层 | 谁做 | 做什么 |
|---|---|---|
| 发现 | **自动** | 撞墙当场写进台账 `scope_requests[]`，同目标重复撞墙只记一条 |
| 记账 | **自动** | 每条带 agent / 工具 / 模式 / 目标 / 次数 / 派工 id |
| 批准 | **父会话（管理员）** | 一条命令逐条批或拒，理由留痕 |

**为什么没有自动批准**：让被约束者自己决定边界 = 授权模型当场被拆掉。
自动的是发现与记账；**批准权始终在管理员手里**。

### 3.2 两个等级，成员之间**平等**

| 等级 | 含义 |
|---|---|
| `scoped`（默认） | 逐路径白名单；白名单外一律拦，越界自动记账 |
| `full` | 项目工作区内自由读写，不必逐路径枚举 |

**`full` 不是某些成员的特权** —— 名录里任何成员都可以被提权，提权命令对全体成员一视同仁。
当前名录里 6 名成员是 `full`（含 3 个内置成员与全部 5 个专项成员），2 名内置成员保持 `scoped`（`explore` / `verifier`）。

提权走管理员 CLI，批准人必须是**真实父会话 id**（不能写「router」这种自称），
写进 `.superagent/roster.json` 并留痕 `.superagent/changes.log`。

### 3.3 `full` 的四条例外（逐条落在代码里，不是文档承诺）

1. 编排层私有状态目录（成员的错题本与方法论所在处）—— 那是成员互相篡位、自己给自己提权的战场；
2. 工作区之外的路径 —— 仍拦，但记账，可逐条批准；
3. 账号级 / 对外不可逆动作（**删除成员、改写成员、建号**、部署、发布）—— 硬拦；
4. 写冲突检测仍按**声明的 SCOPE** 比对 —— `full` 放开的是白名单外的项目内路径，不是冲突检测。

### 3.4 等级按派工时快照

派工那一刻把成员的 tier 写进派工记录，子会话绑定继承这份快照 ——
会话中途的等级变更对**已在飞**的会话不生效（下一个派工才按新等级生效）。
这条是上一轮独立验收实测出来的：管理员在会话中途提权，正在飞的 worker 读白名单外文件**仍被拦**。

### 3.5 诚实边界：护栏是护栏不是沙箱

- **有代码保证**：凡是通过**本插件包里的官方脚本**（任何一份副本 —— 仓库 / 安装目录 / 运行时缓存树，
  判据是**插件包身份**）提权或批准扩权，子代理一律被拦。
- **仍然没有保证**：把脚本复制一份改名再执行（复制品不在插件包目录树下，归属判不出来），
  或用内联代码直接写文件（复合层只判危险操作，作用域交回内层调用）。
- **不是防线的那一条**：「批准人必须是真实父会话 id」是**纵深防御** —— worker 的派工原文里就带着
  `PARENT SESSION:`，照抄就能过。主防线是「插件包身份归属」那条判定。
- 真正的兜底是：运行时权限 + 审计留痕 + **验收时复核**。

## 5. 验证与验收历史

### 5.1 机制层：合成载荷 vs 真实链路（两问，分开取证）

**机制对不对**（判定分支写得对不对）用合成载荷验；
**链路通不通**（平台会不会真把这个工具调用派发给护栏）**只能用真实子会话 + 可观测的触发记录**。

本轮这条区分救了我们一次：

- 早前一次阴性观察（全库 1640 次 `run_code` 调用 0 次被护栏直接拒答 + 一次日志探针）
  被写成了「平台不对容器派发 PreToolUse」的**平台事实**。
- 两天后**金丝雀复测**证明平台**确实**派发并当场 DENY —— 同一份代码形状在不同时刻行为不同，
  **差异来自会话绑定，不是平台性质**。
- ⇒ 阴性样本本身没错，错的是**推广**。现在规则是：凡是「X 没有发生 / 机制不存在」的结论，
  必须同时具备 ① **金丝雀**（同一形状的阳性对照，预期会发生且确实发生了）② **时间戳** ③ **会话/环境标识**。
  缺一件只能写成「该次如此」，不能写成「平台如此」。

### 6.3 机制「自己也犯过」的错（这部分值得单独说）

本轮修的缺陷里，有三条是**机制自己**犯的，而且都是同一类错：

1. **D-72**：watchdog 把「这个文件**没有创建**」判成「声称产出」⇒ 连续 block 诚实的报告，
   **实质在逼成员去创建那个文件**。活体证据：探针成员的 thinking 里已经在「把交付说明改写成能骗过闸门的形状」。
2. **D-77**：派工台账是**无锁的读-改-写** ⇒ 并发写**静默丢记录**。
   活体证据：D-72 那一单在台账里**根本没有记录**（查不到 dispatch_id / scope / session），
   而它确实在跑、确实在改文件 ⇒ 「组队冲突」闸门**看不见**它 ⇒ 两个 worker 可以同时写同一处。
3. **D-78**：watchdog 的路径归属停在**行**级 ⇒ 同一行里与产出动词无关的路径（典型是**引用护栏自己的拒绝原文**）
   被一并认领成「声称产出」。

这三条的共同点：**失败方向都是「静默」** —— 不报错、不抛异常、文件格式合法、内容看着正常。
一个「看起来正常」的错，比一个「明确报错」的错危险得多，因为它连被发现的路径都没有。

## 8. 怎么用（最短路径）

### 8.1 装在哪
- **机制（插件包）**：`C:\Users\yang2\.minimax\plugins\super-agent-router\` —— 由本仓库 `plugin/` 部署而来。
- **数据（项目）**：`.superagent/`（专项名录、每个成员自己的方法论与错题本、变更留痕）—— 可 git、可审计。
- **运行（台账）**：`~/.minimax/v2/plugin-data/hooks/super-agent-router/`（在飞派工、越界待审清单、名额计数）。

部署（仓库 → 安装副本 → 运行时缓存树）：

```powershell
node tools\deploy-plugin.mjs
```

### 8.2 怎么开始用
主 agent 在项目里开一个会话，说你的需求即可。
**SessionStart 会自动注入编排协议**（你会在会话开头看到「[super-agent-router] 本会话已启用 Super-agent 编排机制」），
主 agent 据此路由、组队、派工、验收、复盘 —— 不需要你手动喊「组队」。

### 8.3 怎么确认 Hook 真的生效
1. **插件装好或更新之后，必须新开一个会话** —— Hook 按会话激活，旧会话不会重跑 SessionStart。
2. 新会话开头应出现上面那句启用提示；没有 ⇒ 没生效。
3. 派工一单，回执里应出现：成员、边界条目、层级、**复用提示**（若该成员已有可复用会话）、或明确的拒绝理由。

### 8.4 不生效时按这个顺序查
1. **是不是没新开会话**（装/更新后最常见）。
2. 版本对不对：`node tools\deploy-plugin.mjs` 输出末尾的 `INSTALLED_VERSION`。
3. 危险动作的 matcher 齐不齐：`plugin/hooks/hooks.json` 里必须登记**删除成员 / 改写成员 / 建号 / 部署 / 发布**这几类工具名。
4. 台账在不在：`node plugin\scripts\scope-amend.mjs --list` 能列出待审清单（读不出来 = 边界不可信，机制会拒放行）。
5. 派工被拒时**读回执**：回执会写清是哪一道闸门 —— 边界为空 / SCOPE 冲突 / 名额超限 / 成员不存在 / 名单不可得未核验。

### 8.5 父会话（管理层）的三条日常纪律
1. **复用优先**：同一专项的连续工作追加到已有子会话，不新开（派工前查复用台账）。
2. **发布前跑回归**：`node tools\run-tests.mjs --all --root plugin --repo .` 必须 0 FAIL。
3. **worker 自述不算完成**：必须由独立 verifier 复核，FAIL 要返工重验。
